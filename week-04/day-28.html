2. 全景图:一个 HTTP 请求从浏览器到 K8s 的完整链路

我们以一个具体场景为例:用户在网页上和你的 LLM 产品对话,前端向 https://api.your-llm.com/v1/chat/completions 发起一个 POST 请求,后端是部署在 Kubernetes 集群里的 vLLM 推理服务。整条链路长这样:

┌── 客户端(浏览器/App)─────────────────────────────────────────────┐ │ ① DNS 解析 api.your-llm.com → IP │ │ ② TCP 三次握手(与最近的边缘节点) │ │ ③ TLS 握手(证书验证 + 密钥协商) │ │ ④ 发送 HTTP 请求(方法/Header/Body) │ └───────────────────────────────┬─────────────────────────────────┘ │ 公网,可能 20~200ms ┌────────────▼────────────┐ │ ⑤ CDN / 边缘 POP │ 静态命中就地返回;动态回源 └────────────┬────────────┘ │ ┌────────────▼────────────┐ │ ⑥ L4 负载均衡(云 LB/LVS)│ 按 IP:端口分发,不看内容 └────────────┬────────────┘ │ 进入你的 VPC / 数据中心 ┌────────────▼────────────┐ │ ⑦ Ingress / L7 网关 │ Nginx/APISIX/Envoy: │ TLS 终止 + 路由 + │ 看 URL/Header、限流、鉴权 │ 限流 + 鉴权(JWT) │ └────────────┬────────────┘ │ 集群内网(east-west) ┌──────────────────▼──────────────────┐ │ ⑧ K8s Service(ClusterIP) │ 虚拟 IP,kube-proxy/IPVS │ ⑨ 选一个健康的 Pod(Endpoints) │ 负载均衡到具体 Pod └──────────────────┬──────────────────┘ │ ┌────────────▼────────────┐ │ ⑩ Pod 内:sidecar(可选) │ Envoy mTLS、遥测 │ ⑪ 应用进程(vLLM) │ 排队 → prefill → decode └────────────┬────────────┘ │ 可能再去下游 ┌──────────────────▼──────────────────┐ │ ⑫ 依赖:Redis(会话/限流)、 │ │ pgvector(RAG 检索)、GPU(推理) │ └──────────────────┬──────────────────┘ │ ⑬ 生成响应 → ⑭ 原路(SSE 流式)返回每个 token

这张图值得你反复默画。它的价值在于:任何一次"接口慢"或"接口 500",故障点必然落在这 14 个阶段中的某一个。一个成熟的工程师和新手的区别,不在于会不会写业务代码,而在于报警响起时,能不能在 30 秒内说出"我怀疑是第 ⑦ 层网关限流"还是"第 ⑪ 层 GPU 排队"——然后精准地去那一层验证。

3. 逐段拆解:14 个阶段每一步在做什么

① DNS 解析(把域名变成 IP)

浏览器先查本地缓存 → 操作系统缓存 → 配置的递归 DNS(如 8.8.8.8)→ 一路问到权威服务器。类比:你知道朋友叫"张三"(域名),但寄快递需要门牌号(IP),DNS 就是那本电话簿。首次解析可能几十毫秒,之后靠 TTL 缓存几乎为 0。返回的往往是 CDN 的地址(用 CNAME + 地理调度,把你导向最近的节点)。

② TCP 三次握手 / ③ TLS 握手

拿到 IP 后建立 TCP 连接(SYN→SYN-ACK→ACK,一个 RTT)。然后 TLS 握手:验证证书链、协商对称密钥。TLS 1.3 只要 1 个 RTT,还支持 0-RTT 会话恢复——这是为什么 Week03 我们强调 TLS 版本很重要。跨洋链路一个 RTT 就是 100~200ms,握手成本在长尾延迟里非常显眼,所以 HTTP keep-alive、连接池、HTTP/2 多路复用才这么关键:它们让后续请求复用已经建好的连接,省掉重复握手。

④ 发送 HTTP 请求 / ⑤ CDN 边缘

请求先到达 CDN 的边缘 POP(Point of Presence)。静态资源(图片、JS)在这里直接命中返回,永远到不了你的服务器。像 /v1/chat 这种动态 API 则"回源"——转发到你真正的后端。CDN 顺带做的事:DDoS 清洗、WAF、TLS 终止、gzip/brotli 压缩。

⑥ L4 负载均衡 / ⑦ L7 网关

这是 Week04 的主战场。L4 负载均衡(云厂商的 NLB、LVS)工作在传输层,只看 IP:端口 就把连接转发出去,快但"看不懂"请求内容。L7 网关(Nginx/APISIX/Envoy Ingress)工作在应用层,能看到 URL、Header、Cookie,因此能做:按路径路由(/v1/chat 去 vLLM、/v1/embed 去 embedding 服务)、限流(limit_req)、鉴权(校验 JWT)、灰度发布、TLS 终止。你的第一道限流和鉴权就在这里,是 LLM 服务防刷、防超额的关键关卡。

⑧ K8s Service / ⑨ 选择 Pod

请求进入集群后,目标是一个 Service(一个稳定的虚拟 IP,ClusterIP)。真正干活的是一组会随时扩缩、重启、换 IP 的 Pod。Service 通过 Endpoints 列表知道当前哪些 Pod 是健康的(readiness 探针决定),再由 kube-proxy(iptables 或 IPVS 模式)把流量负载均衡到某个具体 Pod。类比:Service 是公司总机号码,永远不变;Pod 是随时轮岗的接线员,总机负责把你转给一个在岗的人。

⑩ Sidecar / ⑪ 应用进程(vLLM)

如果用了 Service Mesh,请求先经过 Pod 内的 Envoy sidecar(负责 mTLS 加密、重试、遥测),再到你的应用容器。对 vLLM 来说,请求到达后不是立刻算——先进入调度队列,和其他并发请求一起做 continuous batching,然后 prefill(处理你的 prompt)→ decode(逐 token 生成)。这一步往往是整条链路里最慢、方差最大的一段,因为它取决于 GPU 是否空闲、batch 有多满、prompt 有多长。

⑫ 下游依赖 / ⑬⑭ 生成并返回响应

推理过程中可能还要:查 Redis(校验用户配额、取会话历史)、查 pgvector(RAG 检索相关文档)。这些都是串在关键路径上的额外 RTT。最后,LLM 生成的 token 通过 SSE(Server-Sent Events)流式地、一个接一个地沿原路返回给浏览器——这正是 Day22 讲的,为什么 LLM 场景几乎都用 SSE 而不是等全部生成完再一次性返回:用户能立刻看到第一个字(TTFT,首 token 延迟)。

4. 延迟分布:时间到底花在哪里

工程师必须对延迟有数量级的直觉。下面这张表是刻进后端脑子里的"延迟阶梯",记住相对倍数比记住精确值更重要:

操作量级类比(把 1ns 放大成 1 秒)
L1 缓存访问~1 ns1 秒
内存访问~100 ns1.5 分钟
SSD 随机读~16 μs4.5 小时
同机房网络 RTT~0.5 ms5.8 天
Redis 查询~1 ms11 天
PG 索引查询~1–10 ms数周
跨城/跨洋 RTT30–200 ms数年
LLM 首 token(TTFT)100 ms–数 s——(取决于排队+prefill)

两个关键结论:

  • 网络 RTT 比内存慢 5 个数量级,LLM 推理又比一次网络 RTT 慢 2~3 个数量级。所以对 LLM 服务而言,DNS/TCP/TLS 那点握手时间通常是可以忽略的噪声——真正的大头几乎永远在第 ⑪ 层(推理本身)和它的排队。
  • 但"通常"不等于"永远"。当接口出现长尾(P99 突然飙高而 P50 正常),元凶往往不是推理变慢,而是某处重试风暴、连接池耗尽、DNS 超时、TLS 重新握手——这些平时被忽略的小成本在异常时会被放大成灾难。这就是为什么要看分位数(P50/P95/P99)而不是平均值:平均值会把长尾稀释掉,让你完全看不见 1% 用户正在经历的 10 秒卡顿。
心智公式:一次请求的总延迟 ≈ 网络往返 + 网关处理 + 排队等待 + 实际计算 + 下游依赖之和。优化时先问"哪一项占比最大",而不是凭感觉去优化你最熟悉的那一项。这叫 Amdahl 定律的工程直觉——优化占比 5% 的部分,天花板就是 5%。

5. 瓶颈定位:一套自顶向下的排查方法论

当有人说"接口好慢",不要立刻跳进代码。用自顶向下、二分法的思路,沿着第 2 节那张图逐层缩小范围:

  1. 先分清是"慢"还是"错"。看监控:延迟高?还是错误率高?两者排查路径完全不同。
  2. 确定是客户端到网关慢,还是网关到后端慢。这是最重要的一刀。用 curl 的分段计时: 
    curl -w "dns:%{time_namelookup} connect:%{time_connect} \
tls:%{time_appconnect} ttfb:%{time_starttransfer} \
total:%{time_total}\n" -o /dev/null -s https://api.your-llm.com/health
    如果 ttfb(首字节)很大而 connect/tls 正常,说明时间花在服务端处理,而不是网络——直接跳过网络层,去查后端。
  3. 在集群内复现。从一个和后端同机房的 Pod 里直接 curl Service 的 ClusterIP。如果这里也慢,排除掉①~⑦(公网、CDN、网关),问题在⑧之后。这一步瞬间砍掉半条链路。
  4. 看后端自己的分段耗时。理想情况下你的服务有 tracing(OpenTelemetry),一眼能看到"排队 800ms + prefill 200ms + Redis 5ms"。没有 tracing 时,退而求其次看日志时间戳、看 vLLM 的调度指标(队列长度、GPU 利用率)。
  5. 定位到具体资源。如果是排队,看并发是不是超了 batch 容量;如果是某个下游依赖慢,单独压测那个依赖。

常用的分层排查命令速查:

怀疑层命令看什么
DNSdig api.your-llm.com / nslookup解析是否慢、结果是否对
TCP/TLScurl -w 分段 / openssl s_client握手耗时、证书是否有效
连接/端口ss -tan / ss -s大量 TIME_WAIT?连接数打满?
网关Nginx access log $request_time $upstream_response_time时间花在 Nginx 还是 upstream
K8s 路由kubectl get endpoints / describe svc健康 Pod 是否为空、探针是否挂
Pod 内部kubectl logs / exec + curl localhost应用自身耗时、是否 OOM/重启
抓包(终极手段)tcpdump -i any port 8000 -w x.pcap包级别看谁在等谁(Day19/20 学过)

6. 故障诊断:6 类典型故障与它们的指纹

故障不是随机的,它们有可识别的"指纹"。认识这些模式能让你从"瞎猜"进化到"看一眼监控就知道大概是什么":

① 雪崩式重试风暴

某个下游(比如 Redis)短暂抖动 → 上游超时 → 客户端重试 → 请求量瞬间翻几倍 → 把本来能自愈的下游彻底压垮。指纹:错误率和请求量同时陡增,呈自我强化。解药:Day25 学的熔断(快速失败,不再打已知挂掉的下游)、指数退避重试、加抖动(jitter)避免重试同步。

② 连接池 / 端口耗尽

指纹:ss -s 看到海量 TIME_WAIT,新连接建立失败,报 "cannot assign requested address"。常见于短连接 + 高并发。解药:用连接池复用长连接、开启 HTTP keep-alive、必要时调 net.ipv4.ip_local_port_range 和 tcp_tw_reuse。

③ readiness 探针误杀

Pod 启动慢(比如 vLLM 加载 70B 权重要几分钟),但 readiness 探针超时太短 → K8s 以为它没就绪 → 从 Endpoints 摘掉 → 所有 Pod 都被摘 → Service 后端为空 → 全线 503。指纹:kubectl get endpoints 显示地址列表为空。解药:给启动慢的服务配 startupProbe,把就绪判断放宽。

④ P99 长尾(排队问题)

指纹:P50 正常、P99 爆炸。对 LLM 服务,通常是并发请求超过了 GPU 的 batch 承载能力,请求在调度队列里排长队。解药:限流(在网关就把超额请求挡住,而不是让它们进来排队饿死)、扩容 GPU、优化 batch 策略。

⑤ 级联超时配置错误

网关超时 5s,但后端推理正常就要 8s → 网关早早掐断连接返回 504,而后端还在傻傻算完再返回(白白浪费 GPU)。指纹:客户端收到 504 但后端日志显示请求成功完成。解药:超时时间从外到内应该逐层递减——网关超时 > 应用超时 > 单次下游调用超时,且都要留出余量。

⑥ DNS 抖动引发的全局慢

集群内 CoreDNS 压力大或配置了过多 search domain,导致每次服务发现都做多次无用 DNS 查询。指纹:所有服务同时变慢,但各服务自身 CPU/内存都正常。解药:配 ndots、开 NodeLocal DNSCache、用 FQDN 减少 search 展开。

排查心法:故障诊断的本质是不断二分,缩小怀疑范围。每一步都问自己:"我能用一条命令,把嫌疑范围砍掉一半吗?" 而不是一头扎进最可能的那一层。最贵的错误是在错误的层花两小时。

7. Agent 安全视角:这条链路上的完整攻击面

作为做 Agent 安全的人,你看这条链路的方式和纯后端工程师不同——你会问:每一个环节,攻击者能干什么? 把第 2 节那张图重看一遍,每一层都有它的攻击面:

  • ① DNS:DNS 投毒 / DoH 隐蔽信道。攻击者可以把你的服务域名劫持到自己的服务器(中间人),或反过来——被入侵的 Agent 用 DNS 查询作为隐蔽外泄通道(把数据编码进子域名,正是 Day27 讲的 DNS 隧道)。
  • ③ TLS:证书校验被关闭(verify=False 是渗透测试里最常见的低级漏洞)、TLS 剥离、过期证书。mTLS 缺失意味着集群内东西向流量可被嗅探。
  • ⑦ L7 网关:这是鉴权与限流的唯一关卡,一旦绕过就全线失守。攻击点:JWT 未验签 / alg:none 混淆、限流可被分布式 IP 绕过、路径归一化差异导致鉴权绕过(/v1/../admin)。
  • ⑧⑩ 集群内网:一旦攻击者拿到一个 Pod(比如通过一个有漏洞的依赖),集群内网往往是"软内核"——东西向缺乏鉴权。这正是 Day27 反弹 shell 的落地场景:被攻破的 Pod 主动向外连 C2,再横向移动。
  • ⑪ 应用层(LLM 本体):这才是你的主战场——prompt injection、越权工具调用、资源耗尽(超长 prompt 拖垮 GPU 做 DoS)、通过精心构造的输入触发时间侧信道。
  • ⑫ 下游依赖:RAG 检索的 pgvector 若被知识库投毒,等于把恶意指令喂进模型;Redis 未授权访问可导致会话/配额被篡改。

把安全和可观测性结合起来看,你会得到一个强大的洞察:同一套追踪链路请求的手段(tracing、日志、抓包),既是排障工具,也是入侵检测的数据源。 一个"接口 P99 长尾"可能是排队,也可能是攻击者在做资源耗尽;一次"异常的出站 DNS 查询"可能是 CoreDNS 抖动,也可能是数据外泄。会看这条链路的人,既能修故障,也能抓入侵。 这正是你从"只懂 AI 算法"迈向"懂系统的安全工程师"的核心能力。

🔗 与 AI / Agent 安全的连结(5 个具体场景)

场景一:给 LLM 网关设计"多层限流",不能只靠一层。 今天我们看到限流可以发生在 CDN、L7 网关、应用三处。对 LLM 服务,单靠网关按 IP 限流是不够的——攻击者用大量 IP 或合法账号刷你的昂贵推理。正确做法是分层:网关按 IP+账号做粗粒度 QPS 限流,应用层按 token 数/配额做细粒度计费限流(Day25 的多层限流思想 + Redis Lua 原子扣减)。少了任何一层,要么被刷爆 GPU,要么被刷爆账单。

场景二:用"延迟分布"识别针对推理服务的 DoS。 正常流量的 prompt 长度分布是有规律的;攻击者做资源耗尽时,会构造超长上下文让单个请求占满 GPU。把第 4 节的延迟直觉变成检测规则:监控 prompt 长度分布、TTFT 分位数、GPU 排队深度,当它们偏离基线时告警。这是把"性能可观测性"直接变成"安全检测"的典型例子。

场景三:集群内网的"软内核"是 Agent 逃逸后的高速公路。 假设你的 Agent 有一个执行代码的沙箱(Day27 之后我们会在 Phase 3 深入),一旦沙箱逃逸,攻击者面对的就是第 ⑧~⑫ 层这片东西向缺乏鉴权的内网。防御手段正是我们后面要学的:NetworkPolicy(默认拒绝东西向)、mTLS(SPIFFE 工作负载身份)、egress 网关(限制 Pod 只能连白名单,掐断反弹 shell 的出站路径)。今天先建立"内网不可信"这个意识。

场景四:超时配置错误会制造"隐形"的安全与成本问题。 第 6 节⑤那个"网关掐断但后端还在算"的场景,在 LLM 服务里意味着:用户以为失败了会重试,后端却在为已经没人要的请求烧 GPU。攻击者可以故意利用这一点放大资源消耗。正确的超时递减 + 请求取消传播(context cancellation),既是工程正确性,也是抗滥用设计。

场景五:tracing 是排障与取证的共同底座。 当一次可疑请求发生,能不能沿着 traceId 还原它经过的每一跳、调了哪些工具、检索了哪些文档、耗了多少资源?这套能力平时用来定位慢查询,事故时就是取证链。给 Agent 系统从第一天就埋好结构化的、带请求 ID 的全链路日志,是安全和可观测性的公共投资——这也是你未来做 Agent 安全产品时的核心数据资产。

🎯 今日小练习(3 道)

1(动手)分段计时一次真实请求。 挑一个你常用的 API 或网站,运行本文第 5 节那条 curl -w 命令,记录 dns / connect / tls / ttfb / total 五个时间。然后换一个跨国的目标(比如国外的 API)再测一次,对比 connect 和 tls 的差异。回答:这次请求的时间主要花在了哪一段?如果要优化,你会先动哪里?

2(观察)在本地找出 TIME_WAIT。 运行 ss -s 看当前连接状态汇总,再开一个 Python 脚本快速建/断很多短连接(或反复 curl 同一地址),观察 ss -tan | grep TIME-WAIT | wc -l 的数字变化。回答:为什么主动关闭连接的一方会进入 TIME_WAIT?它持续多久(2MSL 是什么)?短连接高并发为什么会因此出问题?

3(思考)画出你自己产品的链路图并标注攻击面。 不写代码,拿张纸,把你正在做的(或设想的)一个 LLM/Agent 服务,按今天第 2 节的方式画成从客户端到后端的完整链路。然后在每一跳旁边写一个问题:"这一层如果被攻破/被绕过,攻击者能拿到什么?我这一层的防御是什么?" 找出你目前防御最薄弱的那一跳——这就是你下周该重点关注的地方。
