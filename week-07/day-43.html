1. GPU vs CPU 的设计哲学：延迟机器 vs 吞吐机器

要理解 GPU，最有效的方式不是先看它的参数表，而是先理解它和 CPU 在「设计目标」上的根本分歧。这两种芯片是为完全不同的问题优化的。

CPU 是一台「延迟优化」机器（latency-oriented）。它的假设是：任务之间高度相关、有大量分支、下一步要干什么取决于上一步的结果。所以 CPU 要让单个任务尽快跑完。为了这个目标，它在一小撮强大的核心里塞满了「加速单个线程」的硬件：庞大的多级缓存（L1/L2/L3 常常占掉芯片一半以上的面积）、复杂的分支预测器、乱序执行引擎、深流水线。这些电路本身不做任何算术——它们的全部工作就是「猜」和「等」，让那几个 ALU 尽量不空闲。

GPU 是一台「吞吐优化」机器（throughput-oriented）。它的假设正好相反：我有海量的、彼此独立的、做着同一件事的小任务（比如给一百万个像素各算一次光照，或者给一个 4096×4096 矩阵的每个元素做一次乘加）。GPU 不在乎「单个任务多快跑完」，它在乎「单位时间内总共完成多少任务」。于是它做了一个截然不同的取舍：把省下来的缓存和控制逻辑的晶体管，全部换成算术单元。

CPU（延迟机器） GPU（吞吐机器） ┌───────┬───────┐ ┌─┬─┬─┬─┬─┬─┬─┬─┬─┬─┐ │ Core │ Core │ │·│·│·│·│·│·│·│·│·│·│ 上千个 ├───────┼───────┤ ├─┼─┼─┼─┼─┼─┼─┼─┼─┼─┤ 小而弱的 │ Core │ Core │ │·│·│·│·│·│·│·│·│·│·│ 算术核心 ├───────┴───────┤ ├─┼─┼─┼─┼─┼─┼─┼─┼─┼─┤ │ 巨大的 L3 │ │·│·│·│·│·│·│·│·│·│·│ │ Cache │ ├─┴─┴─┴─┴─┴─┴─┴─┴─┴─┤ │ 分支预测/乱序 │ │ 小 cache + 高带宽显存 │ └───────────────┘ └───────────────────┘ 几个强核 + 大量控制逻辑 海量弱核 + 极简控制逻辑

一个日常类比：CPU 像一支由几位米其林主厨组成的团队——每人技艺高超、能独立处理复杂的宴席，但总共就那么几个人。GPU 像一个有一万名流水线工人的工厂——每个人只会拧一种螺丝、干得也不算快，但一万人同时拧,总产量碾压主厨团队。让主厨去拧十万颗螺丝是浪费；让流水线工人去做一道需要临场发挥的分子料理，他们又会集体懵掉（这就是 GPU 遇到分支时的性能塌陷，第 2 节会讲）。

深度学习的计算恰好是 GPU 的完美负载：矩阵乘法（GEMM）本质上就是海量独立的乘加运算。一个 Transformer 的前向传播，说到底就是一连串大矩阵相乘。这种「同一个操作、施加在海量数据上、彼此独立」的模式，正是 GPU 生来要吃的。这也是为什么 2012 年 AlexNet 用两块 GTX 580 训练出来后，整个领域一夜之间转向了 GPU。

关键数字感：一块 CPU（如 64 核的 EPYC）峰值双精度算力约 2–4 TFLOPS；一块 H100 的 FP16 Tensor core 算力超过 1000 TFLOPS（1 PFLOPS）。差了 300 倍以上。但代价是 GPU 几乎不能独立跑操作系统、处理复杂分支逻辑——它是 CPU 的「协处理器」，永远需要 CPU 来喂数据、发指令。

2. SIMT 执行模型与 warp：GPU 的调度单位

GPU 有上万个核心，难道每个核心都独立取指、译码、各干各的？如果那样，光是「控制逻辑」的开销就会把省下来的晶体管吃回去。NVIDIA 的答案是 SIMT（Single Instruction, Multiple Threads，单指令多线程）。

你可能听过 CPU 里的 SIMD（单指令多数据，比如 AVX 指令一次处理 8 个 float）。SIMT 是它的「线程化」升级版：GPU 把线程每 32 个打成一捆，这一捆叫一个 warp（线程束）。一个 warp 里的 32 个线程共享同一个程序计数器，在同一时刻执行同一条指令，只是各自作用在不同的数据上。

为什么是 32？这是 NVIDIA 的硬件设计常数（AMD 的对应概念叫 wavefront，历史上是 64）。你写 CUDA 时看似在写「单个线程的代码」，但硬件永远以 warp 为最小调度单位。这带来一个极其重要的性能陷阱——warp divergence（线程束分歧）：

// CUDA kernel 里的一段代码，tid 是线程编号
if (tid % 2 == 0) {
    do_A();   // 偶数线程走这条
} else {
    do_B();   // 奇数线程走这条
}

因为 warp 里 32 个线程必须执行同一条指令，遇到这个 if/else，硬件只能串行化：先让 16 个偶数线程执行 do_A()（此时 16 个奇数线程被「掩码」屏蔽、空转），再让 16 个奇数线程执行 do_B()（此时偶数线程空转）。本该并行的两条路径变成了串行，性能直接腰斩。这就是前面「让流水线工人做临场发挥的料理会集体懵掉」的技术版本——GPU 讨厌分支。

SIMT 还带来一个天才的设计：用并行度来掩盖内存延迟（latency hiding）。CPU 靠大缓存来避免等内存（等一次内存要几百个时钟周期）；GPU 缓存很小，它的策略是——当一个 warp 因为等待显存数据而停顿时，硬件立刻切换到另一个已就绪的 warp 继续算，几乎零成本切换。只要在飞的 warp 足够多，GPU 的算术单元就能一直忙碌，内存延迟被彻底「藏」在计算背后。这就是为什么 GPU 需要「喂给它成千上万个线程」才能跑满——线程太少，延迟藏不住，算力就浪费了。

3. SM 结构：GPU 内部的「小工厂」

一块 GPU 不是「一万个核心的大杂烩」，而是由几十上百个相对独立的流式多处理器（SM，Streaming Multiprocessor）拼起来的。SM 是 GPU 真正的「基本组织单位」——你可以把整块 GPU 想成一座工业园区，每个 SM 是园区里一座独立的小工厂。H100 有 132 个 SM，A100 有 108 个。

每个 SM 内部大致包含这些东西：

  • 若干 CUDA core：做整数和浮点标量运算的基本算术单元（第 4 节详述）。
  • 若干 Tensor core：专门做矩阵乘加的「大杀器」（第 4 节详述）。
  • Warp scheduler（warp 调度器）：负责在众多就绪的 warp 之间挑选下一个执行——这就是第 2 节说的「延迟掩盖」的执行者。
  • 寄存器文件（Register File）：极快、极大（每个 SM 有 64K 个 32 位寄存器），线程私有数据放这里。
  • 共享内存 / L1 缓存（Shared Memory）：SM 内所有线程可见的一块高速片上内存，是手动优化的关键（明天讲 CUDA 时会大量用到）。
  • LD/ST 单元、SFU：负责访存（Load/Store）和特殊函数（sin/exp/sqrt 等）。
整块 GPU (以 H100 为例) ┌────────────────────────────────────────────┐ │ SM ×132 ← 每个 SM 是一座独立小工厂 │ │ ┌──────────────────────────────────────┐ │ │ │ 一个 SM 内部： │ │ │ │ Warp Scheduler ×4 │ │ │ │ CUDA core ×128 Tensor core ×4 │ │ │ │ Register File (256KB) │ │ │ │ Shared Memory / L1 (up to 228KB) │ │ │ └──────────────────────────────────────┘ │ │ │ │ L2 Cache (全 SM 共享, ~50MB) │ │ ───────────────────────────────────────── │ │ HBM 显存 (80GB, ~3.35 TB/s 带宽) │ └────────────────────────────────────────────┘

这张图给你一个重要的内存层级直觉：越靠近算术单元的存储越快越小（寄存器 → 共享内存 → L2 → HBM 显存）。写高性能 CUDA 的核心思想，就是尽量让数据在快的层级（寄存器、共享内存）里多停留、少往慢的 HBM 跑。这个思想会在整个 Week 07、Week 08 反复出现，是 FlashAttention、量化、算子融合等所有优化的底层逻辑。

4. CUDA core vs Tensor core：两种算力单元

初学者最容易混淆的两个词。它们都是 SM 里的算术单元，但干的活完全不同。

CUDA core：通用的标量算术单元

CUDA core 是最基础的算术单元，一个 CUDA core 在一个时钟周期里做一次标量的浮点乘加（FMA：a = a + b*c）。「一万个核心」通常指的就是 CUDA core 的数量（H100 有约 16896 个 FP32 CUDA core）。它通用、灵活，你写的绝大部分逐元素操作（加法、激活函数、归一化）都跑在 CUDA core 上。但它一次只处理一个数，做大矩阵乘法时效率有限。

Tensor core：专用的矩阵乘加引擎

Tensor core 是 Volta 架构（2017，V100）首次引入的专用单元。它不做标量运算，而是一条指令直接完成一个小矩阵块的乘加——比如一次算 D = A×B + C，其中 A、B 是 4×4 或更大的小矩阵。一个 Tensor core 一个周期能顶几十上百个 CUDA core 的矩阵运算吞吐。

为什么专门为矩阵造一个单元？因为深度学习 90% 以上的算力都花在矩阵乘法（GEMM）上。与其用一万个通用 core 笨拙地拼矩阵乘，不如造一批「矩阵专用电路」。这就是领域专用架构（DSA）的思想：牺牲通用性，换特定负载的极致效率。Tensor core 的代价是它只擅长矩阵乘加、且偏好低精度（FP16/BF16/FP8），但这恰好是深度学习需要的。

维度CUDA coreTensor core
处理粒度标量（一次一个数的 FMA）矩阵块（一次一个小矩阵乘加）
擅长逐元素运算、控制流、通用计算GEMM / 卷积 / attention

记住这句话：当你看到「H100 有 1000 TFLOPS」这种夸张数字时，指的几乎都是 Tensor core 的低精度算力，不是 CUDA core 的 FP32 算力（后者只有约 67 TFLOPS）。宣传数字和你实际能用到的算力之间的差距，往往就藏在「是不是 Tensor core、什么精度、稠密还是稀疏」这几个限定词里。

5. 数值单元家族：FP32 / TF32 / FP16 / BF16 / FP8 / INT8

GPU 支持多种数值格式，这不是花架子——精度越低，同样的芯片面积能塞下越多的算术单元、显存能装下越多的参数、带宽能搬越多的数据，于是算力和容量成倍增长。这是大模型能跑起来的关键之一。理解这几种格式的构成很重要：

格式总位数符号/指数/尾数特点与用途
FP64641/11/52双精度，科学计算用；深度学习几乎不用
FP32321/8/23单精度，训练的传统「标准精度」
TF3219*1/8/10NVIDIA 专有：FP32 的指数 + FP16 的尾数，A100 起 Tensor core 默认用，几乎无损换 8 倍吞吐
FP16161/5/10半精度，动态范围小（易溢出），需配 loss scaling
BF16161/8/7指数和 FP32 一样宽 → 动态范围大、训练更稳，尾数少 → 精度略低。现代大模型训练主力
FP8 (E4M3/E5M2)81/4/3 或 1/5/2H100 起支持，推理和部分训练用，需精细校准

这里最值得记住的对比是 FP16 vs BF16。两者都是 16 位，但分配方式不同：FP16 把更多位给了尾数（精度），BF16 把更多位给了指数（范围）。深度学习里「数值范围」比「小数点后的精度」更重要——梯度可能非常大或非常小，一旦超出 FP16 的表示范围就变成 inf 或 0，训练直接崩。BF16 的指数位和 FP32 一样宽，几乎不会溢出，所以现在训练大模型基本都用 BF16。一句话记忆：BF16 = 「FP32 的范围 + 更粗的精度」，用范围换稳定。

而 TF32 是个聪明的过渡产物：它在硬件内部用 19 位表示，指数照抄 FP32（范围一致）、尾数只留 10 位（够用）。好处是——你的 PyTorch 代码一行不用改，Tensor core 就能把 FP32 矩阵乘自动加速好几倍，几乎无感知精度损失。A100 起默认开启（可用 torch.backends.cuda.matmul.allow_tf32 控制）。

6. 代际演进：V100 → A100 → H100 → H200 → B200

把 NVIDIA 数据中心 GPU 这几代串起来看，你能清楚地看到「每一代在补什么短板」，这对做选型和理解成本极有帮助。

代号架构年份显存带宽标志性能力
V100Volta201716/32GB HBM2~900 GB/s首次引入 Tensor core，FP16 训练起飞
A100Ampere202040/80GB HBM2e~2 TB/sTF32、MIG 多实例、结构化稀疏
H100Hopper202280GB HBM3~3.35 TB/sFP8、Transformer Engine、更快 NVLink
H200Hopper2024141GB HBM3e~4.8 TB/s同 H100 算力，显存和带宽大幅增加（专为大模型推理）
B200Blackwell2024–25192GB HBM3e~8 TB/s双 die 设计、FP4、算力再翻倍

从这张表能读出两条主线：

  • 精度不断向下探：Volta 引入 FP16 → Ampere 加 TF32 → Hopper 加 FP8 → Blackwell 加 FP4。每降一档精度，同芯片的算力和显存有效容量就翻倍。这是「用精度换规模」的持续下注。
  • 显存和带宽越来越被当成主角：注意 H200 相对 H100，算力几乎没变，但显存从 80GB 涨到 141GB、带宽从 3.35 涨到 4.8 TB/s。NVIDIA 很清楚——大模型推理的瓶颈不是算力，而是「装不下」和「搬得慢」（这正是 Day 38 会深入的 memory-bound 问题）。

对做 Agent 安全 / LLM 服务的你，选型直觉可以简化为：训练大模型看算力和 NVLink 互联（H100/B200）；推理大模型看显存容量和带宽（H200 常常比 H100 更划算，因为能塞下更长的上下文和更大的 KV cache）。Day 49 会专门做成本与选型分析。

7. 显存与带宽：为什么 HBM 才是主角

最后一节戳破一个新手的常见误解：GPU 性能的天花板，很多时候不是算力（TFLOPS），而是显存带宽（TB/s）。

GPU 的显存用的是 HBM（High Bandwidth Memory，高带宽内存）——一种堆叠在 GPU 芯片旁边、通过超宽总线连接的特殊 DRAM。相比 CPU 用的 DDR5（带宽约 50–100 GB/s），H100 的 HBM3 带宽高达 3350 GB/s，是几十倍的差距。这么高的带宽，就是为了「喂饱」那上万个嗷嗷待哺的算术单元。

但即便这么快，它相对算力仍然「不够快」。有一个关键概念叫 算术强度（arithmetic intensity）：一个操作「每从显存搬 1 字节数据，能做多少次浮点运算」。

  • 如果算术强度高（比如大矩阵乘法，搬一次数据能反复复用做很多次乘加）→ 瓶颈在算力，叫 compute-bound（计算受限）。这时 Tensor core 满负荷，是理想状态。
  • 如果算术强度低（比如逐元素加法、或者大模型推理的 decode 阶段——每生成一个 token 都要把整个模型权重从显存读一遍，却只做很少的计算）→ 瓶颈在带宽，叫 memory-bound（内存受限）。这时算术单元大量空转，等着数据从 HBM 慢慢搬过来。

大模型推理的 decode 阶段是典型的 memory-bound——这就是为什么 H200 只加显存带宽、不加算力，就能显著提升推理速度。也是为什么「量化」如此有效：把权重从 FP16 压到 INT8，搬运的数据量直接减半,memory-bound 的场景速度近乎翻倍。这个「算力 vs 带宽」的张力，是理解一切 LLM 推理优化的总纲，Week 06 的 Roofline 模型会把它讲成一套完整的分析框架。今天你只需要牢牢记住一句话：看一块 GPU 强不强，别只看 TFLOPS，一定要同时看它的显存容量和带宽。

🔗 与 AI / Agent 安全的连结

1. 多租户 GPU 的隔离风险。你做 Agent 安全，很可能面对「多个租户 / 多个 Agent 共享同一块 GPU」的场景。A100 引入的 MIG（多实例 GPU）能把一块卡切成硬件隔离的多份，但更常见的 MPS（时间片共享）隔离要弱得多。理解 SM、显存的物理结构，是评估「租户 A 能否通过显存残留读到租户 B 数据」这类风险的前提。周六（Day 48）会专门做 GPU 多租户安全。

2. 显存残留与数据泄露。GPU 显存（HBM）在一个 CUDA context 释放后，并不保证被清零。如果一个恶意 Agent 能在受害者进程结束后立刻申请同一块显存，就可能读到上一个进程遗留的模型权重、用户输入或中间激活。理解「显存是一块物理资源、由驱动分配复用」这件事，才能意识到这个攻击面。

3. 侧信道计时攻击。SIMT 的 warp divergence、缓存命中/未命中会造成可观测的执行时间差异。攻击者可能通过精心构造输入、测量 GPU kernel 的执行时间，反推出模型结构或部分权重信息。理解 GPU 的执行模型，是判断你的推理服务是否存在计时侧信道的基础。

4. 资源耗尽型 DoS。知道「GPU 要靠海量并行 warp 才能跑满、显存是硬上限」后，你就能设计针对性的防护：一个恶意请求如果构造超长上下文，会撑爆 KV cache 显存，导致整机 OOM、拖垮所有租户。带宽和显存是比 CPU 更脆弱的耗尽点，速率限制和显存配额要专门为 GPU 设计。

5. 精度与对抗鲁棒性。FP8/INT8 量化在提升吞吐的同时会引入数值误差。这层误差可能改变模型对对抗样本的响应边界——同一个 jailbreak 输入，在 FP16 和 INT8 部署上的行为可能不同。做 red team 评测时，必须在实际部署精度下测试，而不是只在 FP32 训练精度下测。

今日小练习（3 道）

1动手：如果你手边有 NVIDIA GPU（本地或云服务器），运行 nvidia-smi，找出这几项并抄下来：GPU 型号、显存总量、当前显存占用、GPU 利用率（GPU-Util）。然后运行 nvidia-smi -q | grep -A3 "FB Memory" 看更详细的显存信息。如果没有 GPU，去 NVIDIA 官网找 H100 的 datasheet，抄下它的 FP16 Tensor core 算力、FP32 CUDA core 算力、显存带宽三个数字，感受它们的数量级差距。

2观察：查一下你常用的模型（比如 Llama-3-8B）如果用 FP16 精度加载，需要多少显存？（提示：粗算公式 = 参数量 × 每参数字节数，FP16 是 2 字节/参数）。再算一下换成 INT8（1 字节/参数）后是多少。想一想：为什么「量化」几乎是显存受限场景的第一优化手段？

3思考：本文说「GPU 讨厌分支」。假设你要在 GPU 上实现一个 Agent 的工具路由逻辑——根据用户输入的不同，走十几条完全不同的处理分支。为什么这种「充满数据依赖分支」的逻辑不适合直接放在 GPU kernel 里跑？在一个真实的 LLM 推理服务里，这类「控制流密集」的工作通常交给谁（CPU 还是 GPU）来做？这对你设计推理网关的架构有什么启示？
