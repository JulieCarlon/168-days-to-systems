1. CUDA 是什么：一层薄薄的并行抽象

CUDA（Compute Unified Device Architecture）是 NVIDIA 2007 年推出的、让你用类 C/C++ 语言给 GPU 编程的平台。在 CUDA 之前，想用 GPU 做通用计算，得把你的问题伪装成「画三角形」骗着图形 API（OpenGL）去算——极其反人类。CUDA 的贡献是：把 GPU 从「只会画画的专用硬件」变成「可以被普通程序员编程的并行计算机」。

理解 CUDA 的第一件事，是分清两个角色：

  • Host（主机）：CPU + 它的内存（DRAM）。你的主程序、main() 函数跑在这里。它是「指挥官」。
  • Device（设备）：GPU + 它的显存（HBM/GDDR）。真正的大规模并行计算发生在这里。它是「工兵连」。

一个 CUDA 程序的典型骨架永远是这三步循环，务必背下来：

┌──────────── Host (CPU) ────────────┐ ┌──────── Device (GPU) ────────┐ │ 1. 在 GPU 显存上分配空间 │ │ │ │ cudaMalloc(&d_x, N) ──────────┼───────>│ [ 一块空显存 d_x ] │ │ │ │ │ │ 2. 把输入数据从内存拷到显存 │ │ │ │ cudaMemcpy(d_x, h_x, H2D) ─────┼───────>│ [ d_x 里装好了数据 ] │ │ │ │ │ │ 3. 启动 kernel，几万线程同时算 │ │ add<<>>() │ │ add<<<...>>>(d_x, d_y) ────────┼───────>│ ▓▓▓▓▓▓▓▓▓▓ 并行执行 ▓▓▓▓▓▓ │ │ │ │ │ │ 4. 把结果从显存拷回内存 │ │ │ │ cudaMemcpy(h_y, d_y, D2H) <────┼────────│ [ 结果算好了 ] │ └────────────────────────────────────┘ └──────────────────────────────┘

这里有个关键的心智模型：CPU 和 GPU 有各自独立的内存，它们不能直接读对方的地址。CPU 上的指针 h_x 指向主机内存，GPU 上的指针 d_x 指向显存，两者不能混用。数据必须显式地「搬」过去、「搬」回来。这就是为什么 CUDA 程序里到处是 cudaMemcpy——它是横跨 PCIe 总线（回顾昨天：Gen4/Gen5 的那根线）的搬运工。

类比：把 Host 想成一个坐在办公室里的项目经理（CPU：单核很聪明，擅长复杂决策但人手少），Device 想成一个远在工厂车间的上万人流水线（GPU：每个工人很笨只会做简单重复动作，但人多）。经理不能直接把脑子里的想法塞进工人手里，必须把「原料」（数据）用卡车（PCIe）运到车间仓库（显存），下达统一的「作业指令」（kernel），等工人们一起干完，再用卡车把「成品」拉回办公室。今天所有的语法，本质都是在描述这条运输+作业流水线。

2. 线程层次：thread / warp / block / grid

CUDA 最精妙、也最容易让初学者晕的地方，是它把线程组织成了四级层次。你必须理解这个层次，因为几乎所有 CUDA 代码都在跟这四个层次的索引打交道。从小到大：

grid（整个 kernel 启动的所有线程） └── block（线程块，一群能协作的线程，最多 1024 个） └── warp（32 个线程，硬件真正的调度单位，你写代码时"看不见"但要懂） └── thread（单个线程，执行你 kernel 里那段代码的一份拷贝）

thread（线程）

最小单位。一个 thread 就是你 kernel 函数体的「一份实例」。如果你启动了 100 万个线程，就是这段代码被同时跑了 100 万遍，每一遍处理数据的不同部分。区分它们靠内建变量 threadIdx。

warp（线程束）

硬件层面的真正调度单位，固定 32 个线程（这是 NVIDIA 的硬件常数，从 2007 年到今天没变过）。回顾昨天的 SIMT：一个 warp 里的 32 个线程共用一个指令流，锁步执行同一条指令，只是各自作用在不同数据上。warp 在你的源码里没有显式关键字，但它无处不在地影响性能——比如 warp divergence（一个 warp 里的线程走了不同 if 分支，导致串行化），我们明天讲性能时会深入。今天记住：block 里的线程数最好是 32 的倍数。

block（线程块）

一群能互相协作的线程，上限 1024 个。为什么要有 block 这一层？因为一个 block 的所有线程被保证调度到同一个 SM（流多处理器）上，因此它们可以：(1) 共享一块高速的 shared memory；(2) 用 __syncthreads() 做栅栏同步（大家等到都到齐了再往下走）。不同 block 之间则不能直接同步或共享 shared memory——这是 CUDA 可扩展性的根基：block 之间互相独立，所以 GPU 可以按自己有多少 SM，灵活地并行或串行地跑这些 block。

grid（网格）

一次 kernel 启动产生的所有 block 的集合。你启动 kernel 时，就是在说「给我开一个 grid，里面有 M 个 block，每个 block 有 T 个线程」，总线程数 = M × T。

block 和 grid 都可以是 1D/2D/3D 的（用 dim3 类型表示），方便你映射到 1 维数组、2 维图像、3 维体数据。每个线程通过下面这套内建变量算出「我是谁、我该处理哪个数据」：

内建变量含义类比
threadIdx.x/y/z线程在其 block 内的局部编号你在班里的座位号
blockIdx.x/y/zblock 在 grid 内的编号你是几班
blockDim.x/y/z每个 block 有多少线程每个班多少人
gridDim.x/y/zgrid 有多少 block一共几个班

于是那句 CUDA 里最经典的「全局索引」公式就顺理成章了——把「几班 × 每班人数 + 座位号」拼成全校唯一的学号：

int i = blockIdx.x * blockDim.x + threadIdx.x;   // 我在全局数组里的下标

3. kernel 启动语法：<<<grid, block>>>

kernel 就是「要在 GPU 上跑、且会被成千上万个线程同时执行」的那个函数。它有三个语法标记你必须认识：

  • __global__：函数修饰符，声明「这是一个 kernel，从 Host 调用、在 Device 执行」。返回类型必须是 void。
  • __device__：声明「这个函数在 Device 上执行、也只能被 Device 上的代码调用」（kernel 里调用的辅助函数）。
  • __host__：普通 CPU 函数（默认就是，通常不写）。

启动 kernel 用一个 C++ 里不存在的、CUDA 独有的三尖括号语法 <<<...>>>（执行配置，execution configuration）：

// 声明一个 kernel
__global__ void myKernel(float* data) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    data[i] = data[i] * 2.0f;
}

// 从 Host 启动它：512 个 block，每 block 256 个线程 => 共 131072 个线程
myKernel<<<512, 256>>>(d_data);

三尖括号里最少两个参数：<<<gridDim, blockDim>>>，即「多少个 block」和「每 block 多少线程」。它们可以是整数（1D），也可以是 dim3（多维）：

dim3 threads(16, 16);              // 每 block 16×16 = 256 线程（适合处理 2D 图像）
dim3 blocks(width/16, height/16);  // grid 尺寸按数据大小算
imgKernel<<<blocks, threads>>>(d_img);
三个必须记住的坑：
  1. kernel 启动是异步的。myKernel<<<...>>>() 这行代码几乎立刻返回，CPU 继续往下跑，GPU 在后台算。想等它算完，要显式调用 cudaDeviceSynchronize()。这个异步特性是性能优化的基础，也是 bug 的重灾区。
  2. 线程数几乎总是多于数据。你通常向上取整开线程（blocks = (N + 255) / 256），于是最后一个 block 会有些线程的 i >= N，越界。所以 kernel 里第一行几乎永远是边界检查 if (i < N)。
  3. 启动本身不报错。kernel 内部的错误（越界、非法访问）不会让 <<<>>> 抛异常，得靠 cudaGetLastError() / cudaDeviceSynchronize() 的返回值捕获。

4. GPU 内存层级：register / shared / global

写 CPU 程序时你几乎不用管内存在哪一层（缓存对程序员透明）。但在 GPU 上，内存层级是显式的、由你手动管理的，而且用对内存层级是 CUDA 性能的头号杠杆。从快到慢、从私有到共享：

层级作用域速度典型大小谁能访问
寄存器 register单线程私有最快（~1 周期）每线程几十~255 个只有该线程自己
共享内存 sharedblock 内共享很快（~20 周期）每 SM 最多 ~228 KB（H100）同一 block 的所有线程
全局内存 global整个 grid 共享慢（~400 周期）几十 GB（就是显存 HBM）所有线程 + Host
常量/纹理内存只读、带缓存缓存命中很快64 KB 常量所有线程只读
本地内存 local单线程私有慢（其实在 global 里）寄存器溢出时用只有该线程自己

关键的三层，用一个「工厂」类比串起来：

  • register = 每个工人手里正在操作的零件。私有、极快，但数量有限。用 CUDA C 声明的普通局部变量（int i; float tmp;）默认就在寄存器里。
  • shared memory = 一个班组共用的工作台。同一 block 的线程可以往上面放数据、互相拿。用 __shared__ 关键字声明。它是你手动把 global 里的热数据「缓存」到片上、给 block 内复用的利器，能把慢 400 周期的访问变成快 20 周期。
  • global memory = 车间外的大仓库（显存）。所有人都能存取，但每次跑一趟很慢。cudaMalloc 分配的、kernel 参数里传的指针，指的都是这里。LLM 推理里的权重、KV cache，全都住在 global memory——所以昨天说「推理是 memory-bound」，指的就是 global memory 的带宽跟不上算力。
为什么这决定性能？ 一次 global memory 访问 ~400 周期，一次 shared memory 访问 ~20 周期，差 20 倍。矩阵乘法之类的算法，如果每个数据从 global 反复读，带宽会成为瓶颈；把一小块数据先搬进 shared memory、让 block 内的线程反复复用，就能把访存次数砍掉一个数量级。这正是 FlashAttention（Week 08 会讲）的核心思想——把注意力计算切成能塞进 shared memory 的小块（tiling），避免把巨大的中间注意力矩阵写回 global memory。

5. cudaMalloc / cudaMemcpy：数据的两地穿梭

因为 Host 和 Device 内存分离，CUDA 提供了一套镜像标准 C 的内存 API。核心四个：

// 1. 在 GPU 显存上分配 N 个 float（对应 CPU 的 malloc）
float* d_x;
cudaMalloc(&d_x, N * sizeof(float));     // 注意：传的是 &d_x，因为它要写指针本身

// 2. Host -> Device：把 CPU 内存 h_x 的内容拷进显存 d_x
cudaMemcpy(d_x, h_x, N * sizeof(float), cudaMemcpyHostToDevice);

// 3. Device -> Host：把结果从显存拷回 CPU 内存
cudaMemcpy(h_y, d_y, N * sizeof(float), cudaMemcpyDeviceToHost);

// 4. 释放显存（对应 CPU 的 free）
cudaFree(d_x);

cudaMemcpy 的第四个参数指明方向：cudaMemcpyHostToDevice（H2D）、cudaMemcpyDeviceToHost（D2H）、还有 DeviceToDevice（显存内部）。

几个初学者必踩的点：

  • 命名约定：习惯上给主机指针加前缀 h_、设备指针加 d_，防止把两个世界的指针搞混。编译器不会帮你查——把 d_x 当 CPU 数组去 d_x[0] 解引用会直接段错误。
  • cudaMemcpy 是同步阻塞的：它会等 GPU 之前排队的活干完、拷贝完成才返回。它天然是 CPU 和 GPU 之间的一道同步点。
  • PCIe 拷贝是有代价的（几 GB/s ~ 几十 GB/s，远慢于显存内部的几 TB/s）。所以优化的一大原则是尽量减少 H2D/D2H 次数，让数据尽量长时间待在 GPU 上——这也解释了为什么大模型训练要把整个 batch、整个权重都常驻显存。

现代 CUDA 还提供 Unified Memory（cudaMallocManaged），让一个指针在 Host 和 Device 两边都能用，底层自动按需搬页——写起来方便，但性能不一定最优，学习期建议先用显式的 cudaMalloc + cudaMemcpy 把机制搞清楚。

6. 写一个完整的向量加 kernel

把前面所有零件拼起来，就是 CUDA 世界的「hello world」——两个长度 N 的向量逐元素相加 C = A + B。请逐行读懂它，它是所有 CUDA 程序的基因：

#include <cuda_runtime.h>
#include <stdio.h>

// ===== kernel：描述"一个线程"干什么 =====
__global__ void vecAdd(const float* A, const float* B, float* C, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;  // 我负责第 i 个元素
    if (i < N) {                                     // 边界检查，防越界
        C[i] = A[i] + B[i];
    }
}

int main() {
    int N = 1 << 20;                 // 约 100 万个元素
    size_t bytes = N * sizeof(float);

    // 1) 主机内存分配并初始化
    float *h_A = (float*)malloc(bytes);
    float *h_B = (float*)malloc(bytes);
    float *h_C = (float*)malloc(bytes);
    for (int i = 0; i < N; i++) { h_A[i] = 1.0f; h_B[i] = 2.0f; }

    // 2) 设备显存分配
    float *d_A, *d_B, *d_C;
    cudaMalloc(&d_A, bytes);
    cudaMalloc(&d_B, bytes);
    cudaMalloc(&d_C, bytes);

    // 3) 拷数据 Host -> Device
    cudaMemcpy(d_A, h_A, bytes, cudaMemcpyHostToDevice);
    cudaMemcpy(d_B, h_B, bytes, cudaMemcpyHostToDevice);

    // 4) 配置并启动 kernel（向上取整开够线程）
    int threads = 256;
    int blocks  = (N + threads - 1) / threads;
    vecAdd<<<blocks, threads>>>(d_A, d_B, d_C, N);
    cudaDeviceSynchronize();        // 等 GPU 算完

    // 5) 拷结果 Device -> Host
    cudaMemcpy(h_C, d_C, bytes, cudaMemcpyDeviceToHost);
    printf("C[0] = %f (应为 3.0)\n", h_C[0]);

    // 6) 清理
    cudaFree(d_A); cudaFree(d_B); cudaFree(d_C);
    free(h_A); free(h_B); free(h_C);
    return 0;
}

编译运行（需要装了 CUDA Toolkit 和 NVIDIA 显卡的机器）：

nvcc vecadd.cu -o vecadd    # nvcc 是 NVIDIA 的 CUDA 编译器
./vecadd                    # 输出 C[0] = 3.000000

回味一下这段代码的哲学：你从头到尾只写了「一个线程怎么算一个元素」，从没写过 for 循环去遍历 100 万个元素。那个「循环」被 <<<blocks, threads>>> 隐式地、并行地展开成了硬件上的几十万个线程。这就是数据并行（data parallelism）的思维方式——从「我怎么遍历所有数据」切换到「单个数据点怎么处理，剩下的交给硬件复制」。你做 AI 时用的 PyTorch，每一个 torch.add、每一次矩阵乘，底层展开后都是这样一个（或一串融合的）kernel。

Python 视角：你不必写裸 CUDA C 才能碰到这些概念。Numba 的 @cuda.jit、CuPy 的自定义 kernel、乃至 Triton（OpenAI 出的、写 GPU kernel 的 Python DSL，vLLM/FlashAttention 大量用它），暴露的都是同一套 thread/block/grid + 显式内存层级的模型。今天理解了 CUDA C 的骨架，读 Triton kernel 时那些 tl.program_id(0)、BLOCK_SIZE 就都能对上号。

7. cooperative groups 与 stream：进阶两件事

cooperative groups（协作组）

传统 CUDA 里，线程同步的粒度很死板：__syncthreads() 只能同步「整个 block」，而 block 之间根本无法同步。Cooperative Groups（CUDA 9 引入）是一套更灵活的 API，让你把「一组协作的线程」显式地表达成一个对象，粒度可以是：warp 内的一部分线程（tile）、整个 block、甚至整个 grid（grid-wide sync，需要特殊启动方式）。

#include <cooperative_groups.h>
namespace cg = cooperative_groups;

__global__ void reduce(float* data) {
    cg::thread_block block = cg::this_thread_block();
    // ... 每个线程算局部值 ...
    block.sync();                       // 等价 __syncthreads()，但更显式、可组合
    cg::thread_block_tile<32> warp = cg::tiled_partition<32>(block);
    float v = cg::reduce(warp, my_val, cg::plus<float>());  // warp 内高效归约
}

好处：让 warp 级别的优化（如 warp shuffle 归约，做 reduction/softmax 时极常用）写起来更安全清晰。你以后读 vLLM、FlashAttention 的 CUDA 源码，会频繁看到 cooperative groups 和 warp-level primitives。

stream（流）

CUDA Stream 是一条「GPU 操作的有序队列」。默认所有操作都进「默认流（stream 0）」，严格按提交顺序串行执行。但真实场景里，你希望拷贝数据和计算能重叠起来——比如一边把下一批数据 H2D 拷进去，一边 GPU 还在算上一批。多个 stream 就是干这个的：不同 stream 里的操作可以并发/重叠执行。

cudaStream_t s1, s2;
cudaStreamCreate(&s1);
cudaStreamCreate(&s2);

// 异步拷贝 + kernel 都挂到指定 stream 上
cudaMemcpyAsync(d_A, h_A, bytes, cudaMemcpyHostToDevice, s1);
vecAdd<<<blocks, threads, 0, s2>>>(d_A, d_B, d_C, N);  // 第4个参数是 stream

cudaStreamSynchronize(s1);   // 只等 s1 里的活干完

Stream 是「计算与传输重叠」「多 kernel 并发」这类吞吐优化的基础设施。推理引擎里，不同请求的 kernel、prefill 和 decode 的调度，背后都在用 stream 编排 GPU 上的并发。今天了解它「是一条命令队列、用来做重叠」即可，Week 08 讲推理调度时会再遇到。

与 AI / Agent 安全的连结

1）自定义 kernel 是攻击面，也是审计难点。 vLLM、FlashAttention、各种量化库都带自己手写的 CUDA/Triton kernel。一个 kernel 里的边界检查写错（少了那句 if (i < N)），就是一个 GPU 上的越界读写——可能读到相邻请求残留在显存里的数据（跨请求信息泄露），或直接让服务崩溃。审计一个推理框架的安全性，读它的自定义 kernel 是绕不开的一环，而这需要你今天学的这套 thread/index/memory 模型才能读懂。

2）显存不像内存那样被自动清零。 cudaMalloc 拿到的显存不保证归零，里面可能是上一个进程/上一个请求留下的数据。在多租户 GPU 或长期运行的推理服务里，如果新分配的 KV cache 缓冲区没被显式清空就参与计算，理论上存在跨租户显存残留泄露的风险。理解 global memory 的生命周期，是评估这类风险的前提（周六 Day 48「GPU 多租户安全」会专门展开）。

3）kernel 的异步性制造了竞态与检测盲区。 kernel 启动异步、stream 之间并发——如果同步点（cudaDeviceSynchronize、stream 依赖）设置错误，就会出现数据竞态：读到还没算完的中间结果。对 Agent 系统而言，这种非确定性缺陷极难复现、极难在测试里抓到，却可能在生产中导致输出错误。写/审推理服务时，把「哪些操作在哪个 stream、哪里有同步」画清楚，是可靠性和安全性的共同前提。

4）资源耗尽型 DoS。 攻击者若能影响 kernel 的启动配置或输入规模（比如一个超长的 prompt 撑爆 KV cache 显存），可以触发 cudaMalloc 失败、OOM、甚至拖垮整卡。理解 grid/block 规模与显存占用如何随输入增长，才能在网关层设计正确的输入上限和配额（回顾 Week 04 的限流）。

5）侧信道的物理基础。 周六将讲的 GPU 侧信道攻击，很多都建立在「共享的内存层级 + 可测量的时序」之上——比如通过观测 shared memory bank conflict 或 global memory 访问延迟推断另一个租户的数据模式。你今天建立的「哪层内存被谁共享、访问代价多大」的地图，正是理解这些侧信道为什么可能存在的物理基础。

1动手：如果你手边有带 NVIDIA 显卡的机器（或云上租一台），把第 6 节的 vecadd.cu 完整敲下来，用 nvcc vecadd.cu -o vecadd 编译运行，确认输出 C[0] = 3.0。没有显卡也没关系——用 Python 的 Numba 写等价版本：@cuda.jit 装饰一个 kernel，用 cuda.grid(1) 拿全局索引，在 Google Colab（免费送 GPU）上跑通。对照体会：cuda.grid(1) 其实就是 blockIdx.x*blockDim.x+threadIdx.x 的封装。

2观察：在向量加 kernel 里，故意把边界检查 if (i < N) 删掉，同时把 N 改成一个不是 256 整数倍的数（比如 N = 1000000 + 7）。编译运行，用 cuda-memcheck ./vecadd（或新版 compute-sanitizer）观察它报出的越界访问错误。体会「线程数多于数据 → 必须边界检查」这条铁律，以及为什么少写一行 if 就是一个真实漏洞。

3思考：假设一个推理服务给每个用户请求都做「cudaMalloc 一块 KV cache 缓冲 → 计算 → cudaFree」。从今天学的 global memory 生命周期出发，论证：为什么「新分配的显存不保证清零」会成为跨用户信息泄露的隐患？作为设计者，你会在这条链路的哪一步、用什么代价最小的方式堵住它？（提示：对比「每次 cudaMemset 清零」和「缓冲池复用 + 使用前初始化」两种方案的性能与安全权衡。）
