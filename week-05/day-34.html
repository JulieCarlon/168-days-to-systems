1 · 什么是侧信道：从功耗到时间的泄密

侧信道攻击（side-channel attack）指的是：攻击者不去破解算法本身、也不利用代码逻辑漏洞，而是通过系统运行时无意泄露的物理/微架构信息来推断秘密。这里的「侧」是相对「正门」而言的——正门是接口、协议、密码学，而侧门是时间、功耗、电磁辐射、声音、缓存状态、温度这些「本不该携带信息、却确实携带了信息」的物理副产品。

类比：想象一个装了防盗门的保险箱，密码你不知道（这是「正门」——需要暴力破解或知道密码）。但你注意到，主人转对一位数字时锁芯会发出一声极轻微的「咔哒」。你不需要知道密码，只要听声音，就能一位位试出来。声音就是「侧信道」——它不是设计用来传递密码的，却泄露了密码。经典密码学里，通过测量 RSA 解密的耗时就能推出私钥的位（Kocher, 1996），道理完全一样。

为什么侧信道在现代 CPU 上如此致命？因为 CPU 为了快，共享了大量资源：L1/L2/L3 缓存、分支预测器、TLB、执行端口、内存控制器——这些资源在不同进程、不同安全域之间是共享的。共享意味着「你的行为会改变我看到的状态」。哪怕操作系统把地址空间隔离得再干净（进程 A 读不到进程 B 的一个字节），只要 A 能观测 B 用了哪一块 cache，信息就漏了。这就是过去十年微架构攻击的总纲。

关键区分：隐蔽信道 vs 侧信道。 侧信道是「受害者无意泄露，攻击者被动/主动观测」；隐蔽信道（covert channel）是「两个本不该通信的进程，故意用共享资源偷偷传数据」（比如沙箱里的恶意代码把数据编码成 cache 状态传给外面的同谋）。技术手法（如 Flush+Reload）两者共用——今天 LAB 我们先做更容易复现的隐蔽信道，它是理解侧信道的最短路径。

侧信道分类速览：

  • 时间侧信道（timing）：测操作耗时。缓存计时、分支计时、除法指令计时都属此类——今天的主角。
  • 功耗/电磁（power/EM）：物理探针测芯片功耗曲线，常用于攻击智能卡、硬件密钥。需要物理接触。
  • 微架构状态（μarch state）：cache、TLB、分支预测器、行填充缓冲（Line Fill Buffer）等的占用状态。Meltdown/Spectre/MDS 全在此。
  • 故障注入（fault）：Rowhammer、电压毛刺（voltage glitching）——主动让硬件出错来绕过检查。

2 · 缓存计时家族：Flush+Reload / Prime+Probe / Evict+Time

所有微架构攻击的「读出」环节，几乎都靠缓存计时来把微架构状态转成攻击者能读的数字。回忆 Day 31：访问一个数据，如果它在 L1（命中），大约几个周期（~1ns）；如果要去主存拿（miss），要上百个周期（~100ns）。这个 ~100 倍的差距，用 rdtsc 指令（读 CPU 时间戳计数器）就能清晰测出来。于是「某地址此刻在不在 cache 里」这一个比特的信息，就能被可靠读取。

2.1 Flush+Reload（最精确，需共享内存）

前提：攻击者和受害者共享同一物理内存页（很常见——共享库如 libcrypto、去重后的相同内存页、mmap 的同一文件）。步骤：

  1. Flush：用 clflush 指令把目标地址从所有层级缓存中赶出去（因为是共享物理页，赶出去对受害者也生效）。
  2. Wait：让受害者运行一小段。如果受害者访问了这个地址，它会被重新加载进 cache。
  3. Reload：攻击者自己访问该地址并计时。快→受害者刚才访问过（命中）；慢→受害者没访问（miss）。

这样攻击者就知道了「受害者刚才有没有碰这块内存」。若受害者的代码是 if (secret_bit) access(table[1]) else access(table[0])，攻击者监视 table[0] 和 table[1] 哪个被加载，就读出了 secret_bit。

2.2 Prime+Probe（不需共享内存，更通用）

当没有共享内存时（跨 VM、跨容器常见），用 Prime+Probe。它攻击的是 cache 的组相联结构（Day 31 的 set-associative）：

  1. Prime：攻击者用自己的数据填满某个 cache set（把整个 way 占满）。
  2. Wait：受害者运行。如果它访问的地址映射到同一个 set，就会把攻击者的某条数据挤出去。
  3. Probe：攻击者重新访问自己 Prime 时放的数据并计时。如果变慢了（有 miss），说明「受害者动过这个 set」。

Prime+Probe 分辨率低于 Flush+Reload（只知道「哪个 set 被动了」而非精确地址），但不依赖共享内存，因此是跨租户、跨 VM 攻击的主力——这正是云安全最关心的场景。

Flush+Reload Prime+Probe ┌──────────────┐ ┌──────────────┐ │ 需共享物理页 │ │ 无需共享内存 │ │ clflush 赶出 │ ←精度高(地址级) │ 填满 cache set│ ←精度低(set级) │ 时间差 ~100x │ │ 看谁被挤出 │ ←跨 VM 可用 └──────────────┘ └──────────────┘ ↑ Meltdown/Spectre 的"读出"多用它 ↑ 云上跨租户攻击多用它

还有 Evict+Time（先测受害者正常耗时，再驱逐某地址后重测，看变慢多少来判断它是否用了该地址）和 Flush+Flush（利用 clflush 自身耗时随缓存状态变化，几乎不产生 cache miss，更隐蔽）。它们是同一思想的变体。

🛡 防御方视角：缓存计时攻击的共性弱点是需要高精度计时和大量重复探测。检测/缓解手段：① 降低计时精度（浏览器把 performance.now() 精度砍到 100μs、加抖动，正是为了防 JS 侧信道）；② 监控异常高频的 clflush / cache miss（可用性能计数器）；③ 关键路径用常数时间（constant-time）实现——不让分支和内存访问依赖秘密（现代密码库如 BoringSSL 的核心都是 constant-time 的）。

3 · Meltdown：乱序执行让越权读「先斩后奏」

2018 年初公开的 Meltdown（CVE-2017-5754）让全世界的运维连夜打补丁。它的杀伤力在于：一个普通用户态程序，能读取整个内核地址空间（乃至整台机器的物理内存）。它把 Day 30 学的乱序执行变成了武器。

3.1 问题的根子：乱序执行 + 延迟的权限检查

回忆 Day 30：现代 CPU 为了不空等，会乱序（out-of-order）提前执行后面的指令，结果先算好放在缓冲区，等轮到它「退休（retire）」时才真正写回、对外可见。关键在于——当一条 load 指令访问了你无权访问的内核地址时，CPU 会产生异常，但异常是在指令退休那一刻才抛出的。在退休之前的「推测窗口」里，CPU 已经用那个非法读到的值去执行了后面几条指令！这些后续指令的结果最终会被丢弃（架构状态回滚，仿佛没发生），但它们对 cache 的影响留下来了——这就是泄密的缝隙。

Meltdown 核心 5 行（概念）： char *kernel_ptr = 0xffff...; // 越权地址(无权读) char secret = *kernel_ptr; // ①推测执行:值已被读出(异常尚未抛) char dummy = probe_array[secret*4096];// ②用secret做下标去访问一块探测数组 // ...此时异常抛出,①②的架构结果被回滚(secret/dummy清零) // 但 probe_array[secret*4096] 那一页已经被载入 cache 了! for(i=0;i<256;i++) time_access(probe_array[i*4096]); // ③Flush+Reload扫256页 // 哪一页命中(最快),它的下标 i 就是 secret 的值

第 ② 行是精髓：用秘密值作为数组下标去访问一块攻击者自己的 probe_array（每个候选值间隔 4096 字节 = 一页，避免预取干扰）。虽然秘密值最终被回滚清零，但「secret 对应的那一页被载入了 cache」这件事不会回滚。第 ③ 行用 Flush+Reload 扫 256 个候选页，哪个最快命中，下标就是 secret。一次能读一个字节，循环起来就能把内核内存整片抠出来，速度可达每秒几 KB。

Meltdown 之所以能读内核，是因为当年为了性能，Linux 把整个内核地址空间也映射在每个进程的页表里（只是标记为「仅内核态可访问」）。乱序执行绕过了这个「仅内核态」的检查窗口。修法就是把内核页表从用户态页表里拆出去——这就是下面要讲的 KPTI。Meltdown 主要影响 Intel 和部分 ARM，AMD 基本免疫（其权限检查发生得更早）。

4 · Spectre：训练分支预测器去「自愿」泄密

Spectre（CVE-2017-5753 / 5715）比 Meltdown 更根本、更难修，因为它不依赖某个厂商的实现瑕疵，而是利用了所有高性能 CPU 都有的推测执行本身。Meltdown 是「越权读自己不该读的」，Spectre 是「骗受害者自己把秘密泄出来」。

4.1 Variant 1：绕过边界检查（Bounds Check Bypass）

考虑一段看似安全的代码（比如内核里的系统调用处理，或 JS 引擎里的数组访问）：

if (x < array1_size) {          // 边界检查
    y = array2[array1[x] * 4096];// 只有 x 合法才会执行
}

攻击者反复用合法的 x 调用它，把 Day 30 讲的分支预测器（BTB）训练成「这个 if 总是成立」。然后突然传入一个越界的 x。CPU 相信历史，推测性地先执行了 if 内部——用越界的 array1[x]（可能是任意内存里的秘密）作下标访问 array2，把对应页载入 cache。虽然边界检查最终发现 x 越界、回滚了架构结果，但 cache 痕迹又一次留了下来。攻击者再用 Flush+Reload 读出秘密。整个过程受害者的代码是"合法"的，漏洞在硬件的推测行为里。

4.2 Variant 2：分支目标注入（Branch Target Injection）

更狠：攻击者在自己的进程里训练 BTB，让某个间接跳转（jmp [rax]）的预测目标指向受害者进程里的一段"小工具（gadget)"代码。当受害者执行到那个间接跳转时，CPU 推测性地跳到攻击者选定的 gadget 去执行，泄露数据。这就是为什么修复它需要 retpoline（下节）——把间接跳转替换成不可被 BTB 预测的形式。

为什么 Spectre 是"永久的"？因为推测执行是现代 CPU 性能的命根子——去掉它性能倒退二十年。所以 Spectre 类漏洞无法靠"关掉某个特性"根治，只能一处一处地在软件里插"投机屏障"（如 lfence）、用 retpoline、以及在编译器/内核里做大量针对性加固。直到今天（2026），新的 Spectre 变种（如 BHI、Retbleed、Inception/BTC）仍在不断被发现——这是一场持久战。

5 · Rowhammer：一个纯物理层的比特翻转攻击

前面都是"读"——不改数据只偷看。Rowhammer则是"写"：它能在你没有写权限的内存位置翻转比特（0↔1），纯靠 DRAM 的物理缺陷。

原理：DRAM 把每个比特存在一个微小电容里，电容会漏电，需要定期刷新。现代 DRAM 密度极高，相邻内存行（row）挨得太近。当你疯狂地、反复地读写某一行（"锤击" hammer），会产生电磁干扰，让相邻行的电容加速漏电——如果在刷新周期到来前电荷跌破阈值，那一位就翻转了。攻击者不能选行读，但能选行"锤"。

// Rowhammer 的核心循环(概念):双面锤击
loop:
    mov (X), %eax     // 读锤击行 X (受害行的上邻)
    mov (Y), %ebx     // 读锤击行 Y (受害行的下邻)
    clflush (X)       // 必须刷出 cache,否则第二次读命中 cache 就不碰 DRAM
    clflush (Y)
    jmp loop          // 每秒数十万次,持续几十毫秒~几秒

为什么可怕：如果被翻转的比特恰好在页表项（PTE）里，攻击者可能把一个指向自己内存的指针"翻"成指向内核内存的指针，从而获得对物理内存的读写——普通用户直接提权到 root。Google Project Zero 2015 年首次演示了这个从"内存偶发错误"到"完整提权"的链条。后续变种 ECCploit（打穿 ECC 内存）、RAMBleed（用 Rowhammer 反过来读数据）、Half-Double（跨越更远的行）说明这个物理问题极其顽固。

🛡 防御方视角：① ECC 内存能纠正单比特错误、检测双比特错误，抬高门槛但非万能；② TRR（Target Row Refresh）：内存控制器检测到某行被高频访问就主动刷新邻行——DDR4/DDR5 标配，但 TRRespass 等研究已证明可被绕过；③ 提高刷新频率（性能/功耗代价）；④ 云上给不同租户的内存做物理隔离/保护带（guard rows）。作为工程师，选服务器/云实例时优先带 ECC 且明确说明 Rowhammer 缓解的机型。

6 · 缓解措施：KPTI / retpoline 和它们的代价

你作为要对性能负责的工程师，最该记住的不是攻击细节，而是缓解要花多少钱（性能）——因为这直接影响你的推理服务吞吐。

6.1 KPTI（Kernel Page Table Isolation）——治 Meltdown

思路：既然 Meltdown 靠"内核页表映射在用户态页表里"，那就彻底拆开。用户态运行时页表里只留极少必要的内核入口，其余内核地址根本不映射——非法地址在推测阶段就没有有效翻译，读不出来。代价：每次系统调用/中断都要切换页表 → 刷 TLB（Day 08 讲过 TLB miss 很贵）。

  • 对 syscall 密集型负载（数据库、网络服务、文件 IO 密集）：开销可达 5%–30%。
  • 对 计算密集型负载（纯 GPU 推理、大矩阵运算，很少进内核）：开销通常 <1%。
  • PCID（进程上下文标识）能减少 TLB 全刷，缓解一部分代价——所以较新 CPU 影响更小。

6.2 retpoline——治 Spectre v2

retpoline = "return" + "trampoline"。把容易被 BTB 注入的间接跳转/调用替换成一段用 ret 指令构造的"蹦床"，让 CPU 的推测被引导到一个无害的死循环（pause; lfence; jmp）里空转，从而无法投机跳到攻击者的 gadget。代价：间接调用变慢，虚函数多/间接跳转多的代码受影响。后来 Intel 用硬件特性 eIBRS/IBPB 部分替代 retpoline。

7 · 云上 GPU 多租户侧信道：你的本职战场

前面讲的都是 CPU。但你做 Agent 安全，真正贴身的是 GPU 上的侧信道——因为 LLM 推理服务经常在共享 GPU 上跑多个租户/多个模型。这块比 CPU 侧信道年轻，但风险真实。

7.1 GPU 为什么也漏

回忆 Week 07 会讲的 GPU 架构：多个 kernel 可能并发跑在同一块 GPU 上（MPS 多进程服务、时间片共享、甚至 MIG 分区之间）。它们共享 L2 cache、显存带宽、SM 调度器。已有研究表明：

  • 显存残留（memory remanence）：租户 A 用完的显存没被清零就分给租户 B，B 直接 cudaMalloc 后读，可能读到 A 的模型权重、KV cache、甚至输入 prompt。这是最实际、最常见的风险。
  • GPU cache 计时侧信道：通过测 L2 命中/带宽争用，可推断同卡另一租户的访存模式——进而指纹识别对方在跑哪个模型、甚至部分推断输入特征。
  • 功耗/频率侧信道：GPU 会根据负载动态调频（DVFS），观察自己 kernel 的执行时间波动，能推断同卡邻居的负载节奏。

7.2 隔离手段与它们的强度

隔离强度: 弱 ────────────────────────────────▶ 强 时间片共享 < MPS < MIG < 整卡独占 < 物理机独占 (context切换 (并发,弱隔离) (硬件分区, (无邻居) (无共享总线) 可能残留) 显存/L2隔离)
  • MIG（Multi-Instance GPU）（A100/H100）：把一块卡硬件切成多个实例，各有独立的显存、L2 切片、SM——是目前 GPU 上最强的租户隔离。但仍非绝对，且切分粒度有限。
  • MPS：为吞吐而生的并发共享，隔离很弱，只适合"同一信任域内"多进程，不要用于跨租户。
  • 无论哪种，释放显存前必须清零（cudaMemset）——这是防显存残留最基本、你自己能立刻落地的一条。
🛡 作为 Agent 安全工程师你能做的：① 跨租户/跨客户的推理默认整卡独占或 MIG 隔离，绝不用 MPS 混租户；② 显存回收时强制清零，模型卸载后校验；③ 在多租户网关层做时序归一化（统一 padding 到固定长度、固定 batch 窗口），削弱通过响应时间推断 token 数/内容的侧信道；④ 把"GPU 共享策略"写进威胁模型，明确哪些数据(权重/prompt/KV)在哪种共享下有暴露面。这正是 Day 48 会深入的主题。

8 · 🔧 实战：手写一个 Flush+Reload 隐蔽信道

我们做一个同机、同进程内的隐蔽信道演示，安全无害：用缓存状态在"发送方"和"接收方"逻辑之间传一个字节。它把今天所有概念（clflush、rdtsc 计时、cache 命中/未命中判定）连成一条能跑的链路。

只在你自己的机器上编译运行。这段代码不攻击任何其他进程，只演示"cache 状态可以编码信息"。Apple Silicon（M 系列）无 clflush/rdtsc 且缓存行为不同，建议在 x86_64 Linux（本机或 VM）上跑。

8.1 覆盖信道核心代码 fr.c

#include <stdio.h>
#include <stdint.h>
#include <string.h>
#include <x86intrin.h>   // _mm_clflush, __rdtsc

#define PAGE 4096
uint8_t probe[256 * PAGE];   // 256 个候选,每个隔一页避免预取

// 测量访问某地址的耗时(周期数)
static inline uint64_t timed_load(void *addr){
    unsigned junk;
    uint64_t t0 = __rdtscp(&junk);
    (void)*(volatile uint8_t *)addr;   // 触发一次 load
    uint64_t t1 = __rdtscp(&junk);
    return t1 - t0;
}

int main(){
    // 先把整个 probe 数组从 cache 刷掉(Flush)
    for (int i = 0; i < 256; i++) _mm_clflush(&probe[i*PAGE]);

    // === 发送方:想传的秘密字节 ===
    uint8_t secret = 'K';               // 试试改成别的字符
    // "发送":用秘密值做下标访问 probe → 把那一页载入 cache
    volatile uint8_t sink = probe[secret * PAGE];
    (void)sink;

    // === 接收方:扫 256 个候选页,找命中的那个(Reload) ===
    int best = -1; uint64_t best_t = ~0ULL;
    for (int i = 0; i < 256; i++){
        uint64_t t = timed_load(&probe[i*PAGE]);
        if (t < best_t){ best_t = t; best = i; }
    }
    printf("recovered byte = %d ('%c'), reload cycles = %llu\n",
           best, (best>=32&&best<127)?best:'?', (unsigned long long)best_t);
    return 0;
}
# 编译运行(x86_64 Linux)
gcc -O0 -o fr fr.c
./fr
# 期望: recovered byte = 75 ('K'), reload cycles = 40~80  (远低于 miss 的 ~250+)
# 多跑几次 / 试着把 secret 改成 'A' 'z' '7',看是否都能恢复

看懂了这段，你就理解了 Meltdown/Spectre 的"读出"环节——它们唯一的区别是：那个 probe[secret*PAGE] 里的 secret，不是你自己定义的字符，而是推测执行期间越权读到、随后被回滚的一个字节。回滚清掉了架构状态，却清不掉这行代码给 cache 留下的痕迹。

与 AI / Agent 安全的连结

1. 共享 GPU 推理的模型/数据泄露。这是最直接的连结。当你把多个客户的推理放在同一块 GPU（时间片或 MPS）上，显存残留可能让后一个租户读到前一个的模型权重、系统 prompt、甚至用户输入。Flush+Reload 的思想同样适用于 GPU L2：邻居能通过计时推断你在跑哪个模型。防御：跨租户默认整卡/MIG 隔离、显存清零、把 GPU 共享策略写进威胁模型。

2. 响应时序侧信道泄露 prompt/输出信息。LLM 服务的响应耗时本身就是侧信道：TTFT（首 token 时间）随 prompt 长度变化、总时长随输出 token 数变化、命中 KV cache（prefix caching）时明显更快。攻击者反复探测可推断:你的系统 prompt 有多长、某个前缀是否被别的用户请求过(跨用户 cache 命中 → 泄露"别人问过类似问题")。防御:对时序做归一化、prefix cache 按用户/租户分区、对敏感响应加固定延迟。

3. Spectre 思想 = prompt injection 的硬件版隐喻。Spectre 的本质是"让系统在推测/信任状态下执行了本不该执行的路径，事后回滚却留下副作用"。这和 indirect prompt injection 惊人地同构:Agent 在"信任检索内容"的前提下执行了注入的指令,即使事后过滤,副作用(已调用的工具、已发出的请求)可能无法回滚。理解 Spectre 会加深你对"信任边界 + 投机执行 + 不可回滚副作用"这一攻击范式的直觉——这正是 Day 132/160 的核心。

4. 沙箱里的隐蔽信道:code interpreter 的隐患。你给 Agent 配了代码执行沙箱(Day 157 会讲),即使网络全断、文件系统隔离,沙箱内的恶意代码仍可能用缓存/时序隐蔽信道把数据编码后传给同机的同谋进程,绕过你所有的"数据出口管控"。这说明:逻辑隔离不等于物理隔离。高敏感场景的沙箱需要考虑到微架构侧信道,可能需要独占物理核、关超线程。

5. 缓解措施 = 你的容量规划变量。KPTI/retpoline/关 HT 这些缓解会实打实吃掉吞吐(syscall 密集可达两位数百分比)。当你为 Agent 服务做容量估算(Day 151/162 的系统设计)时,必须把"我们为了多租户安全开了哪些缓解、因此损失了多少吞吐"算进成本模型。安全和性能在这里是可量化的权衡,而不是口号。
