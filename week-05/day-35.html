1. 本周复盘：CPU 的七块拼图缝成一张图

先把 Day 29–34 的主干快速过一遍。别把这当成流水账——每一条都请你在心里对应一个「它解决了什么问题」。

Day 29 · CPU 工作原理

冯诺依曼结构把「指令」和「数据」放在同一片内存里，用同一条总线读——这带来了统一编程模型，也埋下了「内存墙」的隐患（指令和数据抢带宽）。哈佛结构把两者分开，现代 CPU 在 L1 层面其实是「改良哈佛」：L1i（指令缓存）与 L1d（数据缓存）分开，往下到 L2/L3 又合并。核心的性能公式请刻进脑子：

执行时间 = 指令数(IC) × 每条指令周期数(CPI) × 时钟周期(1/频率) 三个因子分别被谁影响： IC ← 编译器 / 算法 / 指令集（CISC 一条顶多条 vs RISC） CPI ← 微架构：流水线、缓存命中、分支预测（本周主角） 频率 ← 制程 / 功耗墙（已多年停在 ~5GHz 附近）

关键洞见：频率早就撞墙了，这十几年性能提升几乎全靠降低 CPI（微架构魔法）和增加并行度（多核 + SIMD）。这也是为什么本周花了大力气讲流水线和缓存——它们就是 CPI 的战场。

Day 30 · 流水线、分支预测、乱序

流水线（pipeline）把一条指令拆成取指/译码/执行/访存/写回几级，让多条指令像工厂流水线一样重叠执行。代价是三种冒险（hazard）：结构冒险（资源冲突）、数据冒险（后一条要用前一条的结果，用 forwarding 转发缓解）、控制冒险（遇到分支不知道下一条在哪）。

为了不让分支把流水线清空，CPU 用分支预测（BTB + 历史表）猜下一条走哪；猜错要清空并回滚，代价十几个周期。超标量 + 乱序执行（OoO）让 CPU 在等一条慢指令（比如 cache miss）时先跑后面不依赖的指令。推测执行（speculative execution）甚至会先把猜测路径的指令执行了——这正是 Day 34 Spectre 的病根：数据回滚了，但缓存状态没回滚，泄露了秘密。

Day 31 · 缓存层级

内存比 CPU 慢两个数量级，缓存就是中间的缓冲垫。记住这张「延迟阶梯」——它是本周乃至整个系统课的锚点：

操作 延迟(约) 类比(把1个周期当1秒) ───────────────────────────────────────────────────── L1 命中 ~1 ns 1 秒 L2 命中 ~4 ns 4 秒 L3 命中 ~15 ns 15 秒 主存(DRAM) ~100 ns ~2 分钟 NVMe SSD 随机读 ~100 μs ~1 天 机械硬盘寻道 ~10 ms ~4 个月 同城网络往返 ~0.5 ms ~6 天

cache line（通常 64 字节）是缓存的最小搬运单位——你读 1 个字节，硬件搬 64 个。这解释了为什么「顺序访问快、随机访问慢」，也解释了 false sharing（两个核各改一个变量，但它俩在同一 cache line 上，导致缓存行在核间反复弹跳）。

Day 32 · SIMD + 多核 + 内存一致性

SIMD（单指令多数据，SSE/AVX-512）一条指令同时算 8 个或 16 个浮点数——这是 CPU 上做矩阵运算、numpy、以及 llama.cpp 在 CPU 上跑推理的核心加速手段。NUMA（非统一内存访问）：多路服务器里每颗 CPU 有自己的本地内存，访问别的 CPU 的内存要走 QPI/UPI 互联，慢一截（下周整周的主题）。MESI 协议让多核的缓存保持一致；内存屏障（memory barrier）和 happens-before 是并发正确性的地基。x86 是强内存模型（TSO），ARM 是弱内存模型——同一份无锁代码在 Mac M 芯片上可能暴露出在 x86 上藏着的 bug。

Day 33 🔧 · CPU 性能动手 & Day 34 🔐 · 侧信道

周五我们用 perf stat 看了 cache miss 率、用不同矩阵遍历顺序演示了缓存友好性、用 numpy 感受了 SIMD 加速。周六的侧信道把「性能优化机制」翻过来当「攻击面」看：Spectre/Meltdown 的本质是——推测执行 + 缓存留下的时序痕迹，让本该隔离的秘密可以被间接测出来。Rowhammer 则是反复敲同一行 DRAM，让相邻行的比特翻转。这两类攻击的共同教训：凡是"为了快"而共享的东西（缓存、预测器、DRAM 物理行），都是潜在的信息泄露通道。这个思维在 GPU 多租户（下下周）和 Agent 沙箱里会一再出现。

现在把七块拼成一张图——一条 load 指令的完整命运，把本周所有机制串起来：

┌─────────────── 一条 load rax, [rbx] 的旅程 ───────────────┐ 取指(IF) → 译码(ID) → 分支预测器猜好了后续路径 (Day30) ↓ 乱序引擎把它塞进保留站，发现它不依赖谁 → 提前发射 (Day30) ↓ 地址计算 → 查 L1d 缓存 (Day31) ├─ L1 命中 → ~1ns 拿到数据，写回寄存器 └─ L1 未命中 → 查 L2 → L3 → 主存 (~100ns，OoO 期间 CPU 继续跑别的不依赖指令，把这100ns"藏"起来) ↓ 若这是多核共享数据 → MESI 协议确保拿到的是最新值 (Day32) ↓ 若地址被推测执行"偷跑"访问过 → 缓存状态已改变 → 这就是 Spectre 的泄露点 (Day34)
这张图就是本周的「一句话总纲」：现代 CPU 的全部复杂度，都是为了在"内存比 CPU 慢 100 倍"这个残酷现实下，尽量不让 CPU 空等。流水线、乱序、缓存、预测——全是「藏延迟」的手段。记住这一点，下面看 LLM 推理就顺了。

2. LLM 推理里 CPU 到底扮演什么角色

很多人有个直觉误区：「大模型推理是 GPU 的事，CPU 就是个打杂的。」这话对了一半——重活确实在 GPU，但 CPU 承担了整条流水线里所有"胶水"和"调度"工作，一旦这些环节慢了，昂贵的 GPU 就会饿肚子（starvation），利用率掉到 40%。作为做 Agent 安全和推理服务的人，你必须知道 CPU 在推理里具体干哪些活。

2.1 一次推理请求里，CPU 的活清单

阶段CPU 在做什么为什么可能成瓶颈
请求接入HTTP/gRPC 解析、鉴权、限流、路由（vLLM 的 API server 是 Python）Python GIL、序列化开销；高 QPS 下单核打满
Tokenization把文本切成 token id（BPE/SentencePiece，纯 CPU 算法）长 prompt + 高并发时，tokenize 本身能占毫秒级
调度continuous batching：决定哪些请求这一步拼进 batch、KV cache 块分配（PagedAttention 的 block table 在 CPU 侧管理）调度器是 Python 单线程，batch 大时调度开销挤占 GPU 空档
Kernel launchCPU 向 GPU 提交 CUDA kernel、准备参数、下发拷贝命令每步 decode 要 launch 几百个 kernel，launch 开销可能超过 kernel 本身执行时间
采样(sampling)logits 的 top-k / top-p / temperature 处理、penalty——部分实现在 CPUvocab 5万~15万维，采样若落到 CPU 会拖慢每个 token
De-tokenization + 流式返回token id → 文本、SSE 逐块推给客户端流式场景每个 token 都要走一遍，累积可观

看到没？GPU 只负责「矩阵乘」那一小段，前后左右全是 CPU 的活。这也是为什么 vLLM、SGLang 这些引擎近年拼命做的事就是「把 CPU 的开销从关键路径上挪走」——比如把调度和 GPU 计算重叠（overlap）、用 CUDA Graph 把「几百次 kernel launch」压缩成「一次 graph replay」。

2.2 CUDA Graph：直接对应本周的「kernel launch 开销」

Day 29 讲过 CPI 和指令开销。放到异构世界，「CPU 发起一次 GPU kernel launch」本身要走驱动、拷贝参数、系统调用，大约 5–20 微秒。一步 decode 若要 launch 300 个 kernel，光 launch 就 1.5~6 毫秒——而每个 kernel 在 H100 上可能只跑几微秒。CPU 成了 GPU 的"发令官"，但发令太慢，GPU 站着等口令。

# 感受 kernel launch 开销：同样的小算子，开/关 CUDA Graph
import torch, time

x = torch.randn(1024, 1024, device='cuda')

def many_small_ops(x):
    for _ in range(200):        # 模拟 decode 一步里的大量小 kernel
        x = x * 1.0001 + 0.0001
    return x

# 不用 graph：每次 CPU 都要 launch 200 个 kernel
torch.cuda.synchronize(); t0 = time.time()
for _ in range(100):
    many_small_ops(x)
torch.cuda.synchronize()
print(f"eager: {(time.time()-t0)*1000:.1f} ms")

# 用 CUDA Graph：一次录制，之后 replay，CPU 几乎不参与
g = torch.cuda.CUDAGraph()
static_x = x.clone()
torch.cuda.synchronize()
with torch.cuda.graph(g):
    static_out = many_small_ops(static_x)
torch.cuda.synchronize(); t0 = time.time()
for _ in range(100):
    g.replay()
torch.cuda.synchronize()
print(f"cuda graph: {(time.time()-t0)*1000:.1f} ms")
# 典型结果：graph 版快 2~5 倍，快的那部分几乎全是省下的 CPU launch 开销
这个实验能让你亲手感受「CPU 是 GPU 的瓶颈」。在真实 LLM 里，batch size 越小（比如单个用户的 decode），CPU launch 开销占比越高——因为 GPU 那点计算量根本喂不饱它，反而在等 CPU 发令。

3. 推理瓶颈分析：compute-bound vs memory-bound 与 Roofline

这是本周最该带走的一个分析框架，也是下周（内存层级）的桥。判断一个计算「卡在算力还是卡在内存带宽」，用 算术强度（Arithmetic Intensity, AI）：

算术强度 = 浮点运算次数(FLOPs) / 内存访问字节数(Bytes) 单位：FLOPs per Byte Roofline 模型（性能上限）： 达到的性能 = min( 峰值算力, 算术强度 × 内存带宽 ) ↑ compute-bound ↑ memory-bound ┌─ 性能(FLOP/s) │ ╱─────────── ← 峰值算力天花板 (compute-bound 区) │ ╱ │ ╱ ← 斜线 = 带宽×算术强度 (memory-bound 区) │ ╱ │ ╱ └─────────────────────────→ 算术强度(FLOP/Byte) ↑ 拐点：算术强度 = 峰值算力 / 带宽

3.1 为什么 LLM 的 prefill 和 decode 是两种截然不同的负载

这是理解一切推理性能的分水岭，务必吃透：

Prefill（处理 prompt）Decode（逐个生成 token）
一次处理多少 token整个 prompt（几百~几千个）一起一次只算 1 个新 token
矩阵形状大矩阵 × 大矩阵（GEMM）细长向量 × 大权重矩阵（GEMV）
权重复用度高：一份权重服务很多 token极低：一份权重只服务 1 个 token
算术强度高 → compute-bound低 → memory-bound
瓶颈GPU 算力（Tensor Core 吃满）把权重从显存搬到 SM 的带宽

直觉解释 decode 为什么是 memory-bound：生成第 N 个 token 时，你要把模型全部权重（7B 模型 fp16 是 14GB）从显存读一遍，只为了算 1 个 token 的输出。计算量极小，但搬运量巨大。这跟 Day 31 的教训一模一样——瓶颈不是算得慢，是数据搬得慢，只不过 Day 31 是「主存→CPU 缓存」，这里是「GPU 显存(HBM)→GPU 计算核心」。同一个道理，换个尺度。

这也直接解释了几件你天天听到的事：

  • 为什么要 batching：把多个用户的 decode 拼一起，一次读权重服务多个 token，把算术强度拉高，从 memory-bound 往 compute-bound 推，GPU 利用率上去。
  • 为什么量化（INT8/INT4）能加速 decode：权重从 16-bit 压到 4-bit，搬运量减 4 倍，memory-bound 的 decode 直接快近 4 倍——加速来自「少搬数据」，不是「算得快」。
  • 为什么 KV cache 这么关键又这么占内存：不缓存的话，每生成一个 token 都要重算前面所有 token 的 attention，退化成每步都做 prefill。缓存了，代价是显存被 KV cache 大量吃掉（下下周 PagedAttention 主题）。
一句话记忆：prefill 是「算力饱和」的活（像跑分），decode 是「带宽饥饿」的活（像搬砖）。你部署时看到 GPU 利用率高但吞吐低，多半是卡在 decode 的 memory-bound 上——加大 batch 或上量化，而不是换更强算力的卡。

4. 异构计算协调：CPU 与 GPU 如何配合（与踩坑）

异构计算（heterogeneous computing）：一个系统里有多种架构的处理器（CPU 擅长复杂控制流和低延迟单任务，GPU 擅长大规模数据并行），让它们各干各擅长的活。协调的核心难点是三条：数据在哪、谁等谁、怎么重叠。

4.1 数据在哪：PCIe 是隐形的税

CPU 内存（DRAM）和 GPU 显存（HBM）是两片独立的地址空间，中间靠 PCIe 总线连接。PCIe Gen4 x16 大约 32 GB/s——听起来快，但对比 H100 的 HBM3 带宽 ~3.35 TB/s，PCIe 慢了 100 倍。每一次 CPU↔GPU 的数据拷贝，都是走这条窄路。这就是为什么：

  • 你要尽量让数据「常驻」GPU，避免来回拷贝（权重加载一次就留在显存）。
  • 用 pinned memory（锁页内存）——Day 33 的兄弟概念 mlock——让 DMA 引擎直接搬，不经过可分页内存的中转，拷贝更快。
  • 推理框架拼命把 tokenize、采样等「小数据」操作留在能就近处理的地方，避免为了几个 token id 触发一次 PCIe 往返。
# 观察 pinned memory 对 H2D(host→device) 拷贝的影响
import torch, time

N = 256 * 1024 * 1024  # 256M float = 1GB
pageable = torch.randn(N)                    # 普通可分页内存
pinned   = torch.randn(N).pin_memory()       # 锁页内存

def bench(src, tag):
    torch.cuda.synchronize(); t0 = time.time()
    for _ in range(10):
        dst = src.to('cuda', non_blocking=True)
    torch.cuda.synchronize()
    gb = N*4*10/1e9
    print(f"{tag}: {gb/(time.time()-t0):.1f} GB/s")

bench(pageable, "pageable ")   # 受限于额外的一次内存拷贝
bench(pinned,   "pinned   ")   # 通常明显更高，接近 PCIe 峰值

4.2 谁等谁：同步与异步

GPU 操作默认是异步的：CPU 发出 kernel launch 或 copy 后立刻返回去干别的，命令排进 GPU 的 stream（流）队列。只有当 CPU 真的需要 GPU 的结果（比如把 logits 拿回来采样，或 .item()、print(tensor)）时，才会 synchronize 阻塞等待。

新手最常踩的坑：在训练/推理循环里频繁 print(loss.item()) 或 tensor.cpu()。每一次都强制 CPU-GPU 同步，把本可重叠的流水线打断，GPU 被迫停下来等 CPU。这跟 Day 30 分支预测失败清空流水线是同一种"气泡"（bubble）——好不容易并行起来，一个同步点全打回原形。诊断方法：用 Nsight Systems（Day 47 会学）看时间线上那些 CPU 忙、GPU 空的缝隙。

4.3 怎么重叠：让 CPU 和 GPU 都别闲着

理想的推理流水线，是让 CPU 处理请求 N+1 的调度/tokenize，同时 GPU 在算请求 N 的 forward，同时另一个 stream 在做 KV cache 的拷贝。这叫 overlap（重叠），本质和 Day 30 的「流水线并行」思想完全一致，只是把「级」换成了「设备」：

时间 ──────────────────────────────────────→ CPU: [调度step1][tokenize][调度step2][采样step1][调度step3] ... GPU: [====forward step1====][===forward step2===] ... 拷贝: [H2D][.....][D2H step1][H2D step2] ... ↑ 三条通道尽量填满，谁都别站着等口令 对比"没重叠"的糟糕情况： CPU: [调度][ 等GPU ][采样][ 等GPU ] ... GPU: [==forward==] [==forward==] ← 到处是气泡，GPU 利用率上不去

这就是「异构计算协调」这几个字的全部内涵：识别谁擅长什么、把数据放在离它近的地方、用异步 + 多 stream 让所有设备都别停下来等。你之后调 vLLM 参数（比如 --num-scheduler-steps、开不开 CUDA Graph、chunked prefill）本质都是在调这三件事的平衡。

5. 把本周的微架构知识用在推理性能上

最后，把本周 CPU 的具体机制和推理服务的实际调优对应起来，做一张「学以致用」表，帮你把抽象概念钉在工作场景上：

本周概念在 LLM 推理服务里的对应实操建议
缓存友好 / cache line (Day31)tokenizer、采样、调度这些 CPU 热点代码的数据局部性热路径避免 Python 大对象随机访问；性能敏感处用 Rust/C++ 扩展
false sharing (Day31)多线程 API server 里计数器/统计量在同一 cache line高频计数器做 padding 对齐或每线程独立累加再汇总
SIMD / AVX (Day32)CPU 上跑量化模型（llama.cpp）、embedding 计算、前后处理确认 numpy/torch 用了 AVX2/AVX-512 版本；CPU 推理选支持的指令集
NUMA (Day32，下周主题)多路服务器上 GPU 挂在某个 NUMA 节点，CPU 进程若跑在另一节点，PCIe 拷贝要多绕一段用 numactl 把推理进程绑到 GPU 所在的 NUMA 节点
分支预测 / OoO (Day30)解释 CPU 侧代码为何有时慢得莫名——数据依赖、分支密集用 perf stat 看 CPU 侧是否 branch-miss 或 cache-miss 高

快速自测——把 GPU 进程绑到正确的 NUMA 节点（下周会深入，这里先建立肌肉记忆）：

# 看每张 GPU 挂在哪个 NUMA 节点、和其他 GPU 的互联拓扑
nvidia-smi topo -m

# 看系统的 NUMA 拓扑（几个节点、各多少核和内存）
numactl --hardware        # 或 lscpu | grep -i numa

与 AI / Agent 安全的连结

1. 时序侧信道 → 推理服务的信息泄露。Day 34 的 cache-timing 攻击核心是「用时间差反推秘密」。在 LLM 服务上这不是理论：prompt 长度、KV cache 是否命中 prefix、batch 里其他请求的负载，都会以毫秒级的响应时间差表现出来。攻击者可以通过测量 TTFT（首 token 延迟）推断「我的 prompt 是否与另一个租户共享了缓存前缀」，甚至探测系统 prompt 的长度。防御思路和 CPU 侧信道一致：对延迟敏感的路径做时间归一化（padding 到固定延迟），或对跨租户的 prefix caching 做严格隔离。

2. 异构调度是拒绝服务的放大器。本节讲了 decode 是 memory-bound、CPU launch 是瓶颈。攻击者若构造大量「短 prompt + 超长 max_tokens」的请求，会把服务钉死在低效的 decode 阶段，用极小的输入代价耗尽 GPU 的有效吞吐——这是针对推理经济学的 DoS。防御要在网关层限制 max_tokens、按「预估计算量」而非「请求数」做限流，把 Week04 学的限流算法用到推理特性上。

3. GPU 显存残留 = 跨请求的数据泄露。PCIe 两侧是独立地址空间，KV cache、中间激活值都留在显存里。若多租户共享一张卡而显存不清零，前一个用户的 prompt/输出可能被后一个用户的进程读到（Day 48 GPU 多租户会深入）。异构系统里「数据在哪」不仅是性能问题，更是隔离边界问题。

4. Kernel launch 路径是可信计算基（TCB）的一部分。CPU 是「发令官」，它下发给 GPU 的 kernel、参数、拷贝命令，若被篡改（比如恶意的自定义 CUDA 算子、被投毒的推理框架依赖），就能悄悄改变模型行为或窃取权重。Agent 系统里如果允许用户提供自定义算子/插件，这条 CPU→GPU 的命令链必须被当作攻击面严格审计，对应 Week01 讲的信任边界。

5. 性能可观测性 = 安全可观测性。本周学的 perf、以及即将学的 Nsight，既是调优工具也是检测工具。异常的 cache-miss 模式、突然飙升的 kernel launch 频率、非预期的 PCIe 拷贝量，都可能是侧信道攻击或数据外泄的信号。把性能剖析器接进监控（Week12 可观测性主题），让「GPU 利用率异常」和「延迟分布异常」成为安全告警的输入。

1动手：亲手看见 CPU 成为瓶颈。如果你有 GPU 环境，跑本文 §2.2 的 CUDA Graph 对比脚本，记录 eager vs graph 的耗时比。然后把脚本里 many_small_ops 的循环次数从 200 改成 10，再跑一次——观察 graph 的相对优势是变大还是变小，并用「CPU launch 开销占比」解释你看到的现象。（没有 GPU 的话，改跑 §4.1 的 pinned memory 脚本，或用纯 CPU 做同样的"很多小操作 vs 一个大操作"对比。）

2观察：给你的机器画一张延迟/带宽阶梯。在你的机器上运行 lscpu（看缓存大小和 NUMA）、numactl --hardware（若有）、以及 nvidia-smi topo -m（若有 GPU）。把 L1/L2/L3 大小、内存带宽、PCIe 代数、HBM 带宽（查你 GPU 的规格）填进 §3 的 Roofline 心智模型里，算一算：对一个 7B fp16 模型，decode 一步要搬 14GB 权重，在你的 GPU 带宽下理论上单步至少要多少毫秒？这就是你这张卡上单请求 decode 的物理下限。

3思考：为什么"换更贵的卡"常常不解决 decode 慢？假设你把 A100（算力 312 TFLOPS，带宽 2 TB/s）换成算力翻倍但带宽只涨 30% 的新卡，单用户单请求的 decode 速度大约会提升多少？请用「decode 是 memory-bound」的结论推理，并说明在什么条件下（提示：batch size）算力提升才真正开始起作用。把你的答案和「加大 batch」「上量化」两种方案对比一下成本收益。
