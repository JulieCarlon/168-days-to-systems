1. 冯诺依曼架构 vs 哈佛架构

今天你能写 Python，根子上要感谢 1945 年一份未完成的报告。数学家 冯·诺依曼（John von Neumann）在设计 EDVAC 计算机时写下了一个至今仍统治所有主流计算机的思想：程序和数据一样，都存在同一块内存里，都是二进制。

这句话今天听起来平平无奇，但它是革命性的。在此之前的机器（如 ENIAC）要「换程序」意味着用手重新插拔几千根电缆，改一次程序要几天。冯诺依曼说：既然指令也能编码成数字，那就把它和数据一起塞进内存，CPU 挨个把指令读出来执行就行了。换程序 = 换一段内存里的字节。这就是「存储程序（stored-program）」思想——你能 python a.py 然后 python b.py 秒切，本质就是它。

冯诺依曼架构（今天的 PC / 手机 / 服务器） ┌──────────────────────────────┐ │ CPU │ │ 控制单元 + ALU + 寄存器 │ └───────────────┬──────────────┘ │ 一条总线（指令和数据挤同一条路） ┌───────────────┴──────────────┐ │ 内存（指令 + 数据 混在一起） │ └──────────────────────────────┘

类比：把 CPU 想成厨师，内存是仓库。冯诺依曼架构里，菜谱（指令）和食材（数据）堆在同一个仓库、走同一条送货通道。好处是仓库统一管理、灵活；坏处是送菜谱和送食材要抢同一条路——这就是著名的「冯诺依曼瓶颈（von Neumann bottleneck）」：CPU 再快，指令和数据都得从同一条内存总线挤过来，总线带宽成了天花板。你后面会发现，LLM 推理慢的核心原因（memory-bound）就是这个瓶颈的现代放大版。

哈佛架构（Harvard）是另一条路：指令和数据分开存、分开走两条独立总线。好处是取指令和取数据可以同时进行，吞吐翻倍；坏处是不灵活（程序区通常只读，不能自我修改）。纯哈佛架构今天主要活在单片机、DSP、以及 CPU 内部的一级缓存里——现代 CPU 对外是冯诺依曼（主存统一），但 L1 缓存却分成了 L1-I（指令）和 L1-D（数据）两块，这叫「改良哈佛架构（modified Harvard）」。所以真实的 CPU 是两种思想的缝合体。

  • 冯诺依曼：统一内存、单总线、灵活、有带宽瓶颈 → 通用计算机。
  • 哈佛：分离内存、双总线、高吞吐、不灵活 → 嵌入式 / DSP / 缓存层。
  • 现代 CPU：主存冯诺依曼 + L1 缓存哈佛，取两者所长。

2. CPU 三大部件：ALU、寄存器、控制单元

打开 CPU 这个黑盒，抛开缓存、分支预测那些高级玩意（后面几天专门讲），最核心的只有三样东西。

① 算术逻辑单元 ALU（Arithmetic Logic Unit）

这是 CPU 里真正「干活」的电路，负责所有算术运算（加减乘）和逻辑运算（与或非、比较、移位）。它本质是一大堆晶体管搭成的组合逻辑电路：两个输入 + 一个操作码，吐出一个结果和几个标志位（是否为零、是否溢出、是否进位）。你写的 b + c、x > 0、flags & MASK，最终都落到 ALU 上跑一遍。

② 寄存器（Registers）

寄存器是 CPU 内部的一小撮存储单元，是整个存储金字塔里最快、最贵、最少的一层——访问延迟接近 0（1 个时钟周期内），但一颗 x86-64 CPU 通用寄存器也就 16 个（RAX、RBX、RCX…），每个 64 bit。为什么这么少？因为它们直接焊在 ALU 旁边，越多布线越长、越慢、越占面积。

类比：寄存器是厨师手里正握着的那几样东西——刀、正在切的菜。仓库（内存）里东西再多，你要用也得先拿到手上。ALU 只能对寄存器里的值动手，任何来自内存的数据，都必须先 load 进寄存器才能参与运算。这条铁律解释了为什么后面「缓存命中率」这么重要。

③ 控制单元 CU（Control Unit）

控制单元是 CPU 的「大脑指挥中心」。它不算数，只负责协调：从内存把下一条指令取出来、翻译它是什么操作、指挥 ALU 和寄存器按顺序动作、决定下一条指令的地址。它靠两个关键寄存器工作：

  • PC（Program Counter，程序计数器）：存着「下一条要执行的指令」的内存地址。每执行完一条，PC 自动 +1（指向下一条）。if/for/函数调用的本质就是往 PC 里写一个新地址（跳转）。
  • IR（Instruction Register，指令寄存器）：存着「当前正在执行」的那条指令本身。
关键直觉：CPU 没有任何「智能」，它是一台极其死板的机器——PC 指到哪，就取哪条指令，翻译，执行，PC 前进，循环。一秒钟做几十亿次。你所有的 if/for/递归/多线程，在这一层全部塌缩成「不断地读指令、改 PC」。理解了这点，你就理解了汇编、也理解了后面缓冲区溢出攻击为什么能「劫持 PC」。

3. 指令周期：取指—译码—执行—写回

CPU 执行一条指令，走的是一个固定的循环，叫指令周期（instruction cycle），也叫 fetch-decode-execute 循环。经典地分成 4~5 步：

  1. 取指 Fetch：控制单元根据 PC 的值，去内存（实际先查缓存）把这条指令的二进制码搬进 IR。
  2. 译码 Decode：把 IR 里那串 01 翻译成「这是一条加法，操作数在 RBX 和 RCX，结果放 RAX」。
  3. 执行 Execute：ALU 真正做运算，或者控制单元发出内存读写信号。
  4. 访存 Memory（如果需要）：load/store 指令在这一步真正读写内存。
  5. 写回 Write-back：把结果写回目标寄存器，同时更新 PC 指向下一条。

我们用一段能直接看的汇编把它落地。你在 Mac/Linux 上可以这样看 Python 一行加法背后的 C 级汇编（这里用一段 C 演示更清楚）：

# 把 C 编译成汇编看看（Linux；Mac 用 clang 同理）
cat > add.c <<'EOF'
int add(int b, int c) {
    int a = b + c;
    return a;
}
EOF
gcc -O0 -S add.c -o add.s      # -S 只编译成汇编，-O0 不优化方便读
cat add.s

你会看到类似（x86-64，简化后）：

add:
    mov   eax, edi        # 取指+译码+执行：把参数 b(edi) 搬进 eax 寄存器
    add   eax, esi        # ALU 执行：eax = eax + c(esi)
    ret                   # 写回并跳转：结果在 eax，PC 跳回调用者

短短两行运算，CPU 内部却是「取指→译码→ALU 加法→写回 eax→PC 前进」这套流程走了三遍（三条指令）。一条 a=b+c 在硬件层不是一个动作，而是一串微操作。这就是为什么理解硬件后，你对「这段代码到底慢在哪」会有完全不同的判断力。

历史彩蛋：早期 CPU 是「一条指令走完 4 步才开始下一条」，ALU 大部分时间在发呆。现代 CPU 用流水线（pipeline）让第 1 条在写回时、第 2 条在执行、第 3 条在译码、第 4 条在取指——像洗衣店同时洗/烘/叠多批衣服。这是 Day 30 的主角，今天先埋个伏笔。

4. 性能公式：时间 = 指令数 × CPI × 周期

现在到了今天最有价值的一节。你天天说「这个模型跑得慢」，但「快慢」到底由什么决定？计算机体系结构里有一个黄金公式（Iron Law of Performance），一次性讲清楚了所有 CPU 性能的来源：

程序运行时间 = 指令数(N) × 每条指令周期数(CPI) × 时钟周期长度(T) = N × CPI × (1 / 频率) 其中： N = Instruction Count，你的程序被编译成多少条机器指令 CPI = Cycles Per Instruction，平均每条指令花几个时钟周期 T = 一个时钟周期的时间 = 1 / 主频（3GHz → T ≈ 0.33 纳秒）

这个公式的威力在于，它把「性能」拆成三个相互独立、由不同角色掌控的因子：

因子谁能改变它例子
N 指令数算法 + 编译器 + 指令集换更好的算法、开 -O2 优化、用 SIMD 一条指令算 8 个数
CPI 每指令周期CPU 微架构流水线、乱序执行、缓存命中率——缓存 miss 一次 CPI 飙到几百
T 周期长度主频 / 制程工艺超频、更先进的 3nm 工艺让频率更高

为什么这个公式对你极其重要：绝大多数外行只盯着 T（「我的 CPU 有 5GHz！」），但真正决定 AI 负载快慢的往往是 N 和 CPI。举例：你把一个 Python 循环改成 numpy 向量化，主频一点没变（T 不变），但 N 暴跌（一条 SIMD 指令干原来 8 条的活）、CPI 也改善（数据连续、缓存友好），于是快了几十倍。性能优化的本质，就是在这三个因子上做文章。

5. IPC 与「频率不代表性能」

IPC（Instructions Per Cycle，每周期指令数）就是 CPI 的倒数：CPI 是「每条指令花几个周期」，IPC 是「每个周期能完成几条指令」。现代 CPU 通过流水线 + 超标量（一个周期发射多条指令）能把 IPC 做到 3~6,远大于 1。

把黄金公式换个写法，你会得到一个更顺口的版本：

性能 ∝ 频率 × IPC / 指令数 每秒完成的有效工作 = 频率 × IPC = (每秒周期数) × (每周期指令数)

这解释了 CPU 圈一个反直觉的现象：高频率 ≠ 高性能。2004 年 Intel 的 Pentium 4 主频冲到 3.8GHz（当年天文数字），但它为了拉高频率把流水线拉到 31 级，IPC 反而很低，结果被主频只有 2GHz 出头、但 IPC 高得多的对手吊打。近年 Apple M 系列芯片主频只有 3GHz 出头，却能打赢 5GHz 的 x86,靠的就是极宽的乱序执行 + 超高 IPC。

一句话记住：频率是「转多快」，IPC 是「每转干多少活」。真正的性能是两者的乘积。厂商爱吹频率是因为它是一个好懂的大数字；工程师看性能要同时看 IPC。你以后看 GPU 也一样——别只看 boost 频率，要看它每周期能吞多少 FLOP。

你可以在自己机器上直接测 IPC。Linux 下 perf 会同时报告指令数和周期数，两者一除就是 IPC：

# Linux: 测一段命令的真实 IPC（insn per cycle）
perf stat -e instructions,cycles python3 -c "sum(range(10_000_000))"

# 输出里会有类似：
#   30,000,123      instructions      #    0.85  insn per cycle
#   35,300,456      cycles
# 那个 0.85 就是 IPC。Python 解释器 IPC 通常偏低（分支多、缓存不友好），
# 换成 numpy 向量化后 IPC 会明显上升。

Mac 上没有 perf,但可以用 sudo powermetrics 或 Instruments 看类似指标——今天先建立概念，周五的 LAB（Day 33）会带你系统地实操 perf stat 看 cache miss 和 IPC。

6. CISC vs RISC：指令集的两种哲学

前面说 CPU 死板地「取指令、译码、执行」。那么「指令」长什么样、有多少种，是谁规定的？答案是指令集架构（ISA，Instruction Set Architecture）——它是硬件和软件之间的合同：CPU 承诺认识这些指令，编译器负责把你的代码翻译成这些指令。历史上分出两大哲学流派：

CISC（复杂指令集）RISC（精简指令集）
代表x86 / x86-64ARM / RISC-V / MIPS
指令数量多、复杂（上千条）少、简单（几十到几百条）
单条指令一条能干复杂事（如「从内存读、算、写回」一条搞定）每条只干一件小事，load/store 专门指令
指令长度变长（1~15 字节）定长（多为 4 字节），译码简单
理念让硬件复杂点，程序短一点（N 小）让指令简单点，好流水线、好并行（CPI 小、频率高）

类比：CISC 像一台功能超多的多功能料理机——一个按钮「打豆浆」自动完成泡豆、打磨、加热、过滤；RISC 像一套基础厨具——你得分别「加水、加豆、开火、搅拌」，每步简单但你能灵活组合、每步都能优化到极致。

这场争论的现代结局很有意思：两者在内部融合了。今天的 x86 CPU 表面上收的是复杂的 CISC 指令，但进 CPU 后第一件事就是把每条 CISC 指令拆解成若干条内部的类 RISC 微操作（micro-ops / μops）,再喂给一个 RISC 风格的高效执行核心。所以「CISC vs RISC」在 2020 年代已经不是硬件之争，更多是ISA 生态和授权模式之争——这就引出了下一节。

7. x86 vs ARM：两大王朝的现实分工

作为搞 AI 基建的人,你几乎每天都同时接触这两套架构而不自知:你的开发 Mac 大概率是 ARM(Apple Silicon),你训练/推理的服务器大概率是 x86(Intel/AMD),而云上越来越多的省钱实例是 ARM(AWS Graviton)。搞清它们的分工很实用:

x86-64（Intel / AMD）ARM（Apple / Graviton / 手机）
指令集类型CISC（内部转 RISC μops）RISC（AArch64）
商业模式Intel/AMD 自己造芯片、卖芯片ARM 只卖 IP 授权，别人自己造（Apple、亚马逊、高通）
能效性能强、功耗高每瓦性能极佳，先占领手机、正在攻数据中心
典型阵地桌面、传统服务器、绝大多数训练集群手机、Apple Mac、AWS Graviton、边缘设备
软件生态历史包袱重但最全，几乎所有软件原生支持崛起中；部分 x86 二进制需转译（Rosetta 2 / QEMU）

你可以立刻在自己机器上确认你手里是哪个架构:

# 看你当前 CPU 架构
uname -m
#   x86_64   → 你在 Intel/AMD 机器上
#   arm64    → 你在 Apple Silicon 或 ARM 服务器上

# Mac 上看 CPU 详细型号
sysctl -n machdep.cpu.brand_string

# Linux 上看指令集支持的特性（有没有 avx2、avx512、neon 等）
lscpu | grep -i flags

为什么这对 AI 工程重要?两个直接后果:① 你在 M 系列 Mac 上 pip install 一个含 C 扩展的库(如某些旧版 pytorch、老 wheel),可能因为没有 arm64 预编译版而报错或跑进 Rosetta 转译层变慢;② Docker 镜像有架构之分,你在 Mac(arm64)上 build 的镜像直接推到 x86 服务器会跑不起来,必须用 docker buildx 做多架构构建——这个坑你在 Phase 3 学容器时会正面撞上。今天先在脑子里种下「架构不是一个东西」这个意识。

🔗 与 AI / Agent 安全的连结

1. 「频率不代表性能」直接映射到 GPU 选型。 你未来要为推理服务选 GPU,如果只看 boost 频率就会做错决策。真正决定 LLM 吞吐的是「每周期能做多少张量运算」——也就是 GPU 版的 IPC(Tensor Core 吞吐)乘以频率,再乘以显存带宽。今天建立的「性能 = 频率 × 每周期工作量」这个乘积直觉,是你 Week 07 分析 GPU、Week 08 分析推理瓶颈的地基。

2. 冯诺依曼瓶颈是 LLM「memory-bound」的祖师爷。 今天讲的「指令和数据挤同一条总线」在 LLM 推理里被放大成「模型权重和 KV cache 都要从显存搬到计算单元,搬运比计算慢得多」。Day 38 你会推导出「为什么 decode 阶段是 memory-bound」,那套推理的原始直觉就是今天的冯诺依曼瓶颈。

3. 指令集差异 = 供应链攻击面。 你的 Agent 沙箱如果跨架构部署(开发机 arm64、生产 x86),一个被投毒的多架构镜像可能在不同架构上表现不同——攻击者甚至可以让恶意逻辑只在 x86 生产环境触发,在你 arm64 开发机上测试时完全正常。理解架构差异,才能审计「同一份镜像在不同平台是否真的等价」。

4. PC(程序计数器)劫持是内存攻击的核心。 今天你知道了 CPU 靠 PC 决定「下一条执行什么」。Day 41 的缓冲区溢出攻击,本质就是覆盖栈上的返回地址,骗 CPU 把 PC 设成攻击者的 shellcode 地址。理解 PC 的死板机制,才能理解为什么「数据」能变成「被执行的指令」这种攻击成立。

5. 微架构 = 侧信道的物理来源。 今天提到的乱序执行、缓存,这些为了提升 IPC 的优化,恰恰是 Spectre/Meltdown(Day 34)侧信道攻击的物理根源。CPU 为了快而「推测执行」,把不该看到的数据短暂放进了缓存,攻击者再通过缓存时序把它读出来。搞 Agent 安全,尤其是多租户共享 GPU 的场景,这类硬件级泄露是你绕不开的威胁模型。
