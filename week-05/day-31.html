1 · 为什么需要缓存：内存墙与局部性原理

先记住一组数字，这是整个现代计算机性能优化的物理基础。假设 CPU 一个时钟周期是 0.3 纳秒（约 3.3 GHz），把每一级存储的延迟换算成「相当于多少个时钟周期」：

存储层级典型延迟约等于时钟周期类比（放大到「1 周期 = 1 秒」）
寄存器 register0.3 ns11 秒（就在手边）
L1 缓存~1 ns~44 秒（伸手拿桌上的东西）
L2 缓存~4 ns~1212 秒（起身走到书架）
L3 缓存~15 ns~4040 秒（走到隔壁房间）
主内存 DRAM~100 ns~3005 分钟（开车去趟超市）
NVMe SSD~100 μs~300,0003.5 天
机械硬盘~10 ms~30,000,000接近 1 年

看到问题了吗？CPU 内核和主内存之间差了两个数量级。这条鸿沟叫 内存墙（Memory Wall）：几十年来 CPU 速度翻了几千倍，DRAM 延迟几乎没怎么降。如果没有缓存，CPU 每次取数都要等 ~300 个周期，流水线、乱序执行这些昨天讲的精妙设计全都白费。

缓存能起作用，靠的是程序访问内存的两条统计规律，合称 局部性原理（Principle of Locality）：

  • 时间局部性（Temporal Locality）：刚访问过的数据，很可能马上又被访问。比如循环里的计数器 i、函数栈上的局部变量。→ 把它留在缓存里。
  • 空间局部性（Spatial Locality）：访问了某个地址，很可能马上访问它旁边的地址。比如遍历数组 a[0], a[1], a[2]...、顺序执行的指令。→ 一次搬一整块进缓存。

你可以用数学直觉理解：内存访问不是均匀随机分布，而是高度聚集的。缓存本质是一个赌局——赌「你接下来要的东西，我这里已经有了」。命中（hit）就赚了 300 个周期，未命中（miss）也只是回到没缓存的情况。只要命中率够高，期望收益巨大。

平均访问时间公式：AMAT = 命中时间 + 未命中率 × 未命中代价。假设 L1 命中 1 周期、未命中率 5%、未命中要去内存花 300 周期，那么 AMAT = 1 + 0.05 × 300 = 16 周期。命中率从 95% 提到 99%，AMAT 直接降到 1 + 0.01 × 300 = 4 周期。性能对命中率极其敏感——这就是我们今天要学的一切的动机。

2 · L1 / L2 / L3 三层缓存

既然缓存这么好，为什么不做一个巨大的、又快又大的缓存？答案是物理定律：存储越大越慢越贵。SRAM（做缓存用的静态存储）比 DRAM 快，但每比特要 6 个晶体管，成本高、密度低。工程上的妥协就是分层——用一小块极快的，配一块中等的，再配一块大的，形成金字塔。

┌──────────────┐ │ CPU 核心 │ 寄存器（几百字节，0.3ns） └──────┬───────┘ ┌──────┴───────┐ │ L1 I / D │ 32KB+32KB，~1ns，每核私有 └──────┬───────┘ ┌──────┴───────┐ │ L2 │ 256KB~1MB，~4ns，每核私有 └──────┬───────┘ ┌──────┴───────┐ │ L3 (LLC) │ 8~64MB，~15ns，多核共享 └──────┬───────┘ ┌──────┴───────┐ │ 主内存 DRAM │ 16~512GB，~100ns └──────────────┘
  • L1：最快最小，通常分成 L1i（指令）和 L1d（数据）两个独立缓存（哈佛结构，昨天提过），这样取指和取数据不打架。每核私有。
  • L2：稍大稍慢，一般是统一缓存（指令数据混放）。现代 CPU 里每核私有。
  • L3（LLC，Last Level Cache）：最大，通常被同一颗芯片上的所有核共享。这是核间共享数据、以及后面 false sharing 问题的舞台。

访问流程：CPU 要一个地址 → 先查 L1，命中就返回（~1ns）→ 没命中查 L2 → 再没命中查 L3 → 最后才去内存（~100ns），并把数据「回填」到各级缓存里，供下次使用。这叫 缓存层次（cache hierarchy）的 lookup 链。

在 Linux 上你可以直接看到自己机器的缓存配置：

# 方法一：lscpu 一眼看全部层级大小
lscpu | grep -i cache

# 方法二：直接读 sysfs，看得更细（index0=L1d, index1=L1i, index2=L2, index3=L3）
cat /sys/devices/system/cpu/cpu0/cache/index0/size          # 大小
cat /sys/devices/system/cpu/cpu0/cache/index0/level         # 第几级
cat /sys/devices/system/cpu/cpu0/cache/index0/type          # Data/Instruction/Unified
cat /sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size   # cache line 大小
cat /sys/devices/system/cpu/cpu0/cache/index0/ways_of_associativity # 相联度

# macOS 上用 sysctl
sysctl -a | grep cachesize
sysctl hw.cachelinesize

3 · cache line：缓存搬运的最小单位

这是今天最重要的概念之一，请务必记牢。缓存和内存之间搬数据，不是一个字节一个字节搬，而是一整块一整块搬。这个块叫 cache line（缓存行），在几乎所有现代 x86 和 ARM 上都是 64 字节。

也就是说，你哪怕只读一个 char（1 字节），CPU 也会把它所在的、对齐到 64 字节边界的那整行 64 字节全搬进缓存。为什么？因为空间局部性——你读了 a[0]，大概率马上要 a[1]，与其一个个搬，不如一次搬 64 字节（能装 16 个 int 或 8 个 double）。

类比：cache line 就像图书馆的「取书规则」。你只想看某本书的第 37 页，但管理员规定「一次必须借走整本书」。如果你接下来真要看第 38、39 页（顺序访问），这规则帮你省了无数趟；但如果你东翻一页西翻一页（随机访问），你每次都借一整本书却只看一页，浪费巨大——这就是「缓存不友好」的根源。

这解释了一个经典现象：遍历二维数组，行优先比列优先快几倍。C/NumPy 的二维数组默认按行连续存储（row-major）。按行遍历时，每读一个 cache line 就用满 16 个元素；按列遍历时，每次跳一整行的距离，每个 cache line 只用 1 个元素就被换出，命中率暴跌。我们今天的练习就来实测这个。

# 用 Python 感受 cache line 效应（NumPy 底层是连续内存）
import numpy as np, time
n = 8000
a = np.ones((n, n), dtype=np.float64)

t = time.perf_counter()
s = a.sum(axis=1)          # 按行求和：沿连续内存方向，缓存友好
print("行优先:", time.perf_counter() - t)

t = time.perf_counter()
s = a.sum(axis=0)          # 按列求和：每次跨一整行，缓存不友好
print("列优先:", time.perf_counter() - t)
# 典型结果：列优先明显更慢，尽管计算量完全相同

4 · 映射方式：地址如何找到缓存槽

缓存比内存小得多，所以必然是「多个内存地址争抢同一批缓存槽」。给定一个内存地址，怎么决定它能放进缓存的哪个位置？这就是 映射方式（placement policy）。有三种：

4.1 直接映射（Direct-Mapped）

每个内存块只能放进唯一一个缓存槽。规则很简单：槽号 = 块地址 mod 槽数。硬件实现最便宜、查找最快，但缺点致命：如果两个热数据恰好映射到同一个槽，它们会不停把对方踢出去（叫 冲突未命中 / conflict miss），哪怕缓存整体还很空。

4.2 全相联（Fully Associative）

一个内存块可以放进任意缓存槽。灵活性最高、冲突未命中最少，但要查一个地址在不在缓存里，得同时比较所有槽的标签，硬件成本高得离谱。只用在极小的缓存（如 TLB）里。

4.3 组相联（Set-Associative）——实际采用的折中

把缓存分成若干「组（set）」，每组有 N 个槽（叫 N 路，N-way）。一个内存块先用取模确定放进哪个组，然后在组内可以放进任意一路。这就兼顾了两者：定位组便宜，组内小范围灵活。现代 CPU 的 L1 通常 8-way，L3 常见 16-way 甚至更高。

一个 64 位物理地址被硬件切成三段来完成查找：

┌─────────── Tag ───────────┬──── Set Index ────┬── Offset ──┐ │ 剩下的高位，用来在组内比对 │ 选哪个组（set） │ 行内偏移(6位)│ └───────────────────────────┴───────────────────┴────────────┘ └ 64B line → 6 位
  • Offset（偏移）：cache line 是 64 字节 = 2⁶，所以低 6 位定位「行内第几个字节」。
  • Set Index（组索引）：中间几位选哪个组。有多少组就用多少位。
  • Tag（标签）：剩下的高位，存在缓存槽里；查找时和地址的 tag 逐路比对，确认「这一路存的正是我要的那块」。
为什么某些「2 的幂」的步长特别慢？ 如果你以 4096 字节（正好一页、也是 2 的幂）为步长访问数组，这些地址的 Set Index 位可能完全相同 → 全挤进同一个组 → 组内 N 路很快被占满 → 疯狂冲突未命中。这叫 cache thrashing。这也是为什么有些高性能库会故意给数组加一点「padding」，把 2 的幂的尺寸错开一点。

5 · 替换策略：缓存满了淘汰谁

当一个组的 N 路都被占满，又来了一个新块要放进这个组，就得踢掉一个旧的。踢谁？这是 替换策略（replacement policy）：

  • LRU（Least Recently Used，最近最少使用）：踢掉最久没被访问的那个。最符合时间局部性的直觉，效果好，但要精确记录每一路的访问顺序，路数一多硬件成本就高。
  • Pseudo-LRU（伪 LRU）：用一棵二叉树的几个 bit 近似 LRU，成本低效果接近，是实际 CPU 常用的。
  • Random / RRIP 等：随机替换实现最简单；现代 CPU（尤其 L3）常用更聪明的 RRIP 类策略来抵抗「一次性扫过大数组」这种把缓存冲垮的访问模式。

作为软件工程师，你几乎不能直接控制替换策略（它在硬件里），但你要知道它的存在——它解释了为什么「工作集（working set）刚好超过缓存大小」时性能会有一个悬崖式下跌：只要你反复访问的数据总量能装进 L2，就一直命中；一旦稍微超过，LRU 就开始不停淘汰你马上又要用的东西，命中率崩盘。这个「悬崖」在今天的练习里能实测出来。

6 · 写策略：write-through vs write-back

前面讲的都是「读」。写数据时，缓存里改了，什么时候同步回内存？这是 写策略，两种主流：

write-through（写直达）write-back（写回）
行为写缓存的同时立刻写内存只写缓存，标记为「脏(dirty)」，等这行被替换出去时才写回内存
优点内存始终是最新的，简单、一致性好合并多次写、大幅减少内存流量，快得多
缺点每次写都碰内存，慢、占带宽内存暂时是「旧的」，多核一致性更复杂

现代 CPU 的数据缓存几乎都用 write-back，因为写操作也高度聚集，合并起来收益巨大。为了缓和 write-through 的慢，还会配一个 write buffer（写缓冲），让 CPU 写完不必等内存确认就继续跑。

还有一个配套问题：写一个当前不在缓存里的地址时怎么办？

  • write-allocate（写分配）：先把那一行读进缓存，再在缓存里改。常和 write-back 搭配——因为赌你等会儿还会再写它。
  • no-write-allocate（写不分配）：直接写内存，不占缓存。常和 write-through 搭配。
脏行（dirty line）与 dirty 的联系：还记得 Week 02 讲页缓存时的「脏页」吗？那是 OS 层面「内存里的数据比磁盘新，还没写回」；这里的「脏 cache line」是硬件层面「缓存里的数据比内存新，还没写回」。同一个「延迟写、批量刷」的思想，在计算机系统里反复出现——从寄存器到缓存、到页缓存、到数据库 WAL，都是它。

7 · false sharing：多核下的隐形性能杀手

这是本节的重头戏，也是并发编程里最坑的性能陷阱之一，做 LLM 推理并行时你一定会撞上。

先补一个背景：多核 CPU 每核有自己的 L1/L2，同一份数据可能同时存在于多个核的缓存里。为了保证大家看到的是一致的值，硬件跑一套 缓存一致性协议（cache coherence，如 MESI）（明天 Day 32 会细讲）。核心规则是：当一个核写了某个 cache line，其他核里这一行的副本必须作废（invalidate），下次要用得重新去拿最新的。

关键在于：一致性是以整个 cache line（64 字节）为单位的，不是以变量为单位的。于是灾难发生了——两个线程各自修改两个逻辑上毫不相关、但恰好落在同一个 64 字节 cache line 里的变量，硬件会误以为它们在争抢同一块数据，不停地互相 invalidate。这就是 false sharing（伪共享）：没有真正的共享，却付出了共享的代价。

一个 64 字节 cache line： ┌──────────────┬──────────────┬─────────────────────────┐ │ counter[0] │ counter[1] │ ... 其余空间 ... │ │ (线程0在写) │ (线程1在写) │ │ └──────────────┴──────────────┴─────────────────────────┘ ↑ 逻辑上互不相关，物理上同一行 → 每次写都作废对方 → 性能暴跌 
# 用两个 Python 进程 + 共享内存演示（Python 有 GIL，用多进程绕开）
# 直觉版：C/Go 里更明显。这里给出概念性对照代码
import numpy as np
from multiprocessing import Process, shared_memory

# 坏：两个进程各写数组相邻位置 → 落在同一 cache line
# 好：把每个进程写的位置隔开 ≥ 64 字节（8 个 float64）→ 落在不同 cache line

def worker(shm_name, idx, iters):
    shm = shared_memory.SharedMemory(name=shm_name)
    arr = np.ndarray((16,), dtype=np.float64, buffer=shm.buf)
    for _ in range(iters):
        arr[idx] += 1.0          # idx=0,1 相邻 → false sharing
    shm.close()
# 把 idx 换成 0 和 8（隔开 64 字节），两个进程互不干扰，明显更快

解决办法叫 padding / 缓存行对齐：故意在两个热变量之间塞满填充字节，把它们挤到不同的 cache line。C++ 有 alignas(64)、C++17 有 std::hardware_destructive_interference_size，Go 常用 [64]byte 填充，Java 有 @Contended。原则一句话：被不同线程频繁写的变量，让它们各占一整个 cache line。

8 · 缓存友好数据结构 + prefetch

8.1 写缓存友好的代码

把今天所有概念收拢成几条可操作的准则：

  • 顺序访问优于随机访问：数组 > 链表。链表节点散落在堆各处，每跳一个节点大概率一次 miss；数组连续，一个 cache line 顺带带出后续多个元素。
  • 按内存布局的方向遍历：行主序数组就按行遍历（内层循环走连续维度）。这是矩阵乘法优化里「循环交换（loop interchange）」的基础。
  • SoA vs AoS：如果你每次只用对象的某几个字段，用「结构体数组（AoS）」会把用不到的字段也拖进缓存，浪费带宽；改成「数组的结构体（SoA）」——每个字段一个连续数组——只加载真正要用的，命中率更高。这正是列式数据库（Day 136 的 Parquet）和向量化计算快的底层原因。
  • 分块 / tiling：处理大矩阵时，把它切成刚好能塞进 L2 的小块，在小块内把数据反复用完再换下一块，最大化缓存复用。这是所有高性能 GEMM（矩阵乘）内核的核心技巧。
  • 紧凑数据：能用 int32 就别用 int64，能对齐就对齐。数据越小，一个 cache line 装得越多，等效缓存越大。这也是 LLM 量化（Day 52）不只省显存、还能提速的原因之一。

8.2 prefetch：把数据提前搬进来

预取（prefetch）是「在你真正需要数据之前，就提前把它从内存搬进缓存」，用来把 miss 的等待时间藏在其他计算后面。两种：

  • 硬件预取（hardware prefetcher）：CPU 自动检测访问模式。它非常擅长「顺序 / 固定步长」的访问——你按顺序读数组，它就悄悄把后面几行提前拉进来。这也是顺序访问快的又一个原因。但它对随机访问、指针跳转无能为力。
  • 软件预取：程序员显式插入预取指令（GCC 的 __builtin_prefetch(ptr)、x86 的 PREFETCHT0），告诉 CPU「我马上要用这个地址，先帮我搬」。用于硬件预取器猜不到的场景，比如遍历链表时预取下一个节点。用好了能大幅提速，用错了反而污染缓存。
// C 里的软件预取示例：遍历时提前拉下一批数据
for (int i = 0; i < n; i++) {
    __builtin_prefetch(&data[i + 16], 0, 3);  // 提前 16 个预取，0=读, 3=高时间局部性
    process(data[i]);                          // 等真用到时，它已经在 L1 了
}

与 AI / Agent 安全的连结

1 · LLM 推理为什么是 memory-bound（后天 Day 38 的伏笔）。 今天的内存墙就是根源。decode 阶段每生成一个 token，都要把整个模型权重从显存搬到计算单元过一遍，而算术强度极低——搬得多、算得少，瓶颈完全在「搬数据」而非「算」。GPU 的 L1/L2、共享内存（shared memory）本质就是今天讲的缓存层级，FlashAttention 的核心思想正是「把注意力计算分块，让中间结果留在片上高速缓存里，避免反复往显存写 QK 矩阵」——就是 §8.1 的 tiling 在 GPU 上的翻版。

2 · 缓存侧信道攻击（后天专题 Day 34 的地基）。 缓存命中快、未命中慢，这个「时间差」本身就是信息泄露渠道。攻击者通过测量自己访问某地址的耗时，就能推断「受害者刚才是否访问过同一个 cache line」——这就是 Flush+Reload、Prime+Probe 等经典攻击。Spectre/Meltdown 的最后一步「把偷到的秘密带出来」，靠的就是把秘密编码成缓存状态再用时间测出来。今天你理解了 cache line、命中/未命中的时间差，明天的侧信道就水到渠成。做 Agent 安全时，多租户共享 GPU/CPU 的环境里，这类跨租户缓存侧信道是真实威胁。

3 · false sharing 拖垮推理服务吞吐。 高并发推理网关里，每个 worker 线程维护自己的计数器（请求数、token 数、延迟统计）。如果这些计数器在内存里挨着，就会 false sharing，核数越多越慢——你加机器加核，QPS 反而不涨。定位这类问题要靠 perf 看缓存一致性流量。写监控埋点、限流计数器时，给热计数器做 cache line 对齐是基本功。

4 · 缓存友好 = 成本优化。 LLM 服务是算力密集型，同样的 GPU/CPU，缓存友好的实现能多服务几成请求。KV cache 的内存布局（连续 vs 分页，Day 42 的 PagedAttention）、batch 内 token 的排布，都在和缓存层级打交道。理解「顺序访问、紧凑数据、分块复用」这三板斧，是你把推理成本压下来的直接工具。

5 · 用缓存时间差做防御检测。 反过来，防御方也能用缓存行为建模。异常的缓存未命中模式（比如某进程在疯狂 flush 特定地址）可能是侧信道攻击的信号。基于硬件性能计数器（PMC，如 cache-misses、LLC-load-misses）的运行时检测，是容器/GPU 多租户环境里识别侧信道与挖矿等滥用行为的一条思路——这和你后面要学的 eBPF、Falco 运行时检测能接上。

今日小练习

1动手 · 实测行优先 vs 列优先。 运行 §3 的 NumPy 代码，记录 sum(axis=1) 和 sum(axis=0) 的耗时比。然后把 n 从 1000 逐步加到 8000，观察两者的差距是变大还是变小，思考为什么（提示：数组越大越装不进缓存，列访问的劣势越明显）。进阶：用 lscpu | grep -i cache 查出你机器各级缓存大小，估算数组多大时会「溢出」L2、L3。

2观察 · 找到你机器的 cache line 和层级。 在 Linux 上遍历 /sys/devices/system/cpu/cpu0/cache/index*/，把每一级的 level / type / size / coherency_line_size / ways_of_associativity 都打印出来，画出你这台机器的缓存金字塔（各级大小、相联度、line 大小）。macOS 用户用 sysctl -a | grep cache。确认 cache line 是不是 64 字节。

3思考 · 为什么链表在现代 CPU 上「越来越不划算」？ 教科书说「链表插入删除 O(1)、数组 O(n)」，但实际中遍历链表常常比遍历数组慢一个数量级。用今天学的 cache line、空间局部性、硬件预取三个概念，写 200 字解释这个「理论 vs 现实」的落差。再想一步：如果一定要用链表，有什么办法让它对缓存更友好？（提示：把多个节点打包成一个连续块——unrolled linked list / 节点池分配。）
