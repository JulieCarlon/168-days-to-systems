1. LAB 1：STREAM —— 测出你机器的真实内存带宽

STREAM 是内存带宽测试的"事实标准"，1990 年代由 John McCalpin 写的。它做四种极简操作，每种都刻意让 CPU 无事可做、只搬内存，于是测出来的就是纯粹的内存带宽（GB/s）。Day 36 讲的"DDR5 理论带宽几十 GB/s、HBM 几 TB/s"，今天用 STREAM 落到你自己的机器上。

四个核心操作（a/b/c 是大数组，q 是标量）：

操作公式每次迭代读写
Copyc[i] = a[i]读 1 + 写 1
Scaleb[i] = q * c[i]读 1 + 写 1
Addc[i] = a[i] + b[i]读 2 + 写 1
Triada[i] = b[i] + q * c[i]读 2 + 写 1

Triad 是最常被引用的那个数——因为它一次迭代做 2 读 1 写、乘加各一次，最贴近真实科学计算/张量运算的访存模式。

步骤

A下载并编译 STREAM（一个 C 文件，无依赖）。
# 官方源码
curl -O https://www.cs.virginia.edu/stream/FTP/Code/stream.c

# 编译。关键：数组要远大于 L3 cache，否则测的是 cache 不是内存！
# -DSTREAM_ARRAY_SIZE 设成 你的 L3 大小(字节)/8 的 4 倍以上
# 例：L3=32MB，则 4M 个 double(32MB)*4=128MB，用 STREAM_ARRAY_SIZE=40000000
gcc -O3 -fopenmp -DSTREAM_ARRAY_SIZE=40000000 -mcmodel=medium stream.c -o stream

./stream
预期：输出四行，每行一个操作的 Best Rate (MB/s)。一台普通 DDR4 双通道桌面机 Triad 大约 15000–25000 MB/s（15–25 GB/s）；DDR5 或多通道服务器能到 40–200+ GB/s。记下你的 Triad 数——它就是你机器"纯搬内存"的天花板。
B验证"数组够大"。如果 Triad 高得离谱（几百 GB/s 甚至上 TB），说明数组还在 cache 里。
# 看你的 cache 大小
lscpu | grep -i cache
# 输出类似：
# L1d cache: 32K   L1i cache: 32K
# L2 cache: 256K
# L3 cache: 32M      <- 这个是关键，数组必须远大于它
C用线程数变化观察带宽饱和。
for t in 1 2 4 8; do
  echo "=== $t threads ==="
  OMP_NUM_THREADS=$t ./stream | grep Triad
done
解读：带宽不会随线程线性增长。1 线程往往就能吃掉单条内存通道的大部分带宽；加到 4/8 线程后曲线很快压平——因为瓶颈是内存控制器和通道数，不是核数。这正是 Day 38 说的"memory-bound：加核没用，要么加带宽要么减访存"的直接证据。
mac 近似：mac 上也能 gcc（其实是 clang）编译 stream.c，但去掉 -mcmodel=medium，OpenMP 需要 brew install libomp 并加 -Xpreprocessor -fopenmp -lomp。Apple Silicon 的统一内存带宽极高（M 系列可达数百 GB/s），你会看到和 x86 完全不同的数量级——这本身就说明"内存带宽是架构级的差异"。

2. LAB 2：遍历顺序对带宽的影响（cache line 实证）

Day 31 讲了 cache line（通常 64 字节）：CPU 每次从内存搬的最小单位是一整条 line，不是一个字节。这意味着顺序访问几乎免费蹭到后续数据，跳着访问则每次都 miss。今天用一段 Python + numpy 亲手把这个差异测出来。

步骤

A行优先 vs 列优先遍历同一个大矩阵。
cat > /tmp/stride.py <<'EOF'
import numpy as np, time

N = 8000                      # 8000x8000 float64 = 512MB，远超 L3
a = np.ones((N, N), dtype=np.float64)

def bench(fn, name):
    t0 = time.perf_counter()
    s = fn()
    dt = time.perf_counter() - t0
    print(f"{name:12s} {dt*1000:8.1f} ms   sum={s:.0f}")

# 行优先：内存里连续 —— cache 友好
bench(lambda: a.sum(axis=1).sum(), "row-major")
# 列优先：每跨一列跳 N*8 字节 —— 每次几乎都 miss
bench(lambda: a.sum(axis=0).sum(), "col-major")
EOF
python3 /tmp/stride.py
预期：row-major 明显快于 col-major，差 2–5 倍（数量取决于 CPU/prefetcher 聪明程度）。两者做的浮点加法完全一样多，唯一区别是访存顺序。这就是 Day 31/39 的核心结论：同样的算法，cache 友好的写法能快几倍。numpy 底层是 C 连续（行优先），所以按行走顺着内存。
B手写一个"变步长"实验，看步长跨过 cache line 那一刻的跳变。
cat > /tmp/cacheline.py <<'EOF'
import numpy as np, time

N = 64 * 1024 * 1024          # 64M 个 int8 = 64MB
buf = np.zeros(N, dtype=np.int8)

for stride in [1, 2, 4, 8, 16, 32, 64, 128, 256]:
    t0 = time.perf_counter()
    # 每隔 stride 个字节写一次，总写入次数随 stride 递减
    buf[::stride] += 1
    dt = (time.perf_counter() - t0) * 1000
    touches = N // stride
    print(f"stride={stride:4d}B  {dt:7.1f} ms  touched={touches//1000:6d}K elems")
EOF
python3 /tmp/cacheline.py
解读：当 stride 从 1 涨到 64（cache line 大小）时，访问的元素数在快速减少，但耗时下降得慢得多——因为 stride≤64 时每条 line 还是被完整搬进来（浪费）。跨过 64B 后，每次访问都命中一条全新的 line，"每字节有效利用率"最低。这就是 cache line 的物理边界在数据上留下的指纹。

3. LAB 3：perf stat 读 cache miss 与 IPC

perf 是 Linux 的性能计数器前端，直接读 CPU 里的硬件性能计数器（PMC）。Day 30/33 提过的 IPC、cache miss，之前只是名词，今天让 CPU 自己告诉你数字。

步骤（Linux）

A对 LAB 2 的两种遍历分别跑 perf，对比 cache miss。
# 先把 row/col 拆成两个脚本，或用 -c 参数控制
perf stat -e cycles,instructions,cache-references,cache-misses,L1-dcache-load-misses \
    python3 -c "import numpy as np; a=np.ones((8000,8000)); a.sum(axis=1).sum()"

echo "==== 现在换成列优先 ===="
perf stat -e cycles,instructions,cache-references,cache-misses,L1-dcache-load-misses \
    python3 -c "import numpy as np; a=np.ones((8000,8000)); a.sum(axis=0).sum()"
预期：列优先版本的 cache-misses 和 L1-dcache-load-misses 明显更高，insn per cycle (IPC) 更低。IPC 低 = CPU 大量周期在干等内存，正是 memory-bound 的体温计。典型 memory-bound 负载 IPC 常低于 1，compute-bound 能到 2–4。
B读懂 perf 输出的关键行。
# 输出里重点看这几行：
#   12,345,678,901  cycles
#    9,876,543,210  instructions   #  0.80  insn per cycle   <- IPC
#      500,000,000  cache-references
#      120,000,000  cache-misses   #  24.00% of all cache refs  <- miss 率
# miss 率 = cache-misses / cache-references
C用 perf stat -d 一键拿到更全的内存视角。
perf stat -d python3 /tmp/stride.py
# -d 会自动附带 L1/LLC 的 load/miss，以及可能的 TLB 统计
观察：LLC-load-misses（Last Level Cache = L3 未命中）就是"真的要去主存拿数据"的次数。这些访问每一次都是 ~100ns 级别（Day 36 讲的内存延迟），是延迟的主要来源。TLB miss 高则提示你该考虑 huge page（Day 39）。
拿不到计数器？ 云上/容器里常见 <not supported> 或 Permission denied。试：① 宿主机上执行 sysctl kernel.perf_event_paranoid=1（临时放宽）；② 容器加 --privileged；③ 虚拟机可能根本没暴露 PMC，换物理机。实在不行只看 cycles/instructions/IPC（软件也能估），cache 计数器可选。

4. LAB 4：vmstat / free —— 系统级内存脉搏

前面测的是"某个程序"的访存。vmstat 和 free 让你看整台机器的内存/换页节奏——上线后诊断"内存到底去哪了"的第一梯队工具。

步骤（Linux）

A先看内存全景。
free -h
# 关注这三列：
#   used      真正被进程用掉的
#   buff/cache  page cache（Day 10 讲的），可随时回收，别当成"内存不够"
#   available   真正还能给新进程用的（≈ free + 可回收的 cache）
关键认知：Linux 会把空闲内存全拿去当 page cache，所以 free 那列常年很小是正常的——看 available 才对。很多人误以为"内存快满了"其实是 cache，一 echo 3 > /proc/sys/vm/drop_caches 就掉下来。
B每秒采样一次，制造内存压力观察变化。
# 一个终端持续采样（每 1 秒，共 20 次）
vmstat 1 20

# 另一个终端制造压力：吃 2GB 内存并反复访问
stress-ng --vm 2 --vm-bytes 1G --vm-keep -t 20s
读 vmstat 的列：free 掉、cache 变化；重点看 si/so（swap in/out，每秒换页 KB）——si/so 常年非 0 = 在换页 = 内存不够，性能灾难。bi/bo 是块设备读写。cs 是每秒上下文切换，in 是中断。压力上来时 us/sy（用户/内核 CPU%）也会涨。
C看谁在吃内存 —— 按 RSS 排序。
ps -eo pid,user,rss,vsz,comm --sort=-rss | head -8
# rss = 常驻物理内存（真占的）
# vsz = 虚拟大小（预订的，通常虚高，别慌）
mac 近似：mac 无 vmstat（有个同名但字段完全不同的 BSD 版 vm_stat，注意下划线）。看内存用 vm_stat 1（页为单位，页大小 pagesize 查）、活动监视器，或 top -l 1 | head。换页看 "Pageouts"。

5. LAB 5：numactl —— 制造并测量跨 NUMA 损失

这是今天的重头戏，也是唯一必须真 NUMA 机器才有意义的实验（单 socket 机器只有 node0，看不到差异）。Day 37 讲了 NUMA：多路 CPU 每个 socket 挂自己的本地内存，访问别的 socket 的内存要绕互联总线（QPI/UPI/Infinity Fabric），慢 1.5–2 倍。今天亲手把这个"慢"量出来。

步骤（Linux，需 2+ NUMA node）

A先看拓扑，确认有几个 node。
numactl --hardware
# 输出示例（2 node 机器）：
# available: 2 nodes (0-1)
# node 0 cpus: 0 1 2 3 ...
# node 0 size: 128000 MB
# node 1 cpus: 24 25 26 ...
# node 1 size: 128000 MB
# node distances:
# node   0   1
#   0:  10  21     <- 本地=10，到 node1 的相对代价=21（约 2.1 倍）
#   1:  21  10
读 distance 矩阵：对角线永远是 10（本地基准），非对角就是远程访问的相对代价。21 意味着跨节点约慢 2.1 倍。只有 1 个 node？那这台机器不是 NUMA，跳到 mac/单节点说明。
B本地绑定 vs 强制远程，跑同一个 STREAM。
# 本地：CPU 在 node0，内存也在 node0
numactl --cpunodebind=0 --membind=0 ./stream | grep Triad

# 远程：CPU 在 node0，但内存强制分配到 node1 —— 每次访问都走互联
numactl --cpunodebind=0 --membind=1 ./stream | grep Triad
预期：远程版 Triad 带宽比本地低 30–50%，延迟相应变高。这就是"跨 NUMA 惩罚"的真身。如果你的多卡训练/推理进程被调度器随机撒在两个 node 上、内存又分配错节点，白白损失这么多带宽——而 LLM 推理本就是 memory-bound，损失直接变成 TPOT 上升。
C看默认分配策略，以及 interleave 的作用。
# 交错分配：内存平均撒在所有 node，牺牲局部性换总带宽
numactl --interleave=all ./stream | grep Triad

# 查看某进程当前的 NUMA 内存分布
numastat -p $(pgrep -n stream)     # 或指定 PID
# 会显示这个进程在 node0/node1 各分了多少内存
解读：--interleave=all 适合"内存访问遍布、无明显局部性"的负载（如某些大 hash 表），用两个 node 的带宽之和。但对有局部性的负载会更慢。没有万能策略——绑定看访问模式。这正是 Day 37/39 说的 NUMA-aware 的核心：知道数据在哪、让计算靠近它。
D观察"first-touch"策略的陷阱。
# Linux 默认 first-touch：内存分配在"第一个写它的线程"所在的 node
# 常见 bug：主线程初始化整个大数组 -> 全落 node0
#           然后 fork 出 node1 的 worker 去处理 -> 全变远程访问！
# 正解：让各 worker 自己初始化自己那块（并行 first-touch）
没有 NUMA 机器怎么办：mac（尤其 Apple Silicon 统一内存）和单 socket 云主机都没有多 node，LAB 5 无法复现。请当作"知道有这回事"：面试/排障时能说出"跨 NUMA 访问慢约 2 倍、first-touch 策略、numactl --membind"就够了。真要动手，租一台 2-socket 云服务器跑一遍（几块钱一小时），值得。

6. LAB 6：mlock —— 把内存钉死在物理页

Day 10 讲过：进程的内存页可能被换出（swap）到磁盘。对延迟敏感的服务（比如实时推理、密钥缓存），一次意外换页就是几毫秒的尖刺。mlock/mlockall 让你把指定内存钉在物理 RAM 里，永不换出。今天用 Python 试一次。

步骤（Linux）

A用 ctypes 调 mlock，锁住一块 buffer。
cat > /tmp/mlock_demo.py <<'EOF'
import ctypes, ctypes.util, mmap, os

libc = ctypes.CDLL(ctypes.util.find_library("c"), use_errno=True)

SIZE = 64 * 1024 * 1024        # 锁 64MB
# 用 mmap 拿一块匿名内存
buf = mmap.mmap(-1, SIZE)
addr = ctypes.addressof(ctypes.c_char.from_buffer(buf))

# mlock(addr, len)：把这块钉进物理内存
ret = libc.mlock(ctypes.c_void_p(addr), ctypes.c_size_t(SIZE))
if ret != 0:
    err = ctypes.get_errno()
    print(f"mlock 失败 errno={err} ({os.strerror(err)})")
    print("多半是 RLIMIT_MEMLOCK 太小，试 ulimit -l unlimited (需权限)")
else:
    print(f"已锁定 {SIZE//1024//1024}MB。查 /proc/self/status 的 VmLck")

os.system(f"grep VmLck /proc/{os.getpid()}/status")
input("按回车释放并退出...")
libc.munlock(ctypes.c_void_p(addr), ctypes.c_size_t(SIZE))
EOF
python3 /tmp/mlock_demo.py
预期：成功时 VmLck: 显示约 65536 kB。如果报 errno=1 (Operation not permitted) 或 12，是 RLIMIT_MEMLOCK 限制——非 root 默认只能锁很少（常见 64KB）。用 ulimit -l 查上限，容器里 docker run --ulimit memlock=-1 放开。
B看当前锁定上限。
ulimit -l          # 单位 KB，unlimited 表示无限
cat /proc/self/status | grep VmLck
C理解代价与适用场景。
# mlockall(MCL_CURRENT | MCL_FUTURE) 锁住进程全部内存
# 好处：消灭换页导致的延迟尖刺
# 代价：这块内存对系统"消失"，不能被回收 -> 别人更容易 OOM
# 谁在用：数据库(Redis/Oracle)、实时系统、HFT、密钥管理(防敏感数据写盘)
安全视角：mlock 的另一大用途是防止密钥/明文被换出到 swap 分区落盘——否则攻击者拿到磁盘就能翻 swap 找密钥。Day 41（明天）讲内存安全会再碰这个主题。
mac 近似：mac 有 POSIX mlock(2)，上面的 ctypes 代码把 find_library("c") 保留即可尝试，但 mac 无 /proc，去掉那两行 grep。Apple Silicon 无 swap 压力时效果不明显。

🔗 与 AI / Agent 安全的连结

1. STREAM 的 Triad 数就是你推理服务的物理天花板。Day 38 推导过 LLM decode 阶段是 memory-bound：每生成一个 token 要把整个模型权重从显存/内存流一遍。所以 吞吐上限 ≈ 内存带宽 / 每 token 读的字节数。你今天测的 Triad（内存版）和 nvidia-smi 里的 HBM 带宽（显存版）是同一逻辑。做容量规划时，先算这个理论上限，实测达到 60–80% 就算调优到位——盲目加 GPU 核数对 memory-bound 负载没用。

2. cache 友好 = 推理框架的隐形竞争力。LAB 2 里同样的算法因访存顺序差几倍。vLLM 的 PagedAttention、FlashAttention 的分块，本质都是把访存重排成 cache/显存友好的模式，减少来回搬运。你评估一个推理引擎快在哪，perf/nsight 里的 cache/HBM miss 率就是照妖镜——算法一样，访存效率决定生死。

3. 跨 NUMA 是"看不见的 P99 杀手"。LAB 5 测出的 30–50% 带宽损失，在生产里表现为：同样的模型、同样的卡，A 机器 TPOT 稳、B 机器忽高忽低——差别只是 B 的进程被调度器撒到两个 NUMA node、内存分配又错了节点。给推理进程做 numactl --cpunodebind --membind 绑定、让 GPU 挨着同 node 的 CPU/内存（nvidia-smi topo -m 看拓扑），是多卡机器的必修课。

4. mlock 是敏感数据不落盘的第一道锁。你的 Agent 安全产品里，API key、用户 prompt、中间明文一旦被换出到 swap，磁盘取证就能捞出来。对存密钥的内存区 mlock，配合退出前显式清零，是防"冷启动/磁盘取证"类攻击的标准手法。今天你亲手锁了一次，明天 Day 41 讲内存安全会把"敏感数据生命周期"补全。

5. vmstat 的 si/so 是"服务要挂"的最早信号。推理服务最怕 KV cache 撑爆物理内存后开始 swap——一旦 vmstat 的 si/so 常年非 0，延迟就从毫秒跳到秒级，比 OOM 直接杀掉还难查（因为进程还活着，只是慢得像死了）。把 si/so、available 内存做成监控告警，比等 OOM killer 出手要早得多。这也是为什么很多推理部署直接关掉 swap——宁可 OOM 快速失败，也不要 swap 拖着假活。
