本周三条主干结论

结论一：算术强度决定你受什么限制。 Day 36 定义的算术强度（arithmetic intensity） = 浮点运算次数 ÷ 从内存搬运的字节数（FLOP/Byte）。Day 38 我们算过：LLM 的 decode 阶段每生成一个 token，要把整个模型权重（7B 模型 FP16 约 14 GB）从 HBM 读一遍，却只做了大约 2×7×10⁹ 次乘加。算术强度约等于 2 FLOP/Byte，而 A100 的「拐点」在 100+ FLOP/Byte。差了将近两个数量级——所以 decode 的 GPU 利用率经常只有 5%~15%，卡不是在算，是在等内存。

结论二：提升利用率的唯一正路是提高 batch size。 因为权重只读一次，batch 里有多少个序列，就摊薄多少次。batch=1 时算术强度 ≈2，batch=64 时 ≈128，直接把 decode 从 memory-bound 推到 compute-bound 附近。但 batch 大小卡在哪儿？卡在 KV cache 吃掉的显存上。这就是今天的入口：谁能把 KV cache 管得更省，谁就能开更大的 batch，谁的吞吐就更高。

结论三：内存管理是性能问题，也是隔离问题。 Day 41 讲的所有二进制漏洞，根子都在「地址空间是一块可以随意越界读写的线性字节」。今天你会看到，PagedAttention 在 GPU 上重建了一层间接映射——它带来性能收益的同时，也天然带来了隔离边界（一个序列只能通过自己的 block table 触到自己的物理块）；而 prefix caching 又在这个边界上开了一道刻意的共享口子，于是安全问题从「越界」变成了「共享带来的信息泄露」。这条线今天走完。

2. 传统 KV cache 的原罪：预分配与三种碎片

2.1 先把 KV cache 讲清楚

KV cache 是自回归解码的核心加速手段。Transformer 每一层的注意力要用当前 token 的 query，去和历史所有 token 的 key、value 做计算。如果不缓存，生成第 n 个 token 时就要重算前 n−1 个 token 的 K 和 V，总代价是 O(n²) 的重复劳动。缓存下来之后，每步只需为新 token 计算一份 K/V 追加进去，代价降到 O(n)。

代价是显存。 单个 token 的 KV cache 大小（Day 38 推过，这里再写一遍，请务必记住这个公式）：

bytes_per_token = 2 (K 和 V 两份)
                × num_layers            # 层数
                × num_kv_heads          # 注意是 KV 头数，GQA/MQA 下远小于 query 头数
                × head_dim              # 每头维度
                × dtype_bytes           # FP16=2, FP8=1

# Llama-2-7B: 32 层, 32 个 KV 头(MHA), head_dim=128, FP16
# = 2 × 32 × 32 × 128 × 2 = 524288 B = 512 KB / token

# Llama-3-8B: 32 层, 8 个 KV 头(GQA), head_dim=128, FP16
# = 2 × 32 × 8 × 128 × 2 = 131072 B = 128 KB / token
直觉锚点：Llama-2-7B 上，一条 2048 token 的对话，KV cache 就要 2048 × 512 KB = 1 GB。一张 80 GB 的 A100 放完 14 GB 权重后剩 66 GB，理论上只够 66 条这样的对话同时在线。KV cache 不是边角料，它是和模型权重同一量级、甚至更大的显存消费者。

2.2 原罪：按「最大可能长度」预分配一整块连续显存

PagedAttention 出现之前（FasterTransformer、早期 HF generate、TGI 早期版本），KV cache 的管理方式简单粗暴：请求进来时，按 max_seq_len 预先申请一整块物理连续的显存，序列往里追加。

为什么要连续？因为 attention kernel 是按张量写的：它假设第 i 个 token 的 K 就在 base_ptr + i * stride。连续布局让 kernel 能做高效的合并访存（Day 31 学的 memory coalescing）。这个设计对 kernel 友好，对内存管理是灾难。

灾难长这样——假设 max_seq_len = 2048，但用户实际只聊了 30 个 token 就结束了：

2.3 这个问题你其实见过

请回想 Day 09（内存分配器）和 Day 08（虚拟内存与页表）。「要求物理连续 + 按最大值预分配 = 严重碎片」这个困境，操作系统在 1960 年代就撞上过，当年的名字叫「分段式内存管理」（segmentation）。每个进程要一整块连续物理内存，进程来来去去之后物理内存被切得七零八落，只能靠代价高昂的「紧凑化」（把所有进程搬家）来整理。

OS 的解法是分页（paging）：把物理内存切成固定大小的页帧（4 KB），把进程地址空间切成同样大小的页，用页表做映射。于是进程眼里的地址空间是连续的，物理上却可以任意零散。内部碎片被压到「最后一页的半页」，外部碎片直接消失（所有块一样大，任何空闲页都能满足任何请求）。

PagedAttention 的全部创意，就是把这套 1960 年代的答案，一比一搬到 GPU 显存里的 KV cache 上。

3.2 具体怎么切

block（块）是 PagedAttention 的最小分配单位，装固定数量的 token 的 KV。默认 block_size=16。一个 block 占的显存 = block_size × bytes_per_token，对 Llama-2-7B 就是 16 × 512 KB = 8 MB。

引擎启动时做一件事：把「总显存 − 模型权重 − 激活值峰值 − 预留量」剩下的全部显存，一次性切成等大的 block，编号 0..N−1，交给一个 block allocator 管理。这就是你在 vLLM 启动日志里看到的那行：

# vLLM 启动日志（版本不同措辞略有差异，含义一致）
INFO ... # GPU blocks: 7752, # CPU blocks: 512
INFO ... Maximum concurrency for 4096 tokens per request: 30.28x

7752 个 GPU block × 16 token/block = 124032 个 token 的 KV 容量。这个数字就是你这台机器的「KV 预算」，所有并发请求共享它。gpu_memory_utilization 参数（默认 0.9）直接决定了这个数字——它是「允许 vLLM 用掉整卡显存的比例」，剩下的留给 CUDA context、通信 buffer 和碎片。

物理显存池（启动时一次切好，之后不再向 CUDA 申请） ┌────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┐ │ b0 │ b1 │ b2 │ b3 │ b4 │ b5 │ b6 │ b7 │ b8 │ b9 │b10 │ ...│ 每块 16 token └────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┘ ▲ ▲ ▲ ▲ ▲ │ │ │ │ │ 序列 A 的逻辑视图（它以为自己是连续的）： [ token 0-15 ][ token 16-31 ][ token 32-47 ] ↓ block_table_A = [0, 3, 7] ← 物理上完全不连续 序列 B： [ token 0-15 ][ token 16-31 ] ↓ block_table_B = [2, 8]

3.3 收益立刻可算

内部碎片：现在只发生在每个序列的最后一个 block，最多浪费 15 个 token 的空间。对一条 500 token 的序列，浪费率从「(2048−500)/2048 = 75.6%」降到「最多 15/512 ≈ 2.9%」。

外部碎片：彻底消失。所有 block 等大，任何空闲 block 都能满足任何请求——这正是分页相对分段的根本优势。

预留浪费：消失。按需分配（on-demand）——序列生成到第 17 个 token 时才去要第二个 block，不再为「可能生成到 2048」提前占位。

论文实测：显存浪费从 60%~80% 降到 4% 以下，同等显存下能容纳的并发序列数提升 2~4 倍，端到端吞吐相对 HF Transformers 提升 14~24 倍，相对当时的 TGI 提升 2.2~3.5 倍。注意这个提升的来源：不是 kernel 算得更快了（PagedAttention 的 kernel 因为多了查表，单次执行其实比连续版本略慢 20%~26%），而是省下的显存换来了更大的 batch，更大的 batch 提高了算术强度，把 memory-bound 的 decode 推向了 compute-bound。这就是本周结论一和结论二的直接兑现。

4. Block table：逻辑块到物理块的翻译层

4.1 数据结构

block table 就是页表的极简版：一个每序列一份的整数数组，下标是逻辑块号，值是物理块号。翻译逻辑和 Day 08 的页表完全同构：

# 逻辑 token 位置 → 物理地址，全套翻译
BLOCK_SIZE = 16

def locate(token_idx, block_table):
    logical_block = token_idx // BLOCK_SIZE      # 页号
    offset        = token_idx %  BLOCK_SIZE      # 页内偏移
    physical_block = block_table[logical_block]  # 查页表
    return physical_block, offset

# 序列 A 的第 35 个 token，block_table_A = [0, 3, 7]
# logical_block = 35 // 16 = 2  → physical_block = 7
# offset        = 35 %  16 = 3
# 实际显存位置 = kv_cache_pool[7][3]

和 OS 页表的唯一区别是：没有 MMU 硬件替你做这件事。GPU 的 MMU 管的是 CUDA 虚拟地址，管不到「KV cache 内部的逻辑块」这层抽象。所以这次翻译必须写进 attention kernel 里，由线程自己算。这就是为什么 PagedAttention 需要一个定制 CUDA kernel，而不能直接用现成的 attention 实现。

4.2 kernel 里发生了什么

标准 attention kernel 的内层循环是「按顺序扫过一段连续显存」，PagedAttention kernel 的内层循环变成「按 block 分批，每批先查表拿到物理块地址，再扫这一块」。伪代码：

# 概念示意（真实 CUDA kernel 涉及 warp 分工、共享内存、在线 softmax，这里只保留结构）
def paged_attention(q, block_table, kv_pool, seq_len):
    acc, running_max, running_sum = 0, -inf, 0
    num_blocks = ceil(seq_len / BLOCK_SIZE)

    for i in range(num_blocks):                 # 逐 block 迭代
        phys = block_table[i]                   # ← 多出来的一次查表（放在共享内存里）
        K_blk = kv_pool.K[phys]                 # 一次读 16 个 token 的 K，块内仍然连续
        V_blk = kv_pool.V[phys]

        scores = q @ K_blk.T / sqrt(head_dim)
        # 在线 softmax（FlashAttention 风格）：边算边归一，不物化完整 attention 矩阵
        acc, running_max, running_sum = online_softmax_update(
            acc, running_max, running_sum, scores, V_blk)

    return acc / running_sum

三个设计细节值得注意，它们都直接呼应本周学的内存知识：

  • 为什么 block 内仍要连续：块内 16 个 token 是连续存放的，一个 warp 的 32 个线程读它时能形成合并访存（Day 45 会正式讲 memory coalescing，Day 31 的 cache line 是同一个道理）。如果粒度细到单 token，访存会退化成 gather，带宽利用率崩塌。block_size 的本质是「碎片浪费」和「访存效率」之间的旋钮：太小→查表开销大、访存零散；太大→内部碎片回归。16 是实践出来的甜点，长序列场景有人调到 32。
  • block table 放哪：它本身很小（一条 4096 token 的序列只有 256 个 int），一次性拷进 GPU 的 shared memory 或常量区，查表几乎不产生额外 HBM 流量。这是「用一次极便宜的间接寻址，换掉一大堆昂贵的显存浪费」。
  • 和 FlashAttention 的关系：两者正交，且在现代引擎里是叠加使用的。FlashAttention 优化的是「算的时候怎么不把 N×N 注意力矩阵写回 HBM」（Day 53 会细讲），PagedAttention 优化的是「KV 存在哪、怎么分配」。今天的 vLLM 用的是融合了两者的 kernel（FlashAttention 后端支持 paged KV），别把它们当成竞品。

5. Preemption：显存不够时的抢占、换出与重算

5.1 为什么一定会不够

按需分配有个副作用：你无法预知一个请求最终要用多少 block。调度器接了 40 个请求进来时它们都很短，跑着跑着每个都要生成 2000 token，block 池就会见底。这时候必须有人让路——这就是抢占（preemption）。

这个场景在 OS 里也似曾相识：物理内存不够时，内核会把某些进程的页换出到 swap 分区（Day 10）。vLLM 的选择更丰富，因为它掌握着一个 OS 没有的信息：被换出的数据是可以重新算出来的。

5.2 两条策略

Swap（换出）Recompute（重算）
做什么把该序列的 KV block 从 GPU 拷到 CPU pinned memory，释放 GPU block；恢复时拷回来直接丢弃 KV block，恢复时把「原始 prompt + 已生成的 token」当成新 prompt 重跑一次 prefill
代价2 × PCIe 传输。Gen4 x16 单向约 25 GB/s，换出 1 GB KV 约 40 ms，来回 80 ms一次 prefill 的算力。prefill 是 compute-bound，长 prompt 时代价高但可批处理
额外资源需要预留 CPU 内存（swap_space，默认 4 GB/GPU）不需要额外内存
适合beam search、parallel sampling 等多序列共享 block 的场景（重算会重复多次，不划算）单序列请求；vLLM 默认策略

vLLM 默认用 recompute，理由很硬：Day 38 的结论说 decode 是 memory-bound、prefill 是 compute-bound，而 GPU 的算力是过剩的、PCIe 带宽是稀缺的。用过剩的算力去换稀缺的带宽，是这个系统里几乎总是正确的交易。这个判断本身就是 Roofline 思维的直接应用。

5.3 抢占谁：调度策略

vLLM 的调度器维护三个队列：waiting（还没开始）、running（正在生成）、swapped（被换出的）。每一步调度时：

每个 step：
  1. 尝试为 running 队列里的每个序列分配它下一个 token 需要的 block
  2. 若 block 池耗尽：
       按 FCFS 的逆序（最晚到达的先被牺牲）选一个 victim
       → recompute 模式：释放它所有 block，把它踢回 waiting 队列头部
       → swap 模式：拷贝它的 block 到 CPU，移入 swapped 队列
       重复直到能装下当前 step
  3. 若还有空闲 block：从 swapped / waiting 队列里拉新序列进来（admission control）
  4. 执行一次前向

为什么牺牲「最晚到达的」？这是 FCFS 公平性的自然推论——先来的先做完，避免饥饿（starvation）。如果反过来牺牲最早的，长请求可能永远做不完。这和 Day 04 学的调度目标（吞吐 / 延迟 / 公平性三者权衡）是同一套语言。

运维信号：日志里出现 Sequence group ... is preempted by PreemptionMode.RECOMPUTE，或者 metrics 里 num_preemption_total 持续增长，说明你的 KV 预算相对于并发压力不足。三条路：降 max_num_seqs、升 gpu_memory_utilization、或者上 KV cache 量化（Day 52 讲）。频繁抢占会让 P99 延迟剧烈抖动——被重算的请求 TTFT 直接翻倍，这是线上最常见的「吞吐很好看但尾延迟很难看」的成因之一。

6. Prefix caching：共享前缀、写时复制与 radix 树

6.1 动机：你的 Agent 每次都在重复同一段 prefill

做 Agent 的人对这个场景太熟悉了：一个 system prompt 里塞了角色设定、20 个工具的 JSON schema、安全规则、few-shot 示例，轻松 3000~8000 token。每个用户的每一轮对话，都要把这几千个 token 重新 prefill 一遍——算出来的 K/V 和上一次一模一样，因为 attention 是因果的，前缀的 KV 不依赖后面的内容。

这是纯粹的浪费，而且是 TTFT（首 token 延迟）的主要成分。prefix caching（vLLM 里叫 automatic prefix caching，APC；SGLang 里叫 RadixAttention）就是把这段共享前缀的 KV block 留在显存里复用。

6.2 机制：block 哈希 + 引用计数 + COW

实现优雅得让人想鼓掌，而且又是从 OS 抄来的：

第一步，给每个满 block 算一个哈希。 哈希的输入不只是本块的 token，而是从序列开头到本块结尾的全部 token（实现上是「前一块的哈希 + 本块 token」的链式哈希）。为什么必须包含前缀历史？因为 attention 的 K/V 值依赖于该 token 之前的所有上下文；两个 block 里 token 相同但前缀不同，KV 值完全不同，混用就是算错。

block_hash[i] = hash(block_hash[i-1], tokens[i*16 : (i+1)*16])
# 只有"填满"的 block 才参与缓存；最后那个没填满的块不缓存（内容还会变）

第二步，用哈希表查找可复用的物理块。 新请求进来，把 prompt 切块算哈希，逐个查表。命中的块直接把物理块号填进新序列的 block table，并把该物理块的引用计数 +1。命中前缀的部分完全跳过 prefill 计算。

第三步，写时复制（copy-on-write）。 两个序列共享同一个物理块，谁都不能直接往里写。当某个序列要写入一个 ref_count > 1 的块时，allocator 分配一个新块、拷贝内容、把该序列的 block table 指向新块、旧块引用计数 −1。这和 Day 02 学的 fork() COW 是同一个机制，连术语都没改。

第四步，LRU 驱逐。 引用计数归零的块不立即回收，而是放进一个 LRU 空闲队列。若后续有请求命中它的哈希，直接「复活」；显存紧张时按最近最少使用逐出。vLLM 还做了一个细节：驱逐时优先逐出最长前缀链尾部的块，因为靠近根部的块（如 system prompt）被更多请求共享，价值更高。

共享一个 system prompt 的三个请求（block_size=16） [B0]──[B1]──[B2] ← system prompt，3 个块，ref_count = 3 │ ┌─────────────┼─────────────┐ │ │ │ [B3] [B7] [B9] ← 各自的用户输入，ref_count = 1 │ │ │ [B4] [B8] [B10] ← 各自生成的 token 这就是一棵 radix 树（SGLang 直接把它叫 RadixAttention） 命中 = 从根往下走，走多远就省多少 prefill

python - <<'PY'
import time, requests
SYS = "You are a security analyst. " * 400      # 约 2000+ token 的前缀

    r = requests.post("http://localhost:8000/v1/completions", json={

典型场景收益：system prompt 占比越高、并发用户越多，收益越大。多轮对话中每一轮都能命中之前所有轮次的前缀，长会话的 TTFT 可以降到几十毫秒量级。代价：哈希计算和查表有 CPU 开销（在极短 prompt、无共享的场景下反而略微变慢），以及缓存块占着显存不还，会挤压可用 batch——所以它不是无脑开的银弹，要看你的流量形态。

7. 把本周知识算成数字：容量估算与调参 cheat sheet

7.1 一个能直接用的估算脚本

#!/usr/bin/env python3
"""估算某模型在某卡上的 KV 预算与最大并发。把本周的公式全串起来。"""

def kv_bytes_per_token(layers, kv_heads, head_dim, dtype_bytes=2):
    return 2 * layers * kv_heads * head_dim * dtype_bytes

def plan(name, gpu_gb, weight_gb, layers, kv_heads, head_dim,
         seq_len, dtype_bytes=2, util=0.90, block_size=16, act_gb=2.0):
    total   = gpu_gb * util                         # vLLM 实际接管的显存
    kv_gb   = total - weight_gb - act_gb            # 留给 KV cache 的
    per_tok = kv_bytes_per_token(layers, kv_heads, head_dim, dtype_bytes)
    n_tok   = int(kv_gb * 1024**3 / per_tok)
    n_block = n_tok // block_size
    concur  = n_tok / seq_len
    print(f"{name}")
    print(f"  KV/token      : {per_tok/1024:.0f} KB")
    print(f"  KV 预算       : {kv_gb:.1f} GB → {n_tok:,} token → {n_block:,} blocks")
    print(f"  seq_len={seq_len} 时最大并发 ≈ {concur:.0f}")
    print(f"  单条 {seq_len} token 序列占 {seq_len*per_tok/1024**3:.2f} GB\n")

# A100-80G
plan("Llama-2-7B  (MHA, FP16 KV)", 80, 13.5, 32, 32, 128, 4096)
plan("Llama-3-8B  (GQA, FP16 KV)", 80, 16.0, 32,  8, 128, 4096)
plan("Llama-3-8B  (GQA, FP8  KV)", 80, 16.0, 32,  8, 128, 4096, dtype_bytes=1)
plan("Llama-3-70B (GQA, FP16, TP=4，按单卡算)", 80, 35.0, 80, 8, 128, 4096)

跑一遍你会看到几件事：(1) GQA 的威力——Llama-3-8B 的 KV 只有 Llama-2-7B 的四分之一（8 个 KV 头 vs 32 个），并发能力直接翻几倍，这是近两年模型架构演进里对推理成本影响最大的单点改动；(2) KV 量化到 FP8 直接把并发再翻倍，代价是精度损失（Day 52 细讲）；(3) 70B 模型即使 TP=4 切开，单卡权重就吃掉 35 GB，KV 预算被严重挤压，这就是为什么大模型服务对显存容量（H200 的 141 GB vs H100 的 80 GB）如此敏感。

7.3 一条完整的诊断流程

# 症状：吞吐上不去 / P99 抖动
# 1. 先确认是不是 KV 不够（看抢占）
curl -s localhost:8000/metrics | grep -E "preemption|running|waiting|gpu_cache_usage"
#    gpu_cache_usage_perc 长期贴近 1.0 + preemption 增长 → KV 预算不足

# 2. 确认 GPU 是不是真的在算（看利用率与显存带宽）
nvidia-smi dmon -s pucm -c 20
#    sm% 低、mem% 高 → 典型 memory-bound decode（Day 38 的结论）→ 该加 batch

# 3. 确认 batch 有没有开起来
curl -s localhost:8000/metrics | grep num_requests_running
#    running 长期个位数而 waiting 很长 → 被 KV 预算或 max_num_seqs 卡住了

# 4. 确认前缀有没有被浪费
curl -s localhost:8000/metrics | grep prefix_cache
#    queries 高但 hits 低 → 检查 prompt 是否每次都带了随机内容（时间戳、UUID）在最前面
第 4 条是实战中最常见的坑：很多人把「当前时间」「request id」「用户名」拼在 system prompt 的最前面，导致每个请求的第一个 block 哈希都不同，整棵前缀树一次都命不中。规则很简单：把稳定的内容放最前，把变化的内容放最后。这条规则的根源就是 attention 的因果性——前缀变了，后面所有 KV 都失效。

与 AI / Agent 安全的连结

场景一：prefix caching 是一条实打实的跨用户时间侧信道。 这是本节最重要的一条。攻击者可以构造一个 prompt，测量它的 TTFT：如果显著偏低，说明这段前缀已经在缓存里，也就意味着近期有别的用户发过以它开头的请求。逐 block 二分探测，攻击者能一段一段地还原出别人的 system prompt、RAG 注入的文档片段，甚至用户输入的开头。这不是理论——2024 年以来已有多篇工作系统化地演示了对公有推理服务的 prompt 窃取。Day 34 讲的 cache timing 攻击范式（Prime+Probe、Flush+Reload）在这里以「语义层」的形式完整复现了：共享的缓存 + 可测量的时间差 = 侧信道，介质从 CPU L3 换成了 GPU 上的 KV block 而已。缓解措施：多租户服务应当按租户/会话隔离前缀缓存命名空间（把 tenant_id 混进 block hash），或对 TTFT 加入随机延迟；至少不要跨租户共享同一棵 radix 树。作为 Agent 安全工程师，这是你在给业务方做推理平台评审时必须问的第一个问题。

场景二：block table 是一道天然的隔离边界，也是一个值得审计的点。 PagedAttention 的间接映射意味着一个序列只能触及自己 block table 里列出的物理块——这在结构上等价于 Day 08 讲的页表隔离。但这道边界是软件强制的（kernel 里的查表），不像 CPU 有 MMU 硬件兜底。一旦 block table 的下标计算、引用计数、COW 判断中有 off-by-one 或竞态，后果就是一个用户读到另一个用户的 KV——这在语义上等价于 Day 41 讲的越界读，只是泄露的不是内存字节，而是别人的对话内容。这类 bug 在推理引擎的 issue 里真实出现过（尤其是 beam search、多序列 fork、抢占恢复这些复杂路径）。对安全评审来说，引用计数的每一处 +1/−1 和每一处 COW 判断都是高危代码，值得单独拉出来做 fuzzing（Day 41 的技能正好用上）。

场景三：KV cache 是残留敏感数据的载体。 一次对话里的所有内容——用户上传的合同、API key、内部文档——都以 K/V 张量的形式躺在显存 block 里。请求结束后，block 被放回空闲池，但内容通常不清零（清零要写 GB 级显存，代价太高）。如果分配逻辑有缺陷、或者新序列读到了尚未覆写的区域，就是显存版的 use-after-free 信息泄露。更现实的风险是进程外：同一张卡上的另一个容器若能通过 GPU 驱动漏洞读取显存（Day 48 会讲 GPU 多租户与 MIG 隔离），KV cache 就是最肥的目标——它比模型权重值钱得多，因为权重是公开的，对话内容不是。防御方向：敏感场景禁用跨请求 block 复用、按会话结束显式 zero-fill 高敏感块、依赖 MIG 做硬件级显存隔离。

场景四：抢占机制是一条低成本 DoS 路径。 攻击者不需要打满你的带宽，只要构造一批「prompt 极长 + max_tokens 极大」的请求，就能迅速吃光 block 池，触发持续抢占。被重算的正常用户请求 TTFT 翻倍甚至更差，整个服务的 P99 崩掉，而攻击者的请求量可能只有几十 QPS——这是典型的算法复杂度攻击（algorithmic complexity attack），成本极不对称。防御要点：网关层按 prompt_tokens + max_tokens 加权限流（而不是按请求数限流，那毫无意义）、对单请求设 max_model_len 硬上限、按租户设 KV 配额。Day 104 和 Day 107 会系统讲限流算法，但今天你要先建立这个直觉：对 LLM 服务来说，「一个请求」不是一个有意义的计量单位，token 和显存占用时长才是。

场景五：Agent 系统的长上下文让 KV 管理成为架构主约束。 一个真实的 Agent 循环——system prompt + 工具 schema + 历史轮次 + RAG 检索到的文档 + 工具返回结果——上下文轻松突破 32K，且随着轮次单调增长。按今天的公式算：Llama-3-8B 上一条 32K 的会话就要 4 GB KV。这意味着一张 80 GB 的卡最多同时服务十几个活跃 Agent 会话，容量规划完全由 KV 决定而非算力。所以做 Agent 平台时，上下文压缩、会话状态的换出与恢复、以及「哪些历史该丢」的策略，都不是产品优化项，而是系统能不能跑起来的前提。同时它还是攻击面：memory poisoning（Day 160 的主题）之所以危险，正是因为被污染的内容会长期驻留在这条越来越长、且被反复复用的上下文里——而 prefix caching 会让这段被污染的前缀在缓存中持续存活，影响后续所有命中它的请求。
