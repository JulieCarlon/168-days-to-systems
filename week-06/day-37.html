1. NUMA 的起源：SMP 为什么撞了墙

要理解 NUMA，先要理解它取代的东西：SMP（Symmetric Multi-Processing，对称多处理）。

在早期的多核/多路服务器里，所有 CPU 通过一条共享总线连到同一块内存控制器，再连到所有内存条。「对称」的意思是：任何一个 CPU 访问任何一个内存地址，代价都完全一样。程序员根本不用操心「内存在哪」，因为哪儿都一样远。

SMP（共享总线，对称） CPU0 CPU1 CPU2 CPU3 │ │ │ │ └──────┴───┬──┴──────┘ │ ← 一条共享总线（瓶颈！） ┌──────┴──────┐ │ 内存控制器 │ └──────┬──────┘ [ 全部内存条 ]

这个设计很优雅，但有一个致命问题：那条总线是所有 CPU 抢的独木桥。2 颗核还好，8 颗、16 颗核同时想读内存，总线带宽就成了硬瓶颈。就像一栋楼只有一部电梯，人少时没事，上班高峰所有人挤在一部电梯前，加再多楼层（核）也没用——你被电梯（总线）卡死了。这叫总线争用（bus contention）。

硬件工程师的解法很直接：既然一个内存控制器喂不饱那么多核，那就给每组核配一个自己的内存控制器和一堆自己的内存条。于是服务器被切成若干「区」，每个区 = 一组核 + 一个内存控制器 + 一堆内存。这个区就叫 NUMA node（NUMA 节点）。

代价是：一个核访问「自己区」的内存很快，访问「别的区」的内存要先穿过 node 之间的互联（Intel 叫 QPI/UPI，AMD 叫 Infinity Fabric），慢一截。于是「访问哪块内存代价一样」的对称性被打破了——这就是 Non-Uniform Memory Access，非一致内存访问。NUMA 不是一个「新功能」，它是「为了扩展核数不得不付出的代价」。

一句话记住：SMP 是「所有核共享一块内存，公平但堵车」；NUMA 是「每组核分到一块近内存，快但不对称」。今天几乎所有双路/多路服务器（你租的 GPU 机器 99% 是双路）都是 NUMA。单颗桌面 CPU 通常是单 node，但也有例外（见 §2）。

2. NUMA 架构长什么样：node、local、remote

一台典型的双路服务器（比如 2× Intel Xeon 或 2× AMD EPYC）长这样：

NUMA node 0 NUMA node 1 ┌────────────────────┐ ┌────────────────────┐ │ CPU socket 0 │ │ CPU socket 1 │ │ core 0..31 │◄──────►│ core 32..63 │ │ L1/L2/L3 cache │ UPI/ │ L1/L2/L3 cache │ │ 内存控制器 │ Fabric │ 内存控制器 │ └─────────┬──────────┘ 互联 └─────────┬──────────┘ [ 本地内存 256GB ] [ 本地内存 256GB ] (local) (对 node0 是 remote)

关键术语：

  • Local access（本地访问）：core 0 读它同一个 node 上的内存。只走本 node 的内存控制器，最快。
  • Remote access（远程访问）：core 0 读 node 1 上的内存。要先穿过 UPI/Fabric 互联，到对方的内存控制器取数据再传回来。多一跳，慢。
  • NUMA distance（距离）：内核用一个矩阵描述 node 之间的相对代价，本地记为 10，远程一跳常见是 21（约 2.1 倍）。这不是纳秒，是相对比值。

类比：把公司想成两层楼，每层有自己的茶水间。你在 3 楼，去 3 楼茶水间倒水（local）走两步就到；去 4 楼茶水间（remote）要爬楼梯。水都是同样的水，但「取水的时间」取决于你在哪层、水在哪层。NUMA 就是逼你开始关心「数据放在哪个楼层」。

现代 CPU 让情况更复杂了。AMD EPYC 内部由多个 chiplet（小芯片，CCD） 拼成，可以配置成「一颗物理 CPU 里就有多个 NUMA node」（BIOS 里叫 NPS=Nodes Per Socket，可设 1/2/4）。所以「node 数」不一定等于「CPU 插槽数」。一台双路 EPYC 开 NPS=4 就有 8 个 NUMA node。别假设「一颗 CPU = 一个 node」——一切以 numactl -H 实测为准。

3. 本地 vs 远程访问的代价：具体数字

抽象的「慢一截」不够，我们要量化。以一台典型双路服务器为参考（数量级，不同代际有差异）：

访问类型典型延迟相对本地带宽影响
L1 cache 命中~1 ns——
L3 cache 命中~15 ns——
本地 DRAM~80–100 ns1.0×满带宽（如单 node ~150 GB/s）
远程 DRAM（一跳）~130–200 ns1.5–2.0×受 UPI/Fabric 限制，常掉到 60–70%

两条独立的税，都要交：

  1. 延迟税：远程访问每次多 50–100 ns。对延迟敏感、指针追逐型（pointer-chasing）的负载（图遍历、哈希表、链表、KV cache 元数据）打击巨大。
  2. 带宽税：node 间互联（UPI/Fabric）的带宽远小于本地内存带宽。当大批量数据跨 node 流动，互联链路会先饱和，成为新瓶颈——这对 LLM 推理这种 memory-bound 负载（昨天讲过）尤其致命。

更隐蔽的是争用放大：如果 node 0 上跑的 8 个进程全去访问 node 1 的内存，它们不仅各自慢，还会一起把 UPI 链路挤爆，形成「远程访问 → 互联拥塞 → 更慢 → 队列更长」的恶性循环。这就是为什么一台机器 CPU 利用率没满、内存也没满，吞吐却上不去——瓶颈藏在你看不见的互联上。

我们可以用一个极简实验感受它。下面这段用 numactl 强制「在 node 0 上跑、但只用 node 1 的内存」，和「node 0 上跑、用 node 0 内存」对比：

# 需要先装 numactl：  sudo apt install numactl
# 本地：CPU 和内存都在 node 0
numactl --cpunodebind=0 --membind=0 \
  python3 -c "import numpy as np,time; a=np.ones(2_000_000_000//8); t=time.time(); \
  [a.sum() for _ in range(5)]; print('local ', time.time()-t)"

# 远程：CPU 在 node 0，但内存强制放 node 1
numactl --cpunodebind=0 --membind=1 \
  python3 -c "import numpy as np,time; a=np.ones(2_000_000_000//8); t=time.time(); \
  [a.sum() for _ in range(5)]; print('remote', time.time()-t)"

在双路机器上，remote 那次通常比 local 慢 30–60%。这就是「隐性税」的真面目——同样的代码、同样的核、同样的数据量，只因为内存放错了 node。

4. 看见拓扑：numactl 与 lstopo

你无法优化你看不见的东西。三件套：numactl -H 看逻辑拓扑，lstopo 看图形化全貌，numastat 看命中/失配统计。

numactl -H：node 清单与距离矩阵

numactl -H     # -H = --hardware

典型输出（双路，2 node）：

available: 2 nodes (0-1)
node 0 cpus: 0 1 2 ... 31          ← node0 拥有哪些逻辑核
node 0 size: 257669 MB             ← node0 本地内存总量
node 0 free: 251020 MB
node 1 cpus: 32 33 ... 63
node 1 size: 258011 MB
node 1 free: 249800 MB
node distances:
node   0   1
  0:  10  21     ← 0→0 本地=10, 0→1 远程=21（约 2.1 倍代价）
  1:  21  10

这张 distance matrix（距离矩阵）是内核调度器和内存分配器决策的依据。读它的方法：对角线永远是 10（本地基准），越偏离对角线数字越大代表越远。四路机器可能出现 10 / 21 / 31 这样的多档距离——有些 node 之间要跳两跳。

lstopo：一张图看懂整机

sudo apt install hwloc          # lstopo 属于 hwloc 包
lstopo --of png > topo.png      # 导出整机拓扑图
lstopo --of console             # 纯文本版，SSH 里也能看

lstopo 会画出每个 NUMA node、里面的 L3/L2/L1、每个物理核和超线程，以及——关键——PCIe 设备（GPU、网卡、NVMe）挂在哪个 node 下面。这是把 GPU 绑到正确 CPU 的地图，第 7 节会用到。

numastat：本地命中率

numastat            # 全局：numa_hit vs numa_miss vs numa_foreign
numastat -p $(pgrep -f my_server)   # 看某进程的每 node 内存分布

关注两个数：numa_hit（成功在期望 node 上分到内存的次数）和 numa_miss（没分到、被迫用了别的 node）。numa_miss 持续增长 = 你的负载正在大量交远程税，该动手绑定了。

5. 四种内存分配策略与 first-touch 陷阱

Linux 默认怎么决定「一块新申请的内存放哪个 node」？答案不是「申请时」决定的，而是——谁第一个写它，就放谁那边。这叫 first-touch（首次触碰）策略，是 NUMA 世界最重要、也最容易踩坑的规则。

注意：malloc()/np.empty() 只是划出虚拟地址，还没有真正的物理页。物理页要等你第一次写入那个地址、触发缺页中断（还记得 Day 10 的 page fault 吗）时才分配——而内核这时会把它放在执行写入的那个核所在的 node上。

first-touch 陷阱的经典翻车现场：主线程先 np.zeros(huge) 把整个数组初始化（在 node 0 上跑），于是所有物理页都落到 node 0。之后你开一个线程池，一半线程被调度到 node 1 的核上去处理这个数组——它们全程在交远程税，而你以为「数据已经初始化好了、很公平」。正确做法是让每个线程去初始化自己将要处理的那一段（并行 first-touch），这样物理页就自然分布到各自的 node。

如果不想被 first-touch 牵着走，可以用 numactl 或 libnuma API 显式指定策略，共 4 种：

策略numactl 参数行为适合
local / default（不加）first-touch，谁碰谁的 node单进程、线程本地性好的负载
bind--membind=0只能用指定 node，用完宁可 OOM 也不去别的 node严格隔离、延迟敏感服务
preferred--preferred=0优先 node 0，满了才溢出到别的 node（软约束）希望本地但不想 OOM
interleave--interleave=all物理页轮流撒在各 node 上（round-robin）大数组被所有核平均访问、带宽敏感

几个高频用法：

# 把整个进程钉在 node 0（CPU 和内存都是）——延迟敏感服务的标准姿势
numactl --cpunodebind=0 --membind=0 ./my_latency_service

# 大内存分析任务，希望带宽最大化、内存均摊到两个 node
numactl --interleave=all python3 big_matrix_job.py

# 优先本地但允许溢出，避免因单 node 内存不够而 OOM
numactl --cpunodebind=1 --preferred=1 ./worker

bind 还是 interleave？取决于访问模式。如果每个进程只碰自己那一小块（比如 8 个独立 worker，各管各的数据），用 --cpunodebind + --membind 把每个 worker 钉死在一个 node，让它全程本地，最好。如果是一个大对象被所有核共同访问（比如一个共享的大 embedding 表），没有哪个 node 是「主人」，那 --interleave 把它摊开，避免所有核挤向同一个 node 的内存控制器造成热点。interleave 用「大家都稍微慢一点」换「没有人被远程访问 + 热点拖垮」。

另外，内核有个自动搬运机制叫 AutoNUMA / NUMA balancing（/proc/sys/kernel/numa_balancing）：它周期性地检查页面被谁频繁访问，然后把页迁到那个 node。听起来智能，但迁移本身有开销、且对短生命周期负载常常帮倒忙。生产上对延迟敏感服务经常显式关掉它（echo 0 > /proc/sys/kernel/numa_balancing），改用手动绑定，因为「可预测」比「平均可能更好但会抖动」更重要。

6. NUMA 对多卡训练/推理的影响

现在把 NUMA 接回你的本职战场。一台 8 卡训练机通常是双路 CPU + 8 张 GPU，GPU 通过 PCIe/PLX switch 分挂在两个 CPU 下面：GPU 0–3 挂在 node 0，GPU 4–7 挂在 node 1。这个物理事实制造了三个隐性性能陷阱：

陷阱一：数据加载路径跨 node

训练时 DataLoader 的 worker 进程从磁盘/内存读数据，做预处理，再 host-to-device 拷贝到 GPU。如果 worker 被调度到 node 1 的核，而它服务的 GPU 挂在 node 0，那么：数据先落到 node 1 内存 → 跨 UPI 搬到 node 0 → 再经 PCIe 上 GPU。每个 batch 都白白多一次跨 node 搬运。正确做法：把 ranki 的进程（含它的 DataLoader）绑到「它的 GPU 所在的那个 node」。

陷阱二：pinned memory 分配在错的 node

为了让 GPU DMA 更快，PyTorch 用 pinned（page-locked）memory 做 host↔device 传输的中转缓冲。如果这块 pinned buffer 分配在 node 1、但 DMA 目标 GPU 在 node 0，PCIe 事务要跨 UPI，带宽直接打折。绑定 CPU node 后，pinned 内存会自然落在本地（因为 first-touch）。

陷阱三：集合通信（NCCL）拓扑不匹配

多卡 AllReduce 时，如果 GPU 间走的是 NVLink，NUMA 影响较小；但一旦有 GPU 通过 CPU/PCIe 中转（node 0 的 GPU 和 node 1 的 GPU 通信要过 UPI），跨 node 的那一跳会拖慢整个集合操作的木桶短板。这正是明天（GPU 互联）和后面 NCCL 章节的核心。

标准的「NUMA 感知启动」长这样——每个 rank 绑到它 GPU 对应的 CPU node：

# 先查 GPU 挂在哪个 node（见第 7 节）
# 假设 GPU0 在 node0，用 numactl 把这个 rank 钉过去
CUDA_VISIBLE_DEVICES=0 numactl --cpunodebind=0 --membind=0 \
  python train.py --local_rank 0

# 生产里一般用 torchrun + 一个 wrapper 脚本自动算 node
# 也可用 nvidia 提供的绑定工具，或在 launch 脚本里读 nvidia-smi topo

效果有多大？在数据加载重、host-device 拷贝频繁的训练里，正确的 NUMA 绑定能把每步时间降低 10–30%；对 memory-bound 的 LLM 推理（vLLM 多实例部署，每个实例钉一个 node + 对应 GPU），端到端吞吐提升 15–25% 是常见的。这是「不改一行模型代码、纯靠摆对内存位置」拿到的免费加速——也是资深工程师和调包侠的分水岭之一。

7. GPU-CPU NUMA 拓扑：nvidia-smi topo

要做绑定，先得知道「哪张卡挂在哪个 node、哪两张卡之间怎么连」。这张地图由 nvidia-smi topo -m 给出：

nvidia-smi topo -m

典型输出（节选，4 卡）：

        GPU0    GPU1    GPU2    GPU3    CPU Affinity    NUMA Affinity
GPU0     X      NV4     SYS     SYS     0-31            0
GPU1    NV4      X      SYS     SYS     0-31            0
GPU2    SYS     SYS      X      NV4     32-63           1
GPU3    SYS     SYS     NV4      X      32-63           1

读这张表：

  • NUMA Affinity 列直接告诉你：GPU0/1 属于 node 0，GPU2/3 属于 node 1。这就是绑定依据。
  • CPU Affinity 列：GPU0 最该用核 0–31（node 0 的核）。numactl --cpunodebind=0 正好覆盖它。
  • 矩阵里的连接类型，从快到慢：NV#（NVLink，# 是链路数，最快）> PIX（同一 PCIe switch）> PXB（跨多个 switch）> PHB（经过 host bridge）> NODE（同 NUMA node 内）> SYS（跨 NUMA node，要过 UPI，最慢）。

上面的例子里，GPU0↔GPU1 是 NV4（4 条 NVLink，飞快），但 GPU0↔GPU2 是 SYS（跨 node，最慢）。这直接告诉你：如果做 2 卡数据并行，选 GPU0+GPU1 或 GPU2+GPU3，绝不要选 GPU0+GPU2——否则每次 AllReduce 都走最慢的 SYS 路径。很多人随手 CUDA_VISIBLE_DEVICES=0,2 就开跑，性能莫名其妙差一截，根因就在这张表里。

完整的「查拓扑 → 绑定」工作流：

# 1. 看每张卡的 NUMA 归属
nvidia-smi topo -m

# 2. 也可以直接读 sysfs（脚本里自动化用这个）
cat /sys/bus/pci/devices/0000:17:00.0/numa_node   # 输出 0 或 1，-1 表示未知

# 3. 确认 node 的核范围
numactl -H

# 4. 启动时对号入座：GPU0(node0) → 绑 node0
CUDA_VISIBLE_DEVICES=0 numactl --cpunodebind=0 --membind=0 python serve.py
一个反直觉但要记住的点：把进程绑到「GPU 所在的 node」几乎总是对的；但如果你手动绑错了 node（进程在 node0、GPU 在 node1），会比完全不绑还慢——因为不绑时内核的 first-touch 至少有概率蒙对，而你绑错等于把每次 host-device 传输都强制走 UPI。所以绑定要么绑对，要么别乱绑。导读里那个问题的答案就在这。

与 AI / Agent 安全的连结

1. 多租户 GPU 隔离与「NUMA 侧信道」。你在做 Agent 安全，多租户推理平台是常见场景。当两个租户的容器被调度到同一个 NUMA node、共享同一条 UPI 链路和内存控制器时，一个租户的高强度远程访问会拖慢另一个租户——这既是性能干扰，也是一条时间侧信道：攻击者可以通过测量自己内存访问延迟的抖动，推断同 node 邻居的负载模式（是否正在跑大 batch 推理、是否在做 KV cache 换页）。NUMA-aware 的调度隔离（把敏感租户钉到独占 node）是缓解手段之一。

2. 推理服务的可预测延迟与 SLA 攻击面。安全不只是防泄露，也包括可用性。如果你的 LLM 网关承诺 P99 < 200ms，而底层因为没做 NUMA 绑定导致延迟随调度器心情在 100–300ms 抖动，攻击者只要制造跨 node 争用（比如故意提交能触发大量远程内存访问的请求）就能把 P99 顶穿，形成一种低成本的性能型 DoS。把关键路径绑死在本地 node，是让延迟可预测、从而可防御的前提。

3. 沙箱资源核算的盲区。你给 Agent 的 code-interpreter 工具做沙箱时，通常用 cgroups 限制 CPU 份额和内存上限（下周容器章节会讲）。但 cgroups 默认不感知 NUMA 带宽：一个恶意/失控的沙箱进程即使 CPU 配额很低，也能通过疯狂的跨 node 内存访问把 UPI 链路打满，殃及同机所有其他工作负载。资源核算若只看 CPU% 和 RSS，会漏掉「互联带宽」这一维——这是设计 Agent 沙箱时容易忽略的攻击面。

4. 内存取证与残留数据。NUMA 让「物理内存布局」变得和逻辑地址高度相关。在做 GPU/内存多租户安全时，理解物理页落在哪个 node、pinned buffer 复用时是否清零，关系到跨租户显存/内存残留是否可被下一个租户读到。绑定策略和分配器行为共同决定了残留数据的可预测性——这是 Day 48（GPU 多租户安全）会深入的伏笔。

5. 性能基线即异常检测基线。当你为推理集群建立行为基线（用于检测被投毒/被劫持的异常负载）时，NUMA 命中率（numa_hit/numa_miss）本身就是一个信号维度。一个平时本地命中率 95% 的服务突然 remote 访问飙升，可能意味着有非预期进程被塞进了这台机器、或调度被恶意扰动。把 numastat 纳入监控，等于给「谁在偷偷用我的内存带宽」装了一个探针。

在一台双路服务器（或云上的双 socket 实例）上装 numactl，跑第 3 节那两条命令（local vs remote），记录两次耗时并算出百分比差。如果你手上只有单 node 机器，numactl -H 会显示 available: 1 nodes——那就把这条结论写下来：为什么笔记本/单路桌面机通常测不出 NUMA 差异？

35 分钟 · 思考题

你部署一个 vLLM 推理服务，模型权重占 40GB，机器是双路、每 node 256GB 内存、单 node 本地带宽 150GB/s、UPI 带宽约 40GB/s。你打算在这台机器上跑两个独立 vLLM 实例（各用一张 GPU）。请设计内存/CPU 绑定方案，并解释：为什么「两个实例各钉一个 node」通常优于「两个实例都用 --interleave=all」？在什么情况下 interleave 反而更好？

明日预告 · Day 38 · 为什么 LLM 推理是 memory-bound。今天我们反复说 LLM 推理是「memory-bound」，明天就把这句话彻底讲透：从 prefill 和 decode 两个阶段的本质差异出发，亲手推导 decode 阶段的算术强度（arithmetic intensity）为什么低到可怜、KV cache 的内存占用公式怎么算、为什么 batching 能显著提升 GPU 利用率、量化又是从哪个环节抠出加速的。学完你能算出 Llama-2 7B/70B 在给定显存下的吞吐上限——这是所有推理优化的第一性原理。
